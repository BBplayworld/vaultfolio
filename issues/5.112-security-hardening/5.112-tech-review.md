# 5.112 보안 강화 — tech-review (developer, 2026-11-14)

대상: origin/main 기준. 코드 변경 없음. 위험 등급 초안: **risk:high** (공유 토큰 형식 변경 + 서버 저장 구독 형식 변경).

## ① 공유 v73 형식
**현황**: `asset-storage.ts:612 cryptWithKey`(주기 16 문자 시프트, 사실상 난독화), localKey는 `Math.random().toString(36)` 12자(`tool-menu.tsx:143`, `use-share-artifacts.ts:28`). `generateShareToken/parseShareToken`은 동기 함수.

**v73A 사양**
- URL 키: `crypto.getRandomValues` 16바이트(128비트). 링크 표기는 **hex 32자 권장**. base64url은 `_`·`-`를 포함해 `share:{key}_{localKey}` 분할(`asset-data-context.tsx:339` split("_"))과 충돌하므로, 쓰려면 첫 `_` 기준 분할로 바꿔야 한다. hex면 링크 형식(`#share=share:key_localKey`)과 파서 변경 0.
- 키 유도: PBKDF2-SHA256(password=PIN 4자리, salt=URL키(16B)‖토큰salt(16B), 150k회) → AES-256 키(WebCrypto `deriveKey`). 150k는 모바일 약 50~150ms 수준이라 허용 가능하나 preview 실측으로 확정한다.
- 암호화: AES-256-GCM, nonce 12바이트 무작위, AAD="v73A". 순서는 **LZString 압축(`compressToUint8Array`) → 암호화**. 기존 "OK|" 접두는 GCM 태그가 대신하므로 제거.
- 토큰: `"v73A" + base64url(salt16 ‖ nonce12 ‖ ct ‖ tag16)`. 오답 PIN·URL키 손상·변조는 모두 GCM 인증 실패 → null (기존 invalid-access 흐름 그대로).
- **PIN 무차별 대입 근거**: 서버 유출 시 공격자는 토큰만 갖고 URL 키가 없다. 키 유도 입력에 128비트 URL 키가 들어가므로 PIN 10^4 전수 시도도 2^128 탐색이 필요해 불가능하다. 단, **링크가 통째로 유출되면 PIN 4자리(10^4)만 남아 오프라인으로 뚫린다**(PBKDF2는 비용만 올림). PIN은 "링크 전달 경로와 다른 경로로 전달하는 2요소"이며, 보안은 URL 키 비공개에 의존한다. 이 한계는 사용자 문구에 단정적 표현("완벽") 금지.
- **서버 `/api/share`**: POST는 `v73A`만 허용(v72Z 신규 저장 거부), GET은 v72Z·v73A 모두 반환. v72Z는 신규가 없으므로 GET의 sliding TTL 연장을 끄면 최대 30일 안에 자연 소멸한다. `MAX_TOKEN_LEN`은 유지. 주의: salt·nonce가 무작위라 **같은 자산 → 같은 key(sha256[:10]) 성질이 사라진다**. 중복 방지는 기존 owner_id 삭제 로직으로 충분.
- v71P/v71N 읽기 경로(구 링크)는 유지.
- **공유 경로 전수**: ① `tool-menu.tsx:143~159` 링크 공유 ② `use-share-artifacts.ts` 웹→PWA 일회성 코드(`pwa-install-flow.tsx:157`이 사용, `pwa-connect-prompt.tsx`가 입력) ③ 수신 측 `asset-data-context.tsx:332~345`(resolveShareToken)·`:1001`·`:1046`(parseShareToken). 인증카드(`header-menu/share/*`)는 이미지 렌더이며 토큰·암호화 경로가 아니므로 변경 없음. sync:(클라우드 동기화)는 별도 E2EE라 범위 밖.
- **비동기 변경**: `generateShareToken`·`parseShareToken`이 async가 된다. 호출부는 tool-menu(이미 async 핸들러), use-share-artifacts(async), asset-data-context 2곳(수신 effect·PIN 제출 핸들러에 await 추가), 기존 테스트. 암호 로직은 신규 `src/lib/asset/share-crypto.ts`로 분리하고 asset-storage.ts는 얇게 유지. WebCrypto는 HTTPS·localhost에서만 동작(운영·preview 모두 충족).
- **구버전 혼재**: 구 클라이언트는 v73A를 파싱하지 못해 "잘못된 링크"로 표시(데이터 손상 없음). 새 클라이언트는 v72Z를 읽는다.
- **테스트**: 왕복, 오답 PIN, 비트 변조 1곳(salt·nonce·ct 각각), URL키 틀림, v72Z 고정 벡터 하위호환(기존 토큰 fixture), v71P/N 회귀, 토큰 길이(v72Z 대비 ≤ +15% 및 상한 900k 이내), nonce 재사용 없음(2회 생성 토큰 상이).

## ② IP 미저장
**IP 사용처 전수** (`src/server/api-guard.ts`)
1. `getClientIp`(:24) — 모든 라우트.
2. L1 메모리 버킷 `hitL1("{route}:{ip}")` (:172, :181) — 프로세스 메모리, 영속 저장 아님.
3. L2 `guardRateLimit` → `rl:{route}:{ip}` Redis (:196~199). 사용 라우트: finance, crypto, dividend, market-index, price-history, profit, logo, realestate, share(get/post), feedback, push-subscribe, push-test.
4. `/api/sync/route.ts:78` `checkRateLimit(getClientIp)` → `rl:legacy:{ip}` (cache-storage.ts:1015).
5. `reserveGeminiCalls`(:280~) `rl:gemini:{ip}:{day}`, `rl:gemini-{pool}:{ip}:{day}`. 호출처: parse-screenshot, xray-classify.

**권고(작게 하는 쪽)**: ③④ Redis의 IP 키를 전부 삭제. 방어는 ② L1(휘발성 메모리, 재시작 시 소멸 — 영속 저장 아님으로 판단, 대표 확인 가능) + Vercel WAF 속도 제한 규칙(IP 처리는 플랫폼 소관, 코드·저장 없음; 대시보드 설정은 대표 몫으로 요청 필요)으로 대체. Gemini 1인 30회는 **기기 기준(localStorage 일일 카운터)** 으로 이동하되 이는 클라이언트 통제라 우회 가능(저장소 비우기)하다. 서버 전역 1500·풀(pool.dailyLimit)은 유지하며, 이것이 최후 방어선이다.
**약해지는 점**: ① 한 공격자가 전역 1500을 하루에 소진해 OCR·X-Ray가 전체 정지(가용성 공격) ② `heavy`(IP별 LIGHT_USER_CALLS 초과) 구분이 서버에서 불가하므로 HEAVY_POOL_RATIO 로직 제거 ③ 시세 API 폭주는 L1(인스턴스별)·WAF만 의존. **보완**: Gemini 라우트에 한해 L1 분당 한도를 낮추고(예 5/분), WAF 규칙으로 /api/parse-screenshot·xray-classify 한도 설정. 대안(비권고): 일회성 회전 솔트로 IP를 HMAC해 저장 — IP 비저장 원칙과 충돌 소지가 있어 제외.
**테스트 영향**: api-guard·gemini 한도 기존 테스트 개정(IP별 시나리오 삭제), 클라이언트 카운터 단위 테스트 신규(일 경계 KST).

## ③ 푸시 30일·HKDF
- TTL: `cache-storage.ts:309 PUSH_SUB_TTL_SEC` 90→30일(로컬 JSON 구현 :807과 Upstash :1191 모두 상수 공유), client.ts:109 주석 수정. 갱신 시 TTL 연장은 유지.
- 키 분리: `push/crypto.ts`에서 마스터 `PUSH_STORE_KEY`(환경 변수 변경 없음)로 HKDF-SHA256(info="secretasset/push/subid/v2" → HMAC 키, "…/aes/v2" → AES 키). Node `hkdfSync` 사용.
- **기존 데이터 이행**: subId(HMAC)가 바뀌면 `sub:{id}` 키와 집합 멤버가 달라지고, blob도 구 키로 암호화돼 있어 새 키로는 못 읽는다. 해결: ① 신규 blob은 `"2:"` 접두(구 blob은 접두 없음) → `openSecret`가 접두에 따라 v2 키 또는 구(마스터 직접) 키로 복호화(이중 읽기) ② 구독 갱신 요청(subscribe) 시 신 id로 저장하고 구 id 레코드·집합 멤버 삭제 ③ cron 발송 중 구 형식 레코드는 읽은 즉시 신 id·신 키·30일 TTL로 재기록 후 구 레코드 삭제(lazy rewrap). 구 레코드 이행 완료 후 구 키 경로는 다음 릴리스에서 제거(TTL 30일 경과 후). 복호화 불가 레코드는 기존 고아 정리(cron-run.ts:92)에 맡긴다. 클라이언트가 앱 실행 시 자동 재등록하는지는 push-host.tsx·client.ts로 구현 시 확인(자동이면 재등록 경로가 이행을 가속).
- 롤백: 구 코드는 신 레코드를 못 읽어 알림 구독이 사라진다 → 사용자는 재구독 필요(자산 데이터 손실 없음, 알림 일시 중단). 롤백 필요성이 크면 이행 첫 릴리스에서 rewrap 비활성 플래그를 둔다(구현량 +소).
- 테스트: crypto.test(HKDF 키 분리·서로 다른 키·구 blob 호환), storage.test(TTL 30일), cron 이행 테스트.

## ④ 스키마·키·롤백
- **localStorage 스키마·STORAGE_KEYS 변경 0**, 마이그레이션 코드 불필요. 서버로 나가는 값 증가 없음(공유 토큰은 여전히 암호문, URL 키·PIN은 서버 미전송 — 링크 해시 `#` 이후라 서버에 전달 안 됨).
- 서버 저장 변경: 공유 토큰 prefix(v73A), 푸시 sub id·blob 형식(②·③), Redis `rl:*:{ip}` 키 폐기(자연 만료).
- 기록 손실 가능성: 공유 링크는 30일 한시 데이터라 원본(로컬 자산)과 무관. 롤백 시 v73A 링크가 구버전에서 열리지 않음(재공유로 해결). 백업·스냅샷·성적표 계산 무영향.
- `risk:high` 사유: 공유 토큰 형식 + 서버 저장 형식 + 보안 정책 문구 영향. 대표 승인 대상. 데이터·보안 문구(PRINCIPLES 보안 설명, 가이드 페이지의 "서버 IP 저장" 언급)가 있으면 함께 정정해야 한다.
