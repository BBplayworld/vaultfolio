### ③ 공유 토큰 (신규 발견, 가장 심각)
`cryptWithKey`(asset-storage.ts:612)는 LZString 압축문자를 `(idx + key문자코드) mod 64`로 이동시키는 **비제이 시프트 암호(Vigenère류)**다. 키는 PIN 4자리+`Math.random` 12자(비암호학적 난수) 16자 반복. 평문은 항상 `OK|` 접두에 알려진 LZ 구조, 64글자 알파벳 기준 키 문자당 6비트 → 알려진 평문·빈도 분석으로 PIN·localKey 없이 복원 가능성이 높다. 키가 서버에 없다는 점은 맞지만 **암호 강도가 "서버 유출 시 복호 불가"를 보증하지 못한다.** 보유 종목·수량·단가·닉네임이 30일간 서버에 있다 → 대표 원칙·PRINCIPLES 서버 전송 원칙 직접 충돌. 재설계: AES-GCM(WebCrypto)·32바이트 CSPRNG 키를 `#fragment`에만 두고, PIN은 PBKDF2로 키에 결합(PIN 4자리 단독은 오프라인 대입 가능하므로 CSPRNG 키 필수). 토큰 버전 `v73`으로 신설, 구 `v72Z`는 읽기만 지원하고 서버 저장 시 거부, 기존 `share:*`는 TTL 만료(30일)를 기다리거나 일괄 삭제. 링크 형식 변경이라 구 링크는 깨짐 → 대표 확인.

### ① 웹 푸시 — 대안 검토
| 안 | 가능? | 판단 |
|---|---|---|
| endpoint를 사용자 기기 키로 암호화, 발송 시에만 복호 | **불가** | cron 발송 시 기기가 오프라인. 발송자가 복호 능력을 가져야 하므로 서버 유출 = 복호 능력 유출. 시간잠금(tlock)도 유출자가 시각 도달 후 복호 가능해 이득 없음 |
| FCM topic / 공통 구독으로 서버가 endpoint 미보관 | **Web Push 표준에서 불가** | RFC 8030 `Topic` 헤더는 메시지 대체용일 뿐 구독 그룹이 아님. 푸시 서비스는 기기별 endpoint로만 전달. FCM topic은 Firebase SDK 토큰·Admin API 필요 → Google이 구독 목록 보관, 우리 서버는 여전히 토큰 보유·신규 의존 |
| endpoint를 "식별 불가 정보"로 판정 | **단정 불가(부분 가능)** | 근거: endpoint는 브라우저가 만든 임의 URL, 계정·이름·IP·금고와 우리 서버 안에서 연결 없음. 반론: Google·Apple은 발급 사업자라 자기 시스템에서 기기·계정과 연결 가능한 지속적 기기 식별자이고, 개인정보 판단은 "다른 정보와 쉽게 결합" 기준. 우리 쪽 결합 수단이 없어 개인정보에 해당하지 않을 가능성이 높지만 **"유출돼도 복호 불가" 원칙은 충족 못함**(발송 가능 토큰이 유출됨) |
| 보관 최소화 | 가능(부분 개선) | TTL 90일→30일(갱신 연장 유지), 앱 미실행 30일이면 자동 소멸. 발송 로그·UA·IP 미저장 이미 충족. 유출 피해창만 축소 |
| 서버 비보관(로컬 알림) | 부분 가능 | SW Periodic Background Sync로 공개 시세를 받아 기기에서 알림. Chromium 설치형 PWA만, 간격·실행 보장 없음, iOS 미지원 → 알림 품질 저하 |
**결론**: 서버 발송형 푸시는 원칙을 엄격 충족하지 못한다(수학적 한계). 선택지는 A) 원칙 문구를 "계정·IP·자산과 결합 불가한 가명 발송 토큰은 허용"으로 정의(대표 결정), B) 푸시를 로컬 방식으로 축소(기능 후퇴). 권고는 A + 보관 30일 + 키 분리(HKDF) + 처리방침에 "발송 토큰" 명시.

### ② 호출 한도 IP 대안
| 안 | 판단 |
|---|---|
| IP 해시(일일 회전 salt) | IPv4 공간이 42억이라 salt(env) 유출 시 전수 대입으로 복원 가능 → 원칙 엄격 충족 못함. 단 일반 유출(DB만)에는 유효 |
| **IP 미저장**(권고) | 분당 한도는 이미 인스턴스 메모리 L1(`hitL1`)과 Vercel 방화벽(WAF) 속도 제한이 있음 → Redis `rl:*:{IP}` 제거 가능. Gemini 일일 IP 한도는 풀 전체 일일 예산(`rl:gemini-*:{일자}`)만 유지, 남용 대응은 WAF로 |
| 최소 대안 | push 1시간·Gemini 일 단위 윈도우를 60초로 줄이고 해시 적용 |

### 동기화 메타데이터
assetId(클라 난수)·pubKey·version·updatedAt·암호문 크기·90일 TTL이 전부. 계정·IP·기기 수·UA는 저장하지 않음(인증 헤더 `x-sync-auth`는 경로가 아닌 헤더). 식별 가능성은 낮다. 잔여 위험: ① 금고암호가 약하면 서버 유출 후 오프라인 대입(PBKDF2 20만회, salt는 assetId 파생 결정값) ② 암호문 크기·갱신 시각으로 자산 규모·활동 추정. 암호 강도 하한 표시·크기 패딩으로 완화 가능(선택).

## 3. 결론 — "개인정보 처리방침 불필요 구조"를 위한 변경 목록
| 순위 | 변경 | 규모 | risk |
|---|---|---|---|
| 1 | 공유 토큰 암호를 AES-GCM+CSPRNG 키로 교체(v73), 구 토큰 서버 저장 중단·기존 삭제 | 중~대(공유 링크 형식·마이그레이션·테스트) | **high**(공유 토큰·서버 전송) |

| 3 | 푸시 원칙 정의 결정(A 가명 토큰 허용 / B 로컬 알림), A면 TTL 30일·HKDF 키 분리 | 소(A) / 대(B) | A medium, B high(UX) |
| 4 | 동기화 금고암호 강도 하한·암호문 크기 패딩 검토 | 소 | low |
| 5 | GA 설정 점검(`anonymize_ip`는 GA4 기본, `_ga` 쿠키 동의 정책), 피드백 연락처 수집 문구 | 소 | low |

**충돌 지점**: 서버 발송 푸시는 원칙을 엄격히 충족할 수 없음(대안 A/B), 플랫폼 IP 로그·GA는 앱이 못 없앰. 위 1~2를 반영하면 서버 저장 항목은 "복호 불가 암호문 + 공개 캐시 + 가명 발송 토큰"만 남는다. 처리방침 불필요 여부는 푸시·GA·플랫폼 로그 때문에 법무 확인이 있어야 단정할 수 있다.
