# 순자산 변화 알림(PWA Push) 타당성 검토 — 2026-11-12 (구현 금지, main 7807366 기준)

## 1. 현재 코드 현황
- **Service Worker는 있으나 Push는 없음**: `public/sw.js`는 install/activate/fetch(Network-First 오프라인 폴백)만. `push`·`notificationclick` 핸들러 없음. 등록은 `src/app/layout.tsx:181-198`.
- `Notification`/`PushManager`/VAPID/`web-push` 의존성 0건, 구독 저장 API 없음(`src/app/api/`는 finance·sync·share·feedback 등뿐), 크론/스케줄러 없음(`vercel.json`에 crons 없음). 종목 목표가 알림도 미구현. 2026-08 알림 결정은 문서 상태.
- 저장소: 자산은 브라우저 localStorage(평문, `secretasset_*`). 앱 잠금(`src/lib/pwa/app-lock.ts`)은 PIN 해시로 화면만 막는 UI 잠금이며 데이터 암호화 키가 아님. E2EE는 **동기화 전송·서버 보관**용(`/api/sync`) — 로컬 데이터는 SW가 키 없이 읽을 수 있는 구조(단 SW는 localStorage 접근 불가 → 아래 b).
- 서버: Upstash Redis 캐시(시세 캐시·락), KIS 키는 시세 라우트에서 사용.

## 2. 방식 비교
| 방식 | 내용 | 평가 |
|---|---|---|
| (a) 2026-08 결정 | 클라이언트가 종목별 보유수량으로 목표가 환산 → 서버에 "종목 X가 Y원 도달" 조건만 등록 | 종목 단위만 가능. 순자산은 여러 자산·환율·현금·부채의 **합**이라 단일 종목 가격 조건으로 환산 불가. 근사(대표 종목 몇 개 가격 조건으로 "순자산 ±N%" 흉내)는 가능하나 부정확·다수 구독 필요, 서버가 "이 기기가 어떤 종목을 관심 있는지"를 알게 됨(수량은 모름). 결정 문서가 총 순자산 합산 알림을 이미 보류한 이유 |
| (b) 깨우기 Push + SW 로컬 계산 | 서버는 자산 모르고 시장 이벤트 시 모든 구독자에게 동일한 "깨우기" 전송, SW가 로컬 자산으로 계산해 문구 생성 | **서버 무지식 원칙 유지 가능**, 단 아래 제약(userVisibleOnly, 미러 필요) 때문에 "조건 미달 시 조용히 무시"가 불가 |
| (c) Periodic Background Sync | SW가 주기 깨어나 계산 | 크롬 안드로이드(설치 PWA)만, 최소 주기·실행은 브라우저가 결정(사용자 참여도 기반), iOS·Safari·Firefox 미지원 → 핵심 사용자(iOS 포함)에 불균일. 보조 수단으로도 비추 |
| (d) 앱 열 때 인앱 표시 | 이미 홈/결산에서 변동 표시 가능 | 비용·위험 최소. "푸시"는 아님 |

## 3. 플랫폼 제약(정확히)
- **userVisibleOnly**: 웹 푸시 구독은 사실상 `userVisibleOnly:true` 필수. push 이벤트마다 알림을 표시하지 않으면 브라우저가 "백그라운드에서 갱신됨" 같은 기본 알림을 띄우거나(Chrome) 구독 불이익/해지(Safari는 몇 번 누락 시 구독 취소). 따라서 (b)에서 **"변동 작으면 숨김"이 불가**. 서버가 깨우기를 보낸 모든 기기에 알림이 하나는 뜬다 → 서버가 "큰 변동 날만" 보내는 시장 단위 필터(예: 지수 ±2%)로 빈도를 제한하고, 내용은 SW가 계산("내 순자산이 변했어요"/방향)하는 설계만 가능. 개인별 임계치 미달 사용자에게도 중립 문구를 보여줘야 함.
- **iOS 16.4+**: 홈 화면에 설치된 PWA에서만, 사용자 제스처 후 권한 요청. 미설치 Safari 탭은 불가. 알림 신뢰도는 iOS에서 낮은 편(저전력, 무반응 누적 시 구독 정리).
- **SW 실행 제한**: push 이벤트 처리는 `event.waitUntil` 내 짧은 시간(브라우저별 대략 수십 초, 길면 종료). 순자산 계산(자산 읽기+시세 조회+환율)은 시간 내 가능해야 하며 실패 시에도 알림은 표시해야 함(중립 폴백 문구).
- **자산 접근**: SW는 localStorage 접근 불가 → **IndexedDB 미러 필요**(앱이 열릴 때마다 보유 종목·수량·현금·부채의 요약을 IDB에 복제). 이는 로컬 저장 스키마·저장 키 추가이며 동기화·삭제·백업·"모든 삭제"·체험 모드·앱 잠금·구버전 혼재 경로 전부에 일관성 요구(삭제 누락 시 잔존 위험, CHECKLIST 데이터 안전 대상). 잠금 상태: 앱 잠금은 UI 게이트라 기술적으로 SW가 읽을 수 있음 — **그러나 PIN을 건 사용자 의도(타인이 못 보게)와 충돌**하므로 잠금 사용자에겐 알림 문구에 수치 0이 안전.
- **SW 시세 조회**: SW에서 `/api/finance`로 fetch 가능(자기 출처). 단 기기 N대가 동시에 깨어나 조회 → 시장 이벤트 시점에 **thundering herd**가 KIS 한도·서킷에 부담. 현재 Redis 캐시·락이 완충하나 구독자 증가 시 스파이크 검증 필요. 대안: 깨우기 payload에 서버가 이미 가진 공개 시세(지수·환율·주요 종목 등락률)를 실어 SW가 추가 fetch 없이 계산(암호화 불필요, 공개 정보). 보유 종목 전부 커버는 불가 → 근사.
- **문구·잠금화면 보안**: 알림은 잠금화면에 노출 → 금액 표기는 원칙("안전한 자산 관리")과 충돌. 안전선: **금액 없이 방향/%도 최소화**("순자산 변화가 있어요, 앱에서 확인"). %는 총자산 규모는 안 드러내나 개인 포트폴리오 성과가 노출되므로 대표 판단 사안. 마케팅 문구 금액 금지 원칙과 별개로 알림 본문은 금액 금지 권고.
- **서버가 새로 아는 것**: Push 구독(endpoint·키)은 기기 식별자. 자산 값은 안 보내지만 "알림을 켠 기기 목록"이 서버에 생김. 자산 역산 불가(시장 이벤트 단일 payload를 전원 동일하게 broadcast → 구독자별 차이 없음).

## 4. 권고안 (1개): 단계적 — (d) 먼저, 그 다음 (b) 최소형
**권고: 개인 순자산 알림을 지금 푸시로 만들지 말고, 1단계로 (d)를 강화하고, 대표가 원하면 2단계로 (b)의 '시장 단위 깨우기 + 중립 문구'만 시범.**
1. (최소, risk:low~medium) **앱 열 때 인앱 순자산 변동 표시**: 마지막 확인 시점 대비 변화(홈 결산 팁 계열 재사용). 서버·스키마 변경 0(기존 스냅샷 활용 가능 여부는 구현 시 확인). 규모 소(1~2일).
2. (시범, risk:high) Push 인프라 + 시장 깨우기: SW push/notificationclick 핸들러, `/api/push/subscribe`(구독 저장 Redis), VAPID 키(환경변수), 스케줄러(Vercel Cron 1~2회/일, 장 마감 후 또는 지수 ±N% 시), 인앱 안내 후 권한 요청 UI, IDB 미러(보유 요약) 또는 미러 없이 **중립 문구만**("시장이 크게 움직였어요, 내 자산 확인하기" — 개인 계산 없음). **미러 없는 중립형이 서버·로컬 스키마 변경을 최소화하는 최저 위험 버전**이나 "내 순자산 변화"라는 요청 가치는 약함(도미노식 개인 알림이 아니라 시장 알림, 2026-08 '시장가 등락 알림 아님' 결정과 충돌).
- 규모: 2단계 중립형 중(3~5일, 서버 API 1·SW·설정 UI·테스트), 미러+SW 계산형 대(1.5~2주, 마이그레이션·삭제 경로·iOS 실기기 검증).
- **위험 등급**: 1단계 low~medium(위임 머지 가능). 2단계는 **risk:high**(새 서버 저장소=구독 DB·새 API·VAPID 비밀값, 미러형은 로컬 스키마·저장 키 추가=자동 high). 권고하는 어느 쪽이든 2단계는 대표 승인 대상.
- **왜 (b) 전면을 권고하지 않나**: userVisibleOnly 때문에 개인 임계 미달 시 숨길 수 없고, 모든 시장 이벤트가 사용자 전원에게 알림이 되어 "경과일 알림 금지·사용자 지정 조건 알림만"(LEARNINGS 2026-08) 원칙과 충돌. 즉 "내 순자산이 일정 %↑일 때만" 같은 **사용자 지정 조건 알림은 서버 무지식 설계로 구현할 수 없다**(조건 평가에 자산이 필요).

## 5. 대표 결정이 필요한 쟁점
1. **원칙/결정 충돌**: 순자산 합산 알림은 2026-08 보류 결정(서버가 자산을 알아야 함)과 ‘시장가 등락 알림 아님’ 결정을 번복하는 것인가? (b)는 서버가 자산을 모르는 대안이므로 보류 사유는 해소되나, 개인 조건 알림이 아닌 broadcast 구조라는 점을 수용하는지.
2. 사용자 지정 조건 없이 시장 이벤트마다 전원에게 알림이 가는 것을 허용하는가(LEARNINGS 원칙과 충돌 가능).
3. 잠금화면 문구 수위: 금액 금지(권고) / 방향만 / %까지.
4. 로컬 자산 요약을 IndexedDB에 미러하는 것 허용 여부(저장 키·스키마 추가, 앱 잠금 사용자의 기대와 충돌, 삭제·백업 경로 추가).
5. 서버가 '알림 켠 기기 구독 목록'을 보관하는 것 허용 여부(PRINCIPLES 서버 저장 최소 원칙과의 정합).
6. iOS는 홈 화면 설치 사용자만 대상, 알림 없이도 핵심 완결(PRINCIPLES 18행) — 효과 측정 지표(켠 기기 비율·알림 후 앱 진입)를 먼저 정할지.
7. KIS 요청 한도: 구독자 증가 시 동시 시세 조회 부담 — 서버 공개 시세 payload 방식(근사) 수용 여부.

## 핵심 5줄(대표용)
1. 지금 코드에는 SW(오프라인 캐시)만 있고 Push·구독 저장·VAPID·스케줄러는 전부 없음.
2. 가능은 하나 "내 순자산이 N% 바뀌면"이라는 개인 조건 알림은 서버가 자산을 모르는 설계로는 불가(userVisibleOnly로 조건 미달 시 알림을 숨길 수 없음). 서버 무지식 방식은 시장 단위 broadcast + 기기 내 계산뿐.
3. 그 방식은 IndexedDB 미러(로컬 저장 추가)·구독 서버 저장·잠금화면 노출 문제가 생겨 risk:high, 문구는 금액 없이 중립으로만 권고.
4. 권고: 먼저 앱 열 때 인앱 순자산 변동 표시(low, 1~2일)로 가치 검증 → 이후 Push는 대표가 원칙 결정(쟁점 1~3) 후 시범.
5. 결정 필요: 2026-08 보류 번복 여부, 전원 broadcast 허용, 잠금화면 문구 수위, IDB 미러·구독 서버 저장 허용.
