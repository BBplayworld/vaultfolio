## 1. /api/sync 방어 공백 (type:bug 보안·안정성, 제안 p2)
- 근거: `src/app/api/sync/route.ts:21-27` 자체 `getClientIp`가 `x-forwarded-for` **맨 왼쪽** 값을 신뢰(클라이언트가 임의 지정 가능) → PUT rate limit(`:72`, `rl:legacy:{ip}`) 헤더만 바꿔 우회. 다른 라우트는 `src/server/api-guard.ts:21-33`(x-vercel-forwarded-for 우선)을 쓴다. `GET`(`:49-65`)은 rate limit·L1 버킷이 전혀 없고, 서명 검증 **전에** `getAssetEnvelope`(Redis 조회)를 수행 → 임의 assetId로 무제한 Redis 읽기 가능(1건당 4MB급 암호문 로드 가능). `api-guard.ts:13` 주석에 "sync는 무변경 원칙"으로 의도적 제외됐으나 그 이후 다른 라우트만 강화돼 격차 발생.
- 사용자 영향: 정상 사용자 체감 0. 남용 시 Upstash 한도 소진 → 동기화 전체 장애(약 4기기 사용 중이나 장애 시 영향은 전 사용자 시세 캐시 포함).
- 수정 비용: S. `getClientIp`를 api-guard 것으로 교체, GET에 `guardRequest`(L1)와 assetId 형식 검증(길이·문자) 추가. 프로토콜·저장 포맷 무변경, 서버 전송 값 불변.
- 위험: 동기화 라우트 수정이라 위임 머지 조건 ④에 걸려 **대표 승인(medium)** 가능성. 4.47(#84)과 같은 파일군이 아니므로 충돌 없음. 부수: `ticker-search/route.ts:89`는 L1만 있고 L2·업스트림 예산 없음(CDN 캐시 의존) — 같이 점검.

## 2. 로컬 저장 실패 무시 (type:bug 안정성, 제안 p2)
- 근거: `saveAssetData`(`src/lib/asset/asset-storage.ts:118-130`)는 quota 초과 등 예외 시 `false`만 반환하는데, `src/contexts/asset-data-context.tsx:562, 623, 799, 888, 942, 1328`와 `src/hooks/use-nickname.ts:22`는 반환값을 버린다(1176만 `success` 확인). 코인 시세 갱신(`:623`)은 `setAssetData(next)` 후 저장하므로 저장 실패 시 화면은 갱신, 새로고침하면 이전 값으로 복귀. `QuotaExceededError` 처리 코드는 앱 전체에 0건.
- 사용자 영향: 저장공간 부족(iOS 사파리 인앱·스냅샷 누적 큰 사용자)에서 거래·편집이 조용히 유실. 발생 빈도는 낮으나 "기록 손실"이라 신뢰 타격 큼. 재현은 quota 모킹 테스트로 가능.
- 수정 비용: M. 공용 헬퍼(저장 실패 시 1회 토스트 "저장하지 못했어요. 백업을 내려받아 주세요" 류 + GA 무값 이벤트) 하나로 6곳 호출 통일. 스키마 무변경. 문구는 PRINCIPLES 데이터 문구 영향 확인 필요(보안·데이터 문구 변경이면 대표 승인).
- 선행 확인: qa가 실제 사용자 상황(스냅샷 크기)을 추정할 수 없으므로 localStorage 사용량 계측은 하지 않고 코드 경로만 처리.
