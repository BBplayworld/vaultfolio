## 5. 테스트 계획 (vitest는 node 환경, jsdom 없음 → 정적 마크업과 grep으로 검사)
1. `renderToStaticMarkup(<AppGuideContent/>)`와 `<WelcomeGuide/>`(기존 mock 재사용)의 카드 제목·본문이 `SECURITY_COPY`와 같은지 확인한다(두 화면 문구 일치).
2. 문구 grep 테스트 1건: 대상은 정정한 7개 파일과 `security-copy.ts`. "절대 벗어나지", "원천 불가", "문제없습니다", "(blob)", "(pubKey)", "E2EE 암호학적"이 0건이어야 한다.
   - **완료 기준 1은 범위를 좁혀야 한다.** `src/` 전체에서 "blob"·"pubKey"를 grep하면 코드 식별자가 걸린다(`sync-client.ts:58`, `share-menu.tsx:126`, `api/sync/route.ts` 등). 문구 grep은 UI 문자열과 위 파일로 한정한다.
3. 4개 업로드 박스 파일이 같은 상수를 import하는지 grep으로 확인한다.
4. 새 문구에 "서버"가 주어로 오는 문장이 없는지 상수 대상으로 정규식 검사한다(완료 기준 4).

## 6. preview에서 확인 가능한 범위·한계
- 확인 가능:
  - 웰컴 → 자세히 보기(`/?demo=empty`)
  - 앱가이드(`/?demo=1` → 더보기 → 앱가이드)
  - 업로드 박스(`/?demo=1` → 상세 → 주식 추가 → 스크린샷 탭. 업로드 전 박스만 보면 되므로 Gemini를 호출하지 않는다)

  - 대안: `cs.enabled=true`로 mock한 정적 마크업 테스트로 문구를 검증한다. 줄바꿈은 같은 클래스(`break-keep`)인지만 확인하고, 이 한계를 dev-notes에 기록한다.
