## 2. 계좌 연결 — 왜 대표 선택인가
대표 원 지적의 핵심은 "매수·매도가 현금·대출과 **이어진다**"이다. A는 화면 서술을 바로잡을 뿐 데이터로 잇지 않는다. 사업 근거(외부 거래 입력 기기 1~3대)만으로 팀이 빼면 같은 지적이 다른 형태로 재발할 수 있다(COO 5항). 그래서 팀이 확정하지 않는다.

### B'(cto 제안): 거래 저장 시 기존 입출금·상환 기록을 함께 만든다 — 스키마 0
- 주식·코인 매수·매도 폼(반영 저장일 때만)에 선택 행 `현금 계좌에서도 반영`(기본 꺼짐, 같은 통화 현금 계좌만). 켜면 같은 저장 1회(`saveData` 1회, C37)에 기존 `cashTransactions` 출금(매수)·입금(매도) 1건을 reflected로 추가. 새 필드·저장 키 0.
- 결산은 출금↔매수를 이미 ±3일 짝짓기한다. **매도↔입금 짝짓기가 없어** 매도 대금 입금이 '순유입 +'로 잡히므로 `matchRecordedTransfers`에 입금↔매도 짝 추가가 필수(결산 코드 변경 → 창 밖 머지, C21 픽스처 기대값 선기재).
- 하지 않음: 대출 연결(매도 대금 상환·대출로 매수), 부동산·실물, 외화 환산 연결, 과거 거래 소급, 거래 삭제 시 짝 기록 자동 되돌림(링크 필드가 없으므로 — 삭제 토스트에 '입출금 기록은 따로 남아요' 1줄).
- 가드: 4.52 S3 경고(맞춘 뒤 즉시 반영) 그대로 적용, 잔액 음수 허용 여부는 기존 입출금 기록 규칙 따름.

### 5-1. 핵심 설계 판정 — 새 필드 대신 '짝 기록 id로 연결'(저장 형식 변경 0)
- 근거(코드 origin/issue-4.55 9a582ac): `asset-storage.ts` `saveAssetData`·`getAssetData`가 `assetDataSchemaLoose.parse`(zod 기본 = 모르는 키 제거)로 읽고 쓴다. 거래에 새 필드(`linkedAccount` 등)를 넣으면 **구버전 기기가 읽고 저장하는 순간 필드가 지워지고**, push 뒤 신 기기는 같은 id 항목을 원격 우선(`mergeById`는 '없는 항목'만 되살림)으로 받아 **모든 기기에서 연결이 사라진다**. 4.55 D1(클라우드 사본 탈락)과 같은 패턴인데, 항목 안 필드라 D1식 재-push로도 막을 수 없다. 별도 저장 키(4.55 실물 방식)는 동기화 payload·병합·복원 코드를 새로 만들어야 해 더 크다.
- 결정: 연결은 **짝 기록의 id 규칙**으로 저장한다. 거래 저장 시 만드는 입출금·대출 기록 id = `ctx_link_<거래 id>`(현금) / `ltx_link_<거래 id>`(대출). 연결 계좌는 그 기록의 `cashId`·`loanId`가 말해 준다. 타입·zod 스키마·저장 키·동기화 형식 diff 0 → 마이그레이션 코드 불필요. 구버전 기기는 id를 보존하므로 연결이 지워질 수 없다(구조적으로 D1 차단).
- 그래도 risk:high: 세 컬렉션(거래·보유·현금/대출 잔액)을 한 번에 바꾸고 **삭제 시 잔액을 되돌리는 새 쓰기 경로**, 결산 짝 규칙 변경, 홈(첫 화면). 자동 high 사유(스키마)는 아니나 cto 판정으로 high. 대표 승인.

### 5-5 qa 교차 확인 반영 — B항 데이터 안전 결정 (cto, 2026-11-09, qa 198ea31 기준)
spec의 `[cto 5-5 결정 반영 예정]` 자리(3-L 7, F19·F26, 완료 기준 10·13·15)의 정본은 이 절이다(위 '5-5. 다음 착수 지시'와 별개). 코드 근거 origin/issue-4.55: 현금·대출 기록 수정 함수·UI 없음(`asset-data-context.tsx`에 `updateCash/LoanTransaction` 0), 삭제 역가감 `cash-tx-view.tsx:84`·`loan-tx-view.tsx:83` `Math.max(0,…)`, `deleteCash/deleteLoan`은 그 계좌 기록 함께 삭제, 거래일 입력 `max=오늘`·과거 허용(`trade-input.tsx:601`), 결산은 저장값 없이 매번 계산.

**① 되돌림 방식 = 짝 기록 금액 기준 역가감, 하한 0 유지.** '잔액 = 기록 합' 재계산은 **기각** — 이 앱의 잔액은 기록 합이 아니다(초기 잔액·맞추기·미반영 기록·3년 정리). 재계산하면 사용자가 맞춘 잔액을 덮어써 그것이 곧 데이터 손실이다.
- 감소 방향(매도 입금 되돌림·대출 증가 되돌림)만 하한 0. 음수 허용은 기각(출금 가드로 음수 잔액이 없는 앱, 표시·결산 미검증 경로). 차단도 기각(잘못 입력한 거래를 못 지우게 됨). 하한에 걸려도 다른 기록은 하나도 지우지 않는다 — 남은 출금·상환 기록이 사실을 말하고, 잔액은 맞추기로 고칠 수 있다.
- 하한에 걸리면 다이얼로그 1줄은 **실제 줄어드는 금액**(= 현재 잔액)을 보이고 끝에 '잔액이 부족해 0원이 돼요' 류 짧은 꼬리 1개(문구는 ui-designer, 금지어 규칙 동일). 표시 = 결과(같은 `removeLink`).
- 기대값(픽스처 고정):
  - 현금 100 → 연결 매도 입금 500(600) → 출금 450(150) → 거래 삭제: 잔액 **0**, 다이얼로그 −150 + 꼬리, 출금 450 기록 유지, 기록 수 −1(짝만).
  - 대출 300 → 연결 매도 상환 300(0, 완납 목록) → 거래 삭제(F19): 대출 **300**, 활성 목록 복귀·`완납` 배지 없음, 상환 기록 −1. 증가 방향이라 하한 무관.
  - 대출 300 → 연결 매수 대출 증가 200(500) → 상환 기록 400(100) → 거래 삭제: 대출 **0**(완납), 다이얼로그 −100 + 꼬리.
  - 연결 매수 출금 되돌림(잔액 증가)은 항상 전액.
- **불변식(qa B-3 대체)**: '잔액 = 기록 합' 대신 **조작별 변화량 불변식** — 연결 저장 Δ잔액 = ±금액·기록 +1, 되돌림 Δ = ∓금액(하한이면 −현재 잔액)·기록 −1, 짝만 삭제 = 기존 규칙, 구버전 거래만 삭제·종목/코인 삭제·3년 정리 = Δ잔액 0·짝 기록 유지(이중 계상 없음: 금액이 잔액에 1회, 기록 1건). 완료 기준 10·13·15의 '잔액 = 기록 합'은 이것으로 바꾼다.

**② 짝 기록 수정 뒤 삭제 = 짝 기록의 현재 값으로 되돌린다.** 금액·통화는 짝 기록 자신, 계좌는 그 기록의 `cashId`/`loanId`, 날짜는 무관. 거래 금액은 쓰지 않는다. 현재 수정 UI가 없어 실제로는 거래 금액과 같지만, 백업 편집·다른 버전 유입에 대비한 단일 규칙. 짝 기록이 `reflected:false`면 기록만 지우고 잔액은 그대로(기존 미반영 삭제 규칙).

**③ 짝 기록·계좌가 먼저 없어졌을 때**: 짝 기록 없음(따로 삭제·계좌 삭제로 함께 삭제·3년 정리) → 보유 롤백만, 다이얼로그 1줄·토스트 꼬리 없음. 짝 기록은 있는데 계좌가 없음(동기화 경합 고아) → 거래만 지우고 **짝 기록은 건드리지 않는다**(손실 0, 1줄 없음). F17 기대값 그대로.

**④ 과거 날짜(C8) = 연결은 거래일이 오늘(KST)과 같은 달일 때만.** 거래일을 지난달 이전으로 고르면 `연결 계좌` 행을 숨기고 선택을 `연결 안 함`으로 되돌린다. 저장 함수도 같은 조건을 다시 검사해 `false`. 결산 창(1~10일)에 지난달 날짜도 불가(예외 없음, 단순). 근거: 지난달 말 스냅샷은 이미 정해졌는데 잔액은 지금 움직이고 기록은 지난달에 들어가 지난 결산 서술을 바꾼다.
