## 1. 문제
- 홈 '지난 접속 이후' 원인이 앱 안에서 옮긴 돈을 두 원인으로 보여준다(qa 확정): `주식 매수 +100만 / 현금 정리 −100만`, `주식 매도 −500만 / 대출 상환 +500만`. 합은 맞지만 서술이 틀리고, '상환·매수'를 원인으로 쓰는 LEARNINGS 위반 형태다. 시세가 움직인 날(Δ≥1만)에만 드러난다.
- 매수·매도는 현금 계좌와 이어지지 않는다. 거래를 기록해도 현금은 따로 고쳐야 하고, 앱이 그것을 알려주지 않는다(대표 지적 11-09).

## 2. 목표 행동
- 매수·매도·상환을 한 뒤 홈을 열면 원인에 시세·환율·입출금 등 **순자산을 실제로 바꾼 것만** 보고, 캡션 1줄로 '옮긴 돈은 뺐다'를 읽는다.
- `[선택:②]` 주식·코인 매수·매도를 즉시 반영으로 저장할 때 `현금 계좌에서도 반영`을 켜서, 현금 잔액·입출금 기록·결산이 한 번에 맞는다.

## 3. 범위

### 3-A. 홈 헤더 내부 이동 상쇄 (①②③ 공통)
1. **대상 다리**: 매매 다리 `buy:*`·`sell:*`(stock·crypto·realEstate, 4.55 `physical` 포함) / 자금 다리 `cash`(잔차)·`debt`·`deposit`(보증금) / 기록 다리 `income`.
2. **1단계 — 기록 짝(정본: 결산과 같은 함수)**: `matchRecordedTransfers`를 확장해 짝 내역을 돌려준다(새 규칙 금지, 같은 ±3일·날짜 근접·id순·금액 한도).
   - 기존: 반영 출금 ↔ 반영 매수(주식·코인)·대출 상환. 4.55 합류분: 후보에 **실물 신규 등록(매입)** 추가(4.55 저장 경로·날짜 필드 기준, tech-review 3df41ae).
   - `[선택:②]` 추가(B' 필수 조건, A에도 같이 적용): **반영 입금 ↔ 반영 매도(주식·코인)**. 정기 입금(`recurring === true`, 월급)은 후보에서 뺀다. ①이면 이 줄과 결산 래퍼 변경을 빼고 `in`은 항상 0(결산 diff 0 → 위임 머지 조건 유지).
   - 반환: 내역 함수 `matchRecordedTransferDetail()` → `{ out: { stock, crypto, physical, loan }, in: { stock, crypto } }`(KRW). 기존 `matchRecordedTransfers()`는 **출금 짝 합 − 입금 짝 합**(음수 가능)을 돌려주는 얇은 래퍼로 유지. **결산 변경 2곳**: 래퍼 + `settlement.ts:224` 가드 `ctx.matchedTransfer > 0` → `!== 0`(입금 짝만 있는 달의 음수를 무시하면 F6·완료 기준 9가 실패). 이후 `acc.income += matchedTransfer`가 입금 짝을 되돌린다.
   - 홈 헤더: `income`(−)과 해당 `buy:*`·`debt`(+), `income`(+)과 해당 `sell:*`(−)를 짝 금액만큼 줄인다.
3. **2단계 — 잔차 짝(구간 금액 한도)**: 1단계 뒤 남은 매매·`debt`·`deposit`·`cash` 다리를 하나의 풀로 보고, 양(+) 합과 음(−) 합 중 작은 쪽만큼 서로 지운다(결산 풀 G↔C와 같은 의미). **같은 부호끼리는 지우지 않는다.** 이 다리들이 단방향뿐이면(반대 부호 없음) 지금과 같게 둔다.
4. **남는 몫 라벨(LEARNINGS 2026-10)**: 상쇄가 일어난 풀의 남는 몫은 한 줄로 합친다. 남는 몫이 `cash` 다리에서만 왔으면 `신규 현금`/`현금 정리` 유지, 매매·`debt`·`deposit`가 섞이면 **`기록 안 된 변화`**(결산 라벨과 같은 문자열, 새 표시 키 `unrecorded`, 날짜 없음). `매수`·`매도`·`상환`·`추가 대출` 라벨로 남기지 않는다.
5. **임계값**: 상쇄 뒤 `|금액| < CAUSE_DISPLAY_MIN`(1만) 항목은 숨기고 그 몫은 `getAttributionItems`의 기존 잔차 규칙(같은 부호 최대 항목, 없으면 `cash`)으로 얹는다.
6. **항등식**: 표시 항목 합 = `attr.deltaNet`(vitest 단언).
7. **적용 위치**: `getAttributionItems(attr, transfer?)`·`formatAttributionSentence(attr, transfer?)`에 선택 인자 추가. 홈(`dashboard.tsx:491-493`)만 넘긴다. 인자 없으면 기존 결과와 같다(기존 테스트 diff 0).
8. **캡션**: 상쇄 금액 합 ≥ 1만이면 원인 목록 아래 muted 1줄 `자산 사이에 옮긴 돈은 원인에서 뺐어요`(금액 없음). 360px에서 높이 부담이면 ui-review에서 뺀다(컷 가능).
9. 바꾸지 않음: 구간 기록 목록(`records`)·Δ순자산·구간 라벨.

### 3-B'. `[선택:②]` 거래 저장 시 현금 입출금 함께 기록 (스키마 0)
1. **위치**: 주식 `trade-input.tsx`·코인 `crypto-tx-input.tsx` 수동 입력 폼, `즉시 반영` 체크 아래 선택 행 1개 `현금 계좌에서도 반영`(Checkbox, **기본 꺼짐**, 매번 꺼진 채 열림 — 기억 저장 없음).
2. **보이는 조건**: 즉시 반영 ✓(신규 종목 경로 포함) + **거래 통화와 같은 통화의 현금 계좌 ≥ 1개**(코인=KRW, 주식=종목 통화). 아니면 행을 숨긴다. 스크린샷 일괄 가져오기·미반영 저장·거래 수정은 제외.
3. **계좌 선택**: 같은 통화 계좌가 1개면 이름만 표시, 2개 이상이면 켰을 때 선택 1개(기본 = `cash` 목록 첫 항목).
4. **생성 기록**: 기존 `cashTransactions` 1건 — 매수=`withdrawal`, 매도=`deposit`, 금액 = 수량×단가 (+수수료: 매수 가산·매도 차감), 통화 = 거래 통화, 날짜 = 거래일, `reflected: true`, 메모 `{종목명} 매수|매도`, `recurring` 없음. 잔액 가감은 `cash-tx-input`의 `balancePatch` 규칙 그대로.
5. **원자성(C37)**: 거래·보유 패치·입출금·현금 잔액을 **`saveData` 1회**로 저장하는 컨텍스트 함수 1개(기존 `addTransactionWithPosition`/`addTransactionsBatch`/`addCashTransactionWithBalance` 조합 금지). 실패 시 아무것도 저장되지 않는다. 중복 확인 다이얼로그 '추가'에서도 같은 함수, '기존 유지'면 둘 다 저장 안 함.
6. **가드**: 출금이 기존 `isCashWithdrawalValid`를 통과 못 하면 행 아래 오류 1줄, 저장 전체 차단(거래만 저장되지 않음). 4.52 `shouldWarnTxAfterResync({ txDate, reflected: true, refreshedAtIso: lastRefreshedAt("cash") })`가 참이면 행 아래 `resyncWarningText("cash", …)` 그대로 표시(차단 아님).
7. **삭제**: 거래 삭제는 지금과 같다(짝 기록 자동 삭제 없음). 삭제한 거래와 **같은 날짜·같은 금액의 반영 입출금 기록**이 있으면 토스트 아래 1줄 `현금 입출금 기록은 따로 남아 있어요`. 판정은 표시용이며 데이터를 바꾸지 않는다.
8. **토스트**: 기존 `매수|매도 거래가 기록되었습니다.` 유지, B' 켜고 저장하면 뒤에 ` 현금 기록도 남겼어요` 1문장(ui에서 확정).
9. GA: business-pm 확정 시 feature_use page_title `거래 저장·현금 함께 기록` 1개(금액·계좌명 금지). 미확정이면 넣지 않는다.
10. 문구: 화면 문구에 `계좌 연결`·`연동` 금지(실제로 잇지 않음 — 삭제 시 자동 되돌림 없음). `현금 계좌에서도 반영`·`현금 기록도 남겼어요` 형태만.

## 7. 엣지 케이스
- 빈 데이터·첫 사용자·지난 접속 없음: 헤더 자체가 지금 규칙대로 숨김, 캡션 없음. B' 행은 같은 통화 현금 0개면 숨김.

- 오래된 데이터: 짝 확장은 과거 달 결산 표시를 바꿀 수 있다(입금↔매도 ±3일 기록 보유자). 금액 합·Δ는 불변. 측정: F6·F12·부분 짝(매도 300·입금 200)·달 경계(매도 10/30·입금 11/2) 픽스처에 **수정 전 기대값을 먼저 기재·커밋**한 뒤 수정 후 기대값과 나란히 단언(바뀌는 칸만 diff로 남김).
- 두 기기 동시 편집(②): 거래·입출금은 한 번에 저장되지만 다른 기기가 같은 시점에 한쪽만 고치면 동기화 병합에서 한 쌍이 갈라질 수 있다(기존 병합 규칙의 한계, 새로 생기지 않음).
- 외화: USD 종목 매수(체결 환율) + USD 계좌 → 짝은 체결 환율 vs 현재 환율 차이만큼 남음 → `기록 안 된 변화`로 남거나 1만 미만이면 흡수.
- 구버전 기기 혼재(②): B'가 만든 기록은 기존 스키마라 동기화·읽기 그대로. 구버전 결산은 입금↔매도 짝이 없어 F6이 수정 전 모양으로 보인다(한계 3).

## 9. 알려진 한계
1. 달 경계 분리(S2·S7): 기록일과 맞추기 날짜가 다른 달이면 결산이 각 달로 나뉜다(변경 안 함).
2. 단방향 다리(매수만 기록·현금 미수정, 대출만 맞추기)는 지금처럼 `주식 매수`·`대출 상환`으로 보인다 — 상쇄할 반대 다리가 없어 A 범위 밖.
3. `[②]` 거래를 지워도 입출금 기록은 남는다(링크 필드 없음). 구버전 기기 결산은 입금↔매도 짝이 없다.
4. 짝은 ±3일·금액 근접 규칙이라 같은 시기 무관한 비정기 입금이 매도와 짝지어질 수 있다(합계·Δ 불변, 표시만).
5. `[②]` 두 기기 동시 편집 시 거래·입출금 한 쌍이 동기화 병합에서 갈라질 수 있다(기존 병합 한계, qa 13번 확인).
