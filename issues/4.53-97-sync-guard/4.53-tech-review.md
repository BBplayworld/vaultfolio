# 4.53 tech-review — /api/sync 남용 방어 (#97)
기준: origin/main 4fee68c. 위험 등급 초안: **risk:medium**(동기화 라우트 수정 → 대표 승인, 위임 머지 조건 ④ 미충족).

## 1. 현행 분석
- `src/app/api/sync/route.ts`: 자체 `getClientIp`가 XFF **맨 왼쪽**(클라이언트 위조 가능)을 신뢰 → PUT `checkRateLimit`(rl:legacy:{ip}, 분당 10) 헤더만 바꿔 우회 가능. 단 Vercel은 XFF를 실제 IP로 덮어써 운영 실영향은 이론적.
- GET은 rate limit·L1이 없고, 서명 검증 전에 `getAssetEnvelope`(Redis 조회, 최대 4MB급 암호문) 수행 → 임의 assetId로 무제한 Redis 읽기. assetId·nonce·sig 형식 검증도 없음(`csync:asset:{assetId}` 키에 임의 문자열 삽입).
- `src/server/api-guard.ts`: 다른 라우트는 x-vercel-forwarded-for 우선 `getClientIp`, L1 버킷(`hitL1`)을 사용. 주석상 sync는 의도적 제외였음.

## 2. 변경안 (프로토콜·저장 포맷·서버 전송 값 불변)
1. sync의 자체 `getClientIp` 삭제 → `api-guard.getClientIp` 사용(PUT rate limit 키가 신뢰 헤더 기준이 됨).
2. `api-guard.guardL1Only(request, route, limit)` 신설(출처·본문 검사 없이 L1만; sync는 서명 인증 + 동일 출처 fetch라 cross-site 검사로 인한 오차단 위험을 피함). GET 맨 앞에서 호출(`sync-get`, 120/분/IP/인스턴스, unknown IP는 1/4).
3. `parseAuth`에서 assetId `^[A-Za-z0-9_-]{8,128}$`, nonce `^[A-Za-z0-9_-]{1,64}$`, sig ≤200자, ts 유한 숫자 검증 — 저장소 조회·rate limit·sha256·서명 검증 **이전**에 401. 정상 assetId는 `generateAssetId()` = 16B base64url 22자.
- PUT 분당 10 한도는 그대로(변경 없음).

## 3. 임계값 근거 (정상 흐름 비차단)
- 기기 1대: meta 폴링 60초 간격 + focus·visibilitychange 전환 시 tick + pull 가끔 → 분당 보통 1~6회. 공용 IP(가족·사무실) 4기기 × 6 = 24 → 120은 5배 여유, 폭주(분당 수백~수천)만 차단. L1은 인스턴스 메모리라 다중 인스턴스에서 실효 한도는 더 느슨하나 목적은 Redis 폭주 억제.
- push: 기존 10/분 유지, 디바운스 push·409 후 pull→재push 흐름(분당 수 회)은 영향 없음. 4.47 overwrite-guard·되돌리기 push 409 흐름은 서버 응답 코드·본문 불변이라 무영향(테스트로 409 + asset.version 확인).
- preview: 클라이언트가 `isCloudSyncEnabled()` false로 요청 자체를 보내지 않음 → 서버 변경 영향 없음.

## 4. 클라이언트 영향
- GET 429: `fetchRemoteVersion`은 `!res.ok` → null(조용히 건너뜀, 다음 tick 재시도). `pullAsset`은 `data.error`(한국어 "요청이 너무 많습니다…")를 오류 메시지로 표시, 상태 손상 없음. 잘못된 assetId → 401 → "금고 암호가 올바르지 않습니다."(정상 사용자는 도달 불가).

## 5. 데이터 영향·롤백
- 로컬/서버 스키마·저장 키·마이그레이션 0, 서버로 나가는 값 증가 0(요청 형식 불변, 검증만 추가). 구버전 혼재·롤백 시 기록 손실 가능성 없음.
- 위험: 과거 비표준 assetId(`#asset=` 구형)가 있으면 401 → 허용 범위(8~128자 URL-safe)를 넓게 잡아 완화. 롤백 = PR revert 1개.

## 6. 테스트
`src/lib/__tests__/sync-route-guard.test.ts`: 신규→pull→meta→409→재push 정상 흐름, 4기기 폴링 24회 무차단, GET 121번째 429(저장소 호출 0, Retry-After), XFF 좌측 위조 우회 불가(GET·PUT), 잘못된 assetId 7종·과대 nonce/sig·비정상 ts 거부, 틀린 서명 401. 기존 991 전체 통과.

## 7. 하위호환 증명 (후속, qa 인계 전)
- 이력: `git log --all -S/-G`(assetId·generateAssetId·randomNonce·assetIdRegex) 결과 assetId 생성/인증 코드는 **4.5 동기화 beta(989e7b6)에서 도입된 뒤 생성 로직 무변경**(4.10 492ca47·4.22 98ac9a5는 PUT CAS·pull merge만 변경). syncId/vaultId 등 구 식별자 형식은 4.5 내부 용어 변경일 뿐 배포된 별도 형식 없음.
- assetId: `toBase64Url(16B)` = 표준 base64 22자에서 `+→-`, `/→_`, `=` 제거 → 문자 `[A-Za-z0-9_-]` 22자. 수동 입력 검증(connect-dialog, 4.5부터 동일) `^[A-Za-z0-9-_]{20,24}$` ⊂ `{8,128}`. `#sync=`/`#asset=` 링크도 같은 검증을 통과해야 연결됨. 패딩 `=`·`+`·`/`는 생성 단계에서 제거되므로 도달 불가.
- nonce: `toBase64Url(12B)` = 16자 `[A-Za-z0-9_-]` ⊂ `{1,64}`. sig: 표준 base64 64B = 88자(`+/=` 포함) → **문자 제한 없이 길이 ≤200만 검사**(88 ≪ 200). ts: `Math.floor(Date.now()/1000)` 정수(4.5부터 동일) → 유한 숫자 통과.
- 결론: 과거 모든 버전 클라이언트가 만든 토큰이 새 검증을 통과. 정규식 완화 불필요(이미 상위집합). 인증 토큰 자체는 4.5 이후 base64url JSON 동일.
