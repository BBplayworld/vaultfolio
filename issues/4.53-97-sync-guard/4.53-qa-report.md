## 5. 클라이언트 429/401 처리 (코드 추적)
- 백그라운드 meta 폴링(`fetchRemoteVersion`): `!res.ok` → null → pull 안 함, 60초 후 다음 tick에서 재시도. 무한/빠른 재시도 루프 없음. 상태·로컬 데이터 변경 0.
- `pullAsset` 429: `data.error`("요청이 너무 많습니다…")를 error 결과로 반환, 복호화·로컬 교체 이전이라 **덮어쓰기 없음**. 수동 pull만 메시지 표시, 자동 pull(auto)은 토스트 없이 조용히 실패.
- 409 후 force pull이 429로 실패하면 기존 로직대로 3초 뒤 1회 재시도 후 다음 폴링까지 대기(기존 동작, 신규 루프 아님). 로컬 stale 상태에서 push는 baseVersion 불일치로 계속 409 → 서버 데이터 덮임 없음.
- push 경로(PUT)는 GET 한도 영향 없음. 401: "금고 암호가 올바르지 않습니다." — 정상 사용자는 도달 불가(형식 통과 증명).
→ 사용자 기록 손실·덮어쓰기·무한 재시도 위험 없음.
