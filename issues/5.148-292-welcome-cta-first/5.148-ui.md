## 2. 진입 애니메이션 (ENTER = fade + slide-from-bottom-3, 500ms, `motion-safe`)
stagger는 화면 위→아래 순서를 따른다. 지연 재배정:
| 요소 | 현재 | 새 값 |
|---|---|---|
| 히어로 | 기존 | 0ms(그대로) |
| 신뢰 줄 | 60ms | 60ms(그대로) |
| 등록 칸 | 180ms | **120ms** |
| 예시 묶음(라벨·칩·카드·안내 문장) | 120ms | **180ms** |
- 간격 60ms 등차 유지. 가장 늦은 요소도 180+500=680ms에 정착, 기존과 동일 총 시간. 등록 칸이 먼저 떠야 하므로 순서만 교체.
- 안내 문장은 예시 묶음 안에서 같이 들어옴(별도 ENTER 금지, 이중 모션 방지). `skipEnter`·focusCta(체험 복귀 포커스·진입 모션)·셸 상태 전환 `fade-in-0 200ms`는 그대로. 재마운트 없음(순서만 바꾸는 정적 JSX라 상태 전환 시 모션 소실 없음).
- reduced-motion: 전부 `motion-safe:`라 정지 상태로 즉시 표시.

## 3. 칩·버튼 목표 좌표 (planner 운영 실측 기반 계산, 문서 y, 스크롤 0)
등록 칸은 신뢰 줄 끝 + 20에서 시작, 높이 216(최소), 버튼 2번째 하단 = 칸 시작 + 약 200.
| 뷰포트 | 신뢰 줄 끝 | 등록 칸 | 등록 버튼 2개 하단(≈) | 라벨/칩 하단(≈) | 판정 목표 |
|---|---|---|---|---|---|
| 320×568 | 230 | 250~466 | ≤ 452 | ≤ 520 | 버튼·칩 하단 ≤ 568 (여유 ≥ 48) |
| 375×667 | 204 | 224~440 | ≤ 426 | ≤ 494 | ≤ 667 (여유 ≥ 170) |
| 375×560(인앱 웹뷰 추정) | 204 | 224~440 | ≤ 426 (인앱은 `외부 브라우저에서 시작하기` 1개, 더 위) | ≤ 494 | ≤ 560 (여유 ≥ 66) |
| 390×844 | 204 | 224~440 | ≤ 426 | ≤ 494 | 예시 카드 상단 일부까지 보임 |
- 칩 하단 = 등록 칸 끝 + 20 + 라벨 행(약 28~32). 320은 배지가 2줄로 내려가도 칩은 첫 줄 오른쪽이라 하단 동일.
- **칩 가드 결과: 계산상 4개 크기 모두 통과 → 칩은 라벨 행 그대로 둔다.** ceo.md 조건 2의 '칩만 등록 칸 아래 줄' 대체 배치는 쓰지 않는다. 실측에서 320×568 칩 하단이 568을 넘으면(예: 보안 상세·폰트 확대) 그때만 대체 배치(예시 라벨 행 위로 칩만 우측 정렬 별도 줄, 높이 +0 라벨 행 병합)로 ui-review에서 수정 요청.
- 인앱 iOS 가이드 펼침 시 칸 높이가 늘어 칩이 아래로 밀리는 것은 허용(사용자 조작 결과). 단 펼침 전 상태에서 위 표 통과가 기준.

## 4. 점검 방법 (ui-review·qa)
- Playwright 모바일 UA, 0건 기기(localStorage 비움)로 320×568, 375×667, 375×560, 390×844. 각 크기에서 `getBoundingClientRect().bottom`을 `welcome-cta-slot` 안 버튼 2개(`welcome-cta-inapp` 포함), `welcome-trial-link`에 대해 읽어 `≤ innerHeight` 확인, scrollY=0.
- 인앱 iOS: UA를 인앱+iOS로, `welcome-cta-inapp` 클릭 → `welcome-inapp-guide` 펼침. 가이드 하단이 문서 안에서 잘리지(`overflow-hidden` 클리핑) 않고 칸이 늘어나는지, 펼친 뒤 아래 예시 카드와 겹침 0 확인(375×560·320×568 스크린샷). 스크롤 시 가이드 마지막 줄이 화면 안으로 올 수 있어야 함.
- `직접 입력 · 가져오기` 팝오버: 열기 후 팝오버 rect가 `0 ≤ left`, `right ≤ innerWidth`, `top ≥ 0`, `bottom ≤ innerHeight`(위로 열려 상단이 잘리지 않는지가 핵심, 4.86 p2 '320 가져오기 행 가림' 비교). 위로 올라와 상단이 짧아졌으므로 아래로 열리는지 위로 열리는지 기록, 어느 쪽이든 화면 안이어야 함. 320·375×560 둘 다.
- 보안 상세 펼침(자세히 보기) 상태에서 등록 칸이 아래로 밀리는 것은 허용, 접힌 기본 상태가 기준.
- 데스크톱 1280×800: 단일 컬럼 중앙(기존 max-w)에서 등록 칸 → 예시 → 설치 박스 순, 설치 박스가 안내 문장 아래. 첫 화면에 등록 칸 전체가 보임. 설치 박스 레이아웃 변화 0.

## 5. 다크/라이트
- 색 변경 0. 등록 칸 `bg-card/80 shadow-xs`, brand 버튼, 칩 `bg-brand/15 dark:bg-brand/20`, 안내 문장 `ASSET_THEME.distributionCard.muted` 그대로. 다크에서 등록 칸이 신뢰 줄 바로 밑으로 오므로 카드(bg-card/80)와 배경 경계가 흐리지 않은지(shadow-xs로 분리) 스크린샷 확인. 안내 문장(text-2xs muted)이 예시 카드 바로 밑으로 왔을 때 다크 대비는 5.147 B 다크 대비 감사 기준(≥4.5:1 목표, 2xs라 미달이면 text-xs 승격은 별건 후보)으로 같이 본다.
- 스크린샷 대상: 라이트·다크 × 320×568·375×667·375×560·1280×800, 인앱 iOS 펼침 1세트.
