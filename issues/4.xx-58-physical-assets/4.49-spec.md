정본 우선순위: 이 spec 13절(11-08 재점검) > 12절(11-07 COO 조건) > 4.49-tech-review(일정·롤백 문구는 8·12·13절로 대체) > 그 밖의 절.
위험 등급: **high 유지**. assetData 스키마, 저장, 동기화 병합, 스냅샷·결산 매핑을 함께 바꾼다.

## 1. 문제
자산군이 부동산·주식·코인·현금·대출 5종뿐이다(`types/asset.ts` `assetDataSchema`). 그래서 금 같은 실물 보유분은 현금이나 부동산 "other"로 위장 입력되거나 아예 빠진다. "내 자산을 정확히 아는 상태"(PRINCIPLES 1장)에 구멍이 있다.

## 2. 목표 행동
- 실물 자산을 1건 이상 등록한다.
- 평가액을 고친 달의 결산에서 그 변화가 "평가 갱신"으로 분류된다.
- 기기 혼재·롤백 상황에서도 실물 자산이 남는다.

## 3. 범위
### 3-1. 유형(5)
`gold` 금 · `silver` 은 · `jewelry` 귀금속·보석 · `collectible` 수집품·미술품 · `other` 기타 실물.
차량·보험환급금·전월세 보증금은 제외한다(대표 2026-11-01). **모르는 유형 값은 `other`로 읽는다.** v2에서 유형을 추가해도 v4.40 기기의 pull이 parse 오류로 실패하지 않게 하기 위해서다.

### 3-2. 입력 방식 비교와 권고
| | 부동산(현행) | 코인(현행) | 실물 권고 |
|---|---|---|---|
| 저장 정본 | `purchasePrice`·`currentValue`(원, 수동 입력, 필수 >0) | `quantity`×`currentPrice`(시세 자동, `baseDate`) | **평가액 방식**: `purchasePrice`·`currentValue` |
| 시세 | 실거래 추정은 보조(`marketEstimate*`, 파생값) | 업비트 시세가 정본 | v1 없음 |
| 결산 | `breakdown.realEstate`·`cost.realEstate` 차이 → `price:realEstate`(평가 갱신) / `buy·sell:realEstate`(`asset-report.ts:696-746`) | 시세 효과 | 부동산 경로와 같은 구조 |

평가액 방식을 권고하는 근거:
1. v1에는 시세가 없다. 수량×단가로 받으면 사용자가 단가를 매번 고쳐야 해서 수고는 같고 입력 칸만 늘어난다.
2. 보석·수집품은 수량×단가가 성립하지 않는다. 다섯 유형에 공통으로 쓸 수 있는 값은 평가액이다.
3. 부동산과 같은 형태라 `computeNetAsset`·스냅샷·결산 매핑을 같은 패턴으로 재사용할 수 있다.

**수량·단위 메타는 v1에서 넣지 않는다**(cto). 지금 쓰는 곳이 없고, v2에서 시세를 연동할 때 추가한다. 미래 필드가 생겨도 지워지지 않도록 아래 3-3의 passthrough로 대비한다.

### 3-3. 자료형 (제안)
- `physicalAssetSchema = { id, type(enum 5, 모르는 값은 other), name(필수), currentValue(>0 필수), purchasePrice(≥0, 비우면 저장 시 currentValue로 채움 → 수익 0), purchaseDate(필수, 결산 유입 판정), description? }`
- 스키마는 **`.passthrough()`**로 둔다. v4.40 기기가 미래 버전의 필드를 저장 중에 지우지 않게 하기 위해서다.
- `assetDataSchema.physicalAssets: z.array(...).optional()`로 두고 **`.default([])`는 쓰지 않는다.** 키가 없는 경우와 빈 배열을 구분해야 3-5의 계약이 동작한다. 현행 `cash`·`loans`는 default([])라서 이 구분이 없다.

### 3-4. 저장 위치: 분리 키 + 메모리 병합 (cto 정정 반영)
**사실 확인**
- 구버전 코드는 `assetDataSchemaLoose.parse`(zod 기본 strip)로 읽고, `saveAssetData`로 검증본을 저장한다(`asset-storage.ts:111,121-123`). 그래서 새 배열을 assetData 안에 두면 첫 저장 때 실물 자산이 지워진다.
- 구버전 `clearAssetData`(`:407-445`)는 `secretasset_`로 시작하는 키를 keep 목록과 일부 접두만 남기고 전부 지운다. 이 함수는 동기화 pull, 백업 가져오기(`:341`), 데모 주입에서 매번 실행된다.
- 따라서 `secretasset_` 접두를 쓴 분리 키도 롤백된 기기의 첫 pull이나 가져오기에서 사라진다.

**결정**
- 분리 키를 쓰되, 이름은 다음 어디에도 걸리지 않게 짓는다.
  - `startsWith("secretasset_")`
  - `STORAGE_KEY_PREFIXES`(`secretasset_profit:`, `secretasset_notice_seen_`)
  - `secretasset-gemini-`
  - 레거시 `profit:`
- 확인한 키 순회 지점: `clearAssetData`, `clearUserCaches`(`asset-storage.ts:456`), `migrateStorageKeys`(`local-storage.ts:117·171`), `one-time-migrations.ts:86`, `profit-cache-cleanup.ts:34`, `use-gemini-usage.ts:57`.
- 메모리·Context·동기화·백업 payload에서는 `getAssetData`가 이 키를 읽어 `assetData.physicalAssets`로 합쳐 다룬다.
- **키 이름 후보**(최종 결정은 tech-review):
  1. `secretasset.physical_assets` — 권고. 점(.) 구분이라 위 접두에 걸리지 않고, `storage-stats.ts:25`의 `startsWith("secretasset")` 집계에는 자동으로 포함된다.
  2. `sa_physical_assets`
  3. `vaultfolio_physical_assets`

  2·3을 고르면 storage-stats에 명시적으로 추가해야 한다.

**신버전이 책임질 일**
1. "모든 데이터 삭제"에서 이 키를 명시적으로 지운다(`backup-status.ts:106` 패턴).
2. 가져오기(`applyImportedPayload`), 공유 반영(`applySharedData`), 데모 주입을 각 경로의 교체 의미에 맞게 처리한다(3-5 표).
3. `storage-stats` 집계에 이 키를 넣는다.
4. `saveAssetDataRaw`(`:396`)와 `itemCountFingerprint`(`:160`)에도 반영한다.

**알려진 한계**(브리프 위험 절에 기재): 구버전에서 "모든 데이터 삭제"를 하면 이 키가 남는다. 이후 신버전으로 돌아오면 실물 자산이 다시 보인다. 머지 후 구버전 기기에서만 생긴다. **기기를 남에게 넘기려고 지운 경우에는 다음 사용자에게 실물 이름·평가액이 보일 수 있다(노출 위험).** 브리프에는 "잔존"이 아니라 "노출" 문장으로 적는다(C14·C17).

### 3-5. 데이터 안전 계약 (경로별)
| 경로 | 계약 |
|---|---|
| 동기화 pull | 원격 `assetData.physicalAssets` 키가 없으면(구버전 기기가 push한 경우) **로컬을 유지**한다. 키가 있으면 `mergeById`로 기존 규칙(신규 보존, 삭제 존중)을 적용한다. `collectAssetIds`(`:197`)와 `reconcileAdditiveMerge`(`:228`)에 실물 배열을 추가한다. 키가 없는 payload의 `remoteIds`에는 로컬 실물 id를 넣지 않는다 |
| 구버전 기기의 pull | zod strip으로 오류 없이 실물만 버린다. 이후 그 기기의 push에는 키가 없으므로 위 계약으로 보호된다(C5·C13 순환 테스트) |
| 백업 가져오기 | 키가 있으면 교체한다. **키가 없으면(구 백업) 로컬을 유지하고 토스트 1줄**을 띄운다: "실물 자산은 기존 값을 유지했어요" |
| 공유 링크·복원 코드(packV7) | 토큰에 실물을 넣지 않는다(포맷 변경 C7 없음). ① 코드를 만들 때 실물이 1건 이상이면 안내 1줄: "실물 자산은 복원 코드에 포함되지 않아요. 백업 파일을 써 주세요." ② `applySharedData`(공유 반영)는 교체 의미에 맞춰 **로컬 실물을 비운다**. 받는 쪽 순자산이 보낸 쪽보다 작아지는 것은 알려진 한계로 둔다(공유 사용 0건) |
| 데모 주입 | 교체 의미에 맞춰 실물 키를 비우거나 데모 값으로 채운다(tech-review). 체험 모드는 메모리 Storage라 원본에 영향이 없다 |
| 모든 데이터 삭제 | 실물 키를 명시적으로 삭제한다 |
| 스냅샷 | `SnapshotBreakdown.physical?`·`SnapshotCost.physical?`을 optional로 둔다(`tenantDeposit` 선례). 필드가 없으면 0으로 읽는다. 기능 이전 스냅샷은 실제로 0이므로 맞다 |
| 월 스냅샷 병합 | `mergeMonthlySnapshots`(`:290`)에서 같은 달에 로컬 `breakdown.physical > 0`이고 수신값에 필드가 없으면 로컬을 유지한다 |
| **일별 스냅샷** | **v1 제외**. pull은 일별을 통째로 교체한다(`:358`). 구버전 기기가 쓴 날의 일·주 그래프가 실물만큼 내려가는 문제는 알려진 한계로 둔다 |
| 자산 보유 판정 | `hasAnyAssets`(`:67`) 시그니처에 실물을 넣는다. 0건 판정을 쓰는 곳은 웰컴, GA `countAssets`, trial 세 곳이다 |
| 체험 거부(C28) | `trialRejectReason`(`trial-boot.ts:66-81`)이 **새 키도 읽어** 1건 이상이면 거부한다 |
| 마이그레이션 | 기존 데이터에는 키가 없으므로 변환하지 않는다. 복원 테스트는 필수다(10절) |

### 3-6. 결산·원인 매핑 (cto 정정)
- `computeNetAsset`(`asset-data-context.tsx:212`)에 `physicalValue`를 추가해 `totalValue = realEstate + physical + financial`로 만든다. 실물은 **금융자산에 넣지 않는다**.
- 스냅샷 기록(`asset-data-context.tsx:699`, `asset-report.ts:1162`)에 `breakdown.physical`·`cost.physical`을 넣는다.
- 원인 효과(`asset-report.ts`):
  - `price:physical` = Δbreakdown.physical − Δcost.physical
  - `buy:physical` / `sell:physical` = Δcost.physical
  - 추정 경로는 부동산(`:556-558`)처럼 `purchaseDate` 구간으로 판정한다.
  - `AttributionGroupKey`에 `physical`("실물")을 추가한다.
- 결산 매핑(`settlement.ts` `mapSettlementCauses`):
  - `price:physical` → `valuation`("평가 갱신"). 부동산과 한 항목으로 묶고 결산 항목 수는 늘리지 않는다.
  - `buy/sell:physical` → `TRADE_KEYS`(내부 이동 풀)
  - `matchedTransfer` 짝짓기 대상에 "구간 안 `purchaseDate`가 있는 실물 신규분"을 추가한다(±3일, 금액은 둘 중 작은 값, 기존 규칙 재사용, C23).
  - 자산 변화 원인 상세에서만 `price:physical`을 별도 행으로 둔다.
- 결산 화면 컴포넌트·라벨은 바꾸지 않는다. 바뀌는 것은 엔진의 키 매핑과 짝짓기 함수뿐이다.

## 4. 사용자 흐름
1. FAB → "실물 자산" → 입력 폼.
   - 항목: 유형 칩·이름·현재 평가액·매입가(선택)·매입일·메모. 확인 버튼은 `Button variant="brand"`.
   - **폼 상단 안내 1줄**: "현금·부동산에 금을 넣어 두셨다면 그 항목은 지워 주세요." 같은 금을 두 번 계상하는 것을 막기 위해서다.
2. 저장하면 토스트를 띄우고 `trackAssetSave{asset_type: physical, method: manual}`를 보낸다. 자산 0건이었으면 `first_asset_saved`도 같이 간다.
3. 홈: Hero 순자산에 합산하고, 구성 바에 "실물" 항목을 부동산·금융자산과 같은 단계로 둔다.
4. 상세 허브 "실물 자산" 탭: 항목 카드(이름·유형·평가액·매입가 대비 손익)와 편집·삭제.
5. 평가액을 수정하면 당일 월 스냅샷이 갱신되고, 다음 결산의 "평가 갱신"에 반영된다.

라벨은 두 가지만 쓴다: 메뉴·탭은 "실물 자산", 구성 바는 "실물".

## 5. 엣지 케이스
| 상황 | 동작 |
|---|---|

| 이중 계상 | 폼 안내 1줄만 둔다. 자동 탐지는 하지 않는다 |

## 7. GA (11-08 정정: page_title 1개 방식)
- GA로 나가는 값은 `page_title` 1개뿐이다(`ga.ts` 현행, 4.41 #68 단순화). `PARAM_VALUES`는 page_title을 고르는 내부 타입이며 전송되지 않는다.

## 10. 완료 기준 (qa 검사 문장)
1. v4.53(직전 main) 형식 데이터(실물 키 없음)로 시작한 기기가 v4.54에서 기존 5종 자산과 스냅샷을 그대로 보여 준다(복원 테스트).
2. 실물을 1건 저장하면 분리 키(tech-review가 정한 이름)에 배열이 생기고, `secretasset_asset_data`에는 `physicalAssets`가 없다. 분리 키 이름은 `secretasset_`로 시작하지 않는다.
3. v4.54에서 실물을 저장한다 → v4.53(직전 main) 코드로 자산 저장 1회, pull 1회, 가져오기 1회를 한다 → 다시 v4.54로 연다. 이때 실물이 남아 있다.
4. 동기화 단위 테스트(push→pull→저장→push 순환):
   - 구버전 payload(키 없음)를 pull하면 로컬 실물이 유지된다.
   - 신버전에서 삭제하면 다른 기기가 pull한 뒤 삭제가 반영된다.
   - 두 기기가 동시에 추가하면 양쪽 항목이 모두 남는다.
5. 백업 가져오기:
   - 구 백업 JSON을 가져오면 실물이 유지되고 토스트 1줄이 뜬다.
   - 키가 있는 백업을 가져오면 실물이 교체된다.
6. 공유·복원 코드:
   - 실물이 있을 때 코드를 만들면 미포함 안내 1줄이 뜬다.
   - 공유 데이터를 반영하면 로컬 실물이 비워진다.
   - "모든 데이터 삭제" 후 실물 키가 없다.
7. 월 결산 원인이 패턴별 기대값과 같고, 모든 패턴에서 원인 합계가 Δ순자산과 같다(C20·C21·C23·C24):

| 패턴 | 기대값 |
|---|---|
| ① 오래전 산 금을 처음 등록(현금 등록 사용자) | 기록 안 된 변화 +X(기존 InfoHint로 설명됨, 부동산과 같다) |
| ② 같은 상황, 현금 미등록 사용자 | 순유입 +X |
| ③ 현금 잔액을 직접 줄이고 금 등록 | 0(풀 상쇄) |
| ④ 기록된 출금 → 금 등록(±3일) | 0(`matchedTransfer`로 짝지어짐, 두 다리가 갈리지 않음) |
| ⑤ 평가액만 수정 | 평가 갱신 ±Δ(부동산과 합산), 원인 상세에는 `price:physical` 행 |
| ⑥ 변화 없는 달 | 실물 관련 원인 0 |
