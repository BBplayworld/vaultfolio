# #60 인앱 브라우저 도착 개선 — direction (경험 절)

상태: planning ① / 사업 절·합의 절: 아래 작성됨(business-pm, 2026-10-31) / 근거: `in-app-browser-gate.tsx`, `detect-browser.ts`, `welcome-guide.tsx`

## 경험
### 1. 사용자가 하게 될 행동
- 카페·카톡·Threads 링크로 인앱에 도착한 자산 0건 방문자가 전체 차단 화면 대신 **웰컴 화면을 먼저 본다**.
- 웰컴의 CTA 슬롯에서 "외부 브라우저에서 시작하기" 한 번으로 Chrome/Safari로 이동한다(Android 자동, iOS 주소 복사 + 가이드).
- (#59와 결합) 인앱에서도 예시 둘러보기는 가능하다(메모리 전용이라 유실 위험 없음).

### 2. 범위
- 포함: 게이트 노출 조건 변경(0건·동기화 없음·공유/동기화 링크 없음일 때만 웰컴 노출), 로드 전 **문구 없는 빈 덮개**, 웰컴 CTA 슬롯 4번째 상태 `inapp`, 감지 토큰 3개 추가(`barcelona`·`daumapps`·`band\/`), 0건 판정 헬퍼 `hasAnyAssets` 1개(`page.tsx`·`use-share-artifacts.ts`·`preview-gate.tsx` 3곳만 교체), 자산 생성 진입점 인앱 차단 검증.
- **줄일 수 있는 것**: iOS 가이드 신규 제작(기존 `InAppExternalGuide` 재사용) / 신규 GA 이벤트(기존 `pwa_install{method: inapp_move}`·`welcome_view{source: inapp}` 재사용) / PIN 흐름 변경(1건 이상은 현행 유지).
- **하지 않을 것**: 감지 토큰 `kakaostory`·`snapchat` 추가, `asset-data-context`의 0건 판정 교체, 인앱에서 자산 등록 허용, 자산 1건 이상 게이트 완화, 새 진입점·딥링크 스킴 추가, 외부 이동 후 "이어서 보기" 맥락 전달(쿼리 파라미터 금지 — `/`로 이동).

### 3. 기존 화면 변화
- 바뀌는 곳: 인앱 + 0건일 때 `InAppBrowserGate` 미노출(웰컴 노출), 웰컴 CTA 슬롯 `data-state="inapp"` 추가. 
- 그대로: 인앱 + 1건 이상 = 현행 게이트(PIN), 동기화 기기 = 현행, 앱 잠금, `isBackgroundWorkBlocked`(인앱이면 계속 true).

### 4. 사업 절에 대한 의견
- `동의`. 사전 확인(`app_mode=inapp` 신규 기기 조회)은 개발과 병행, 앱 공지 불필요에 동의. 효과는 `welcome_view source`별로 분리해 본다.

### 5. 문구 (팀 확정 — 최종 확인은 반영 결정으로 갈음)
- 슬롯 제목 "자산 등록은 Chrome·Safari에서 시작해요" / 본문 "이 화면에서는 입력한 내용이 사라질 수 있어요." / 버튼 "외부 브라우저에서 시작하기" / iOS 캡션 "주소가 복사됐어요. 브라우저에 붙여넣어 주세요."
- 일정: 11/9~11/12 (#61 다음, #59 앞). 컷 규칙: 11/24 #59 미통과 시 #59만 되돌리고 #60 포함 반영.

## 사업 (business-pm, 2026-10-31)
1. **왜 지금**: 첫 발견 기여(채널 유입 누수 방지). Threads·카페·카톡 링크는 인앱으로 열리는 비중이 높은데 지금은 자산 0건이어도 앱을 보기 전에 전체 차단된다. 단 인앱 도착 규모는 **모른다**: 게이트 뒤에서는 웰컴 조회가 없어 `welcome_view source=inapp`으로 현재 비율을 알 수 없고, 사용자 속성 `app_mode=inapp` 기기 수가 유일한 간접 단서다. 현 유입 월 약 17기기에서 기여는 작고(월 +0.3~0.8 추정), 가치는 채널을 키울 때 누수를 막는 선행 조건 + 감지 누락 인앱(Threads 등)의 유실 위험 제거에 있다
2. **누구를 위해**: 카페 연재·Threads 글을 보고 링크를 누른 3040 투자자. 인앱에서 자산을 입력했다가 외부 이동 시 잃는 사람
3. **성공의 모습** (신규 이벤트 없음):
   - `welcome_view{source:inapp}` 기기 대비 `pwa_install{method:inapp_move}` 기기 비율 ≥ 20%(8주, 표본 작아 정성 병기). 이동하면 외부 브라우저에서 새 기기로 집계되어 이후 등록 전환 추적은 끊김 — 이동 수까지만 측정
   - 가드레일: 인앱 0건 상태에서 `secretasset_assetData` 생성 0(자동 테스트), 정상 브라우저 오탐 차단 0
4. **하지 않으면 잃는 것**: 약함. 지금 규모에선 잃는 숫자가 월 1기기 미만. 다만 채널 노출을 늘리는 순간(마케팅 주 7건) 접촉 자체가 막히는 구조라 방치 비용이 커진다. 사전 확인(착수 조건 아님): 대표가 GA에서 `app_mode=inapp` 신규 기기 수 1회 조회 — 값이 월 2 미만이면 "채널 확대용 선행 정비"로만 서술하고 효과 판독은 포기한다

## 합의 (business-pm)
- 최종 방향: 0건·동기화 없음·해시 없음일 때만 웰컴 노출, 인앱 슬롯은 등록 CTA를 대체(공존 금지), 1건 이상은 현행 유지. 사전 확인 조건 동의(경험 절 4항)는 개발 방향을 바꾸지 않으므로 병행 조회
- spec 6절 질문 답: 감지 보강으로 게이트가 새로 뜨는 기존 인앱 사용자에 대한 앱 공지/릴리스 노트 **불필요**(보호 목적, 공지 채널 없음, 마케팅에서 언급 안 함)
