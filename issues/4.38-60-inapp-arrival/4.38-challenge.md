# 4.38 challenge — 인앱 브라우저 도착 개선 (#60)

작성: cto, 2026-10-31. 기준 코드 issue-4.37 e4f27c6. 대상: 4.38-direction.md, 4.38-spec.md(초안)

## 판정: `통과` (조건 4개 반영) — 위험 등급 `medium`
저장 스키마·동기화·금액 계산은 건드리지 않고, 새 화면 상태와 게이트 조건만 바꾼다. 다만 감지 정규식이 백그라운드 동작 차단과 연결돼 있어 low가 아니다.

## 1. 코드 사실 확인
- **깜빡임**: `page.tsx`는 `isDataLoaded` 전에 `null`을 반환한다(73행). 게이트는 `mounted` 뒤에 무조건 덮는다(in-app-browser-gate.tsx 44).
  - spec대로 "로드 전에는 덮음 유지"를 지키면 1건 이상 사용자에게 웰컴이 깜빡이지 않는다(사실 확인).
  - 반대 방향의 깜빡임이 있다. **0건 인앱 방문자는 로드 전 "외부 브라우저에서 열어주세요" 경고가 잠깐 보였다가 사라진다.**
- **오탐 영향**: `isInApp`을 쓰는 곳은 게이트만이 아니다.
  - `isInAppGateActive()` → `isBackgroundWorkBlocked()`(background-gate.ts 15)가 시세·환율·스냅샷 자동 갱신을 끈다.
  - `welcome_view source`, 사용자 속성 `app_mode`도 같은 값을 쓴다.
  - 오탐이 나면 일반 브라우저의 **자산 보유 사용자**가 PIN 이동 게이트에 막힐 뿐 아니라 시세 갱신까지 멈춘다. 화면 차단보다 피해가 크다.
- **0건 판정 중복**: 같은 5배열 판정이 4곳에 있다. `page.tsx:34`, `use-share-artifacts.ts:21`, `preview-gate.tsx:27`(`hasAnyAssets`), `asset-data-context.tsx:857`.
- **효과 크기 사전 확인 가능**: 인앱에서도 웰컴은 게이트 아래에 렌더된다. 그래서 `welcome_view{source: inapp}`가 **지금도 집계된다**(welcome-guide.tsx 101). 사업 절의 "사전 확인 조건"은 대표가 공유하는 GA 수치로 바로 판독할 수 있다. 단 Threads는 현재 감지되지 않아 web으로 집계된다.
- **안전망**: 누락된 생성 경로로 자산이 생겨도 판정이 다시 계산되면 1건 이상이 되어 현행 PIN 게이트가 다시 덮는다. 유실 위험은 "외부 이동 안내가 늦게 뜨는 것"으로 제한된다. 그래도 spec 5절의 전수 확인은 유지한다.

## 2. 조건 (spec 반영)
1. **로드 전 덮개는 문구 없는 빈 덮개**(`bg-background`, 같은 z-layer)로 한다. 경고 본문·버튼은 로드 후 판정이 false일 때만 보인다. 1건 이상 사용자에게는 결과가 현행과 같다(경고가 수백 ms 늦게 보임).
2. **감지 토큰은 3개로 축소**: `barcelona`(Threads), `daumapps`(다음), `band\/`(밴드). `kakaostory`·`snapchat`은 국내 유입 채널 근거가 없어 뺀다.
   - 음성 샘플 UA를 테스트에 고정한다: iOS·Android의 Chrome·Safari·삼성·웨일·Edge·Firefox, 그리고 PWA standalone.
   - 실기기 UA를 수집하지 못하면 알려진 한계로 적는다(C9).
3. **0건 헬퍼**: `hasAnyAssets(data)` 1개를 lib/asset에 두고, 이번 diff가 닿는 `page.tsx`·`use-share-artifacts.ts`·`preview-gate.tsx`(#59 재사용)만 교체한다. `asset-data-context`는 건드리지 않는다(요청 외 변경 금지, 회귀 범위 최소).
4. **완료 기준 5 수정**: "`secretasset_assetData` 키가 생기지 않는다" → "인앱 0건 웰컴에서 모든 진입점을 눌러도 자산 0건이 유지된다". 부트스트랩이 빈 기본값을 저장하는지에 따라 거짓 FAIL이 날 수 있다. 이 부분은 qa가 확인한다.
- 추가 완료 기준: 1건 이상 + 인앱(카톡 UA)에서 로드 전 순간에 웰컴·경고 문구가 모두 보이지 않고, 로드 뒤 현행 게이트가 보인다.

## 3. 범위 동의
- `go` → `useExternalMove` 훅 추출(게이트·웰컴 단일 구현), `InAppExternalGuide` 재사용, 신규 GA 없음. 모두 동의한다.
- 1건 이상 Threads·밴드 인앱 사용자는 이번 릴리스부터 게이트를 보게 된다. 이는 의도된 보호다. PIN 이동 경로가 이미 있어 데이터는 옮겨진다. 앱 공지는 불필요하다고 본다.
- 문구의 "[대표 동의 대기]" 표기는 지운다. 대표가 중간 판단을 하지 않으므로 팀이 확정하고, 최종 확인은 반영 결정으로 갈음한다. "입력한 내용이 사라질 수 있어요"는 기존 게이트 근거와 같은 사실이다.

## 4. 5개 질문
1. 꼭 해야 하나: 채널(Threads 매일, 카페)은 링크가 인앱으로 열린다. 지금은 0건 방문자도 첫 화면을 보기 전에 전부 차단된다. Threads는 감지되지 않아 인앱에서 등록하면 유실될 수 있다. 유입 손실과 유실 위험을 동시에 줄인다.
2. 더 작게: 조건 2(토큰 축소), 조건 3(교체 범위 제한).
3. 합치기: 외부 이동 로직을 훅 1개로 합치고, 인앱 슬롯이 등록 CTA를 대체한다(공존 금지). 동의한다.
4. LEARNINGS·DECISIONS: 새 진입점이 아니라 기존 웰컴 슬롯 상태를 하나 추가하는 것이라 충돌이 없다. #48 퍼널 영향은 변경 날짜를 기록해 보정한다.
5. 익명 측정: `welcome_view{inapp}` 기기 대비 `pwa_install{inapp_move}` 기기 비율로 잰다(기존 이벤트).
