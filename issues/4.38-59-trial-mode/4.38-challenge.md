작성: cto, 2026-10-31. 기준 코드 issue-4.37 e4f27c6(main 75f9b04와 같은 내용). 대상: 4.38-direction.md, 4.38-spec.md(초안)

## 판정: `축소` — 위험 등급 `high`
방향(웰컴에서 예시 금고 탐색, 저장 0)은 유지한다. 다만 **진입 방식을 "실행 중 localStorage 교체"에서 "부팅 시 격리 게이트"로 바꾸고** 아래 범위를 줄인다. spec·tech-review에 반영되면 재검토 없이 통과로 처리한다.
절차 메모: 사업 절이 비어 있고 spec이 challenge보다 먼저 작성됐다(#57과 같은 순서 문제). 합의 절은 축소 반영과 함께 완료한다.

## 1. 위험 등급: medium(초안) → high
- WORKFLOW 6장 기준 high에 해당한다. 앱 전체의 저장소 접근(51개 파일, setItem·removeItem 직접 호출)을 바꿔치기하고, 동기화 활성 판정(`isCloudSyncEnabled`)을 바꾸기 때문이다. "애매하면 높은 쪽" 규칙도 같은 결론이다. 같은 성격의 선례인 #31 preview 게이트도 초안이 high였다.
- 스키마·키를 바꾸지 않으므로 마이그레이션은 필요 없다. 다만 아래 S1의 실패가 일어나면 **실제 기기 데이터가 삭제**된다. 그래서 high로 둔다.

## 2. 코드 사실 확인 (spec 11절 확인 필요 항목)
- zustand `persist`는 0건이다. `profit-basis-store`는 마운트 후 effect에서 읽는다. 모듈 최상위에서 localStorage를 읽거나 참조를 붙잡아 두는 코드도 0건이다(grep). **모듈 로드 시점에 원본을 캡처하는 문제는 현재 코드에 없다.**
- 데모를 넣는 `applyImportedPayload`는 내부에서 `clearAssetData()`를 호출한다. 이 함수는 `Object.keys(localStorage)` 가운데 `secretasset_*` 키를 keep 목록만 빼고 전부 지운다(asset-storage.ts 402~438).
  - 이 때문에 메모리 Storage는 **키가 `Object.keys`로 열거돼야 한다.** Map 내부 필드만 쓰는 클래스로 구현하면 정리 함수가 아무 키도 찾지 못한다.
  - 격리가 새면 원본 삭제로 이어지는 경로가 바로 이것이다.
- `PreviewGate`는 `AssetDataProvider` 바깥에 있고, 주입이 끝날 때까지 children을 렌더하지 않는다(preview-gate.tsx 10행 주석, layout.tsx 63). spec은 이를 "재사용 불가"로 적었다. 하지만 **패턴 자체는 재사용할 수 있고, 아래 대안 B의 근거다.**
- `initAndSync`는 `isBackgroundWorkBlocked`를 거친다(asset-data-context 869). 차단 지점을 한 곳에서 관리하는 설계는 사실과 맞다. 타 탭 `storage` 이벤트는 `getAssetData()`를 다시 읽을 뿐이라 체험 탭에서는 해가 없다(1024·1173).
- sessionStorage는 격리되지 않는다. home-tip 세션 닫기, app-lock 세션 키가 여기에 해당한다. 체험 중 팁을 닫으면 같은 탭에서 종료한 뒤에도 그 세션 동안 닫힌 상태로 남는다. 데이터 손실이 아니므로 알려진 한계로 둔다.

## 4. 대안 비교
| 안 | 방식 | 판정 |
|---|---|---|
| A (spec) | 웰컴에서 실행 중 `defineProperty` 교체 → 마운트된 provider에 주입 → 종료 시 복구 후 reload | S2·S4를 구조적으로 안고 있다. provider·store를 각각 다시 초기화해야 해서 누락 위험이 크다 → **채택 안 함** |
| **B (권고)** | 링크가 `/?trial=1`로 이동한다(새 URL 허용, DECISIONS 2026-10-31 ③). 운영용 `TrialGate`를 PreviewGate처럼 provider 바깥에 둔다. 게이트 순서: S3 판정 → 메모리 Storage 설치 → 검증 4종 → `materializeDemo`+`applyImportedPayload`(메모리) → 쿼리 제거 → children 렌더. 새로고침하면 쿼리가 없으므로 실제 화면이 된다. 종료는 `location.assign("/")`이다 | provider가 처음부터 메모리만 읽는다. 복구 코드가 없다. PreviewGate 패턴(`resolvePreviewAction`·`stripDemoQuery`)을 재사용한다. 덤으로 홍보 글에서 체험으로 바로 연결할 수 있다(v1 범위 아님) |
| C | 격리 라우트 `/trial` + 별도 provider 트리 | 51개 파일이 localStorage를 직접 호출하므로 저장소 격리는 결국 필요하다. B보다 안전하지 않고 라우트만 중복된다 → 기각 |
| D | 저장소 어댑터를 주입하도록 리팩터링(컨텍스트 주입) | 가장 깨끗하지만 51개 파일 리팩터링이라 회귀 범위가 크다. 이번 범위 밖 |

B의 필수 조건은 두 가지다.
- (a) **`?trial=1`이 없는 일반 방문자의 첫 렌더 지연·빈 화면이 0이어야 한다.** PreviewGate처럼 init 단계에서 children을 숨기는 동작을 운영 전체에 적용하지 않는다. 쿼리가 있을 때만 게이트가 동작한다.
- (b) TrialGate의 운영 번들 크기 증가를 최소화한다. demo-data는 지금처럼 동적 import로 둔다.

## 5. 축소 범위
1. 진입은 B로 한다. 종료 시 "원본 복구" 단계를 삭제한다(spec 4·5.2·5.4).
2. **GA 허용 목록을 없앤다.** 체험 페이지에서는 `track`·`trackScreen`·`setUserProps`를 전부 끈다. 진입 이벤트 `feature_use{demo}`는 실제 페이지에서 이동 직전에 보낸다(beacon 전송). 종료 이벤트 `onboarding_action{trial_start}`는 복귀한 실제 페이지에서 sessionStorage `trial_exit`를 읽고 보낸다. 이렇게 하면 ga.ts에는 체험 여부 1줄만 들어간다. `welcome_view` 재전송 억제는 뺀다(기기 단위 집계라 영향 없음).
3. 쓰기 진입점은 "읽기 전용 완전성"이 아니라 **외부 전송 진입점만** 숨긴다. FAB(스크린샷 인식·Gemini 호출), 더보기(공유·피드백·동기화), 설정이 대상이다. 상세 행 편집은 메모리 안에서만 일어나고 새로고침하면 사라지므로 허용한다. spec 11절의 "읽기 전용 완전성" 조사는 삭제한다.
4. `isCloudSyncEnabled() && !isTrialMode()` 가드는 유지한다. 메모리에 sync 상태가 없어 사실상 이중 안전장치이며, 1줄이다.

## 6. 완료 기준 추가·수정
- 추가: S1 모킹(defineProperty 무시, 전역 식별자 불일치 각각)에서 `clearAssetData`가 원본에 호출되지 않고 원본 키·값 해시가 같다.
- 추가: 원본에 자산 1건/sync assetId/pwa_auth가 있으면 `/?trial=1`이 일반 화면으로 열리고 원본이 변하지 않는다.
- 추가: `?trial=1`이 없을 때 렌더 결과·지연이 main과 같다(게이트 미동작).
- 수정: 완료 기준 5는 "체험 페이지 gtag 호출 0건"으로 바꾼다. 실제 페이지 진입·복귀 이벤트는 각 1건이다.
- 알려진 한계(C9): iOS Safari·WKWebView·삼성 실기기에서 defineProperty가 실제로 동작하는지는 검증할 수 없다. 검증 4종이 fail-closed로 막고, 실패하면 체험이 열리지 않는다(데이터 무접촉).
