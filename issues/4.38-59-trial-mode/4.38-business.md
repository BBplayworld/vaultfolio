# 4.38 business — 체험 모드(#59) · 인앱 도착 개선(#60) · 보안 안내 정정(#61)

작성: business-pm, 2026-10-31. 상태: planning ②. 3개 이슈를 한 릴리스(4.38) 단위로 묶어 1쪽으로 정리. 에이전트는 GA 조회 불가 — 수치는 대표 제공값, 아래 산식 입력은 모두 가정.

## 1. 누구의 문제
- 대상: 엑셀·노션으로 자산을 정리하던 3040 주식 투자자 중 처음 온 사람(자산 0건).
- #59: 스크린샷을 올리기 전에 "내 것이 되면 어떤 화면인지" 만져볼 수 없다. 웰컴 미리보기는 정적이다.
- #60: 카페·카톡·Threads 링크가 인앱으로 열리면 자산 0건이어도 앱을 보기 전에 전체 차단된다. 감지 누락 인앱은 입력 후 유실 위험.
- #61: 앱 안 보안 문구가 실제 동작과 달라(단정·"절대") 대표의 보안 메시지 기준과 어긋난다.

## 2. 월 활성 기여 가설과 산식 (보수적, 표본 작음)
전제: 웰컴 조회 7기기/13일 → 월 약 15기기. 이 값으로 비율을 곱하는 것 자체가 표본 7의 외삽이다(0/7의 95% 상한 약 35%). 방향만 말한다.

| 이슈 | 산식 | 월 기여(Δ첫 등록 기기) | 병목 |
|---|---|---|---|
| #59 | 15 × 진입 20~40% × 체험 후 시작 15% = 0.45~0.9 | **+0.5~1** | 전환 |
| #60 | 인앱 신규 월 2~5(가정, 유입 17의 10~30%) × 이동 성공률 증가분 15%p = 0.3~0.75 | **+0.3~0.8**(이동 기준, 등록은 그보다 작음) | 첫 발견 |
| #61 | 직접 기여 가설 없음 | **없음**(신뢰 정정) | 해당 없음 |

- 합계 보수 +1 안팎. 100명 목표의 1% 수준이며 이 릴리스 단독으로 목표에 닿지 않는다. 숫자를 부풀리지 않는다.
- 근거가 이슈별로 약하다: #59는 후보 4와 같은 "가치를 모른다" 가설(원인 미구분), #60은 인앱 비율 미확인.
- 구조 효과: #59+#60은 인앱 방문자가 "등록은 막히지만 가치는 본다"가 된다. 채널(마케팅 주 7건)을 키울 때 누수를 막는 선행 정비라는 점이 핵심 가치.

## 3. 지표와 가드레일 (익명 기기, 기존 GA 위주)
| 지표 | 정의 | 목표(8주) |
|---|---|---|
| 체험 진입률 | `feature_use{demo}` 기기 ÷ `welcome_view` 기기 | ≥ 20% (10% 미만이면 링크 위치 재검토) |
| 체험 후 시작 | `onboarding_action{trial_start}` 기기, 그중 `first_asset_saved` | 시작 ≥ 2, 등록 ≥ 1이면 방향 확인 |
| 인앱 이동 | `pwa_install{method:inapp_move}` 기기 ÷ `welcome_view{source:inapp}` 기기 | ≥ 20% (정성 병기) |
| 인앱 규모(사전) | 사용자 속성 `app_mode=inapp` 신규 기기 수 — 대표 1회 조회 | 월 2 미만이면 효과 판독 포기 |
- 가드레일: ① 체험 중 `settlement_view`·`ai_prompt`·`asset_count_bucket` 변화 0(#51·#54 판독 보호). ② welcome→onboarding_action 기존 14%(1/7) 미악화. ③ 인앱 0건에서 `secretasset_assetData` 생성 0, 정상 브라우저 오탐 차단 0. ④ 체험 격리 후 원본 저장소 키 변화 0.
- 코호트 기록: 머지일을 #48 웰컴 퍼널 경계로 기록(대표 10/31 오염 감수). 인앱 이동 시 외부 브라우저에서 새 기기로 집계되어 first_visit이 중복될 수 있음 — 신규 유입 해석 때 `inapp_move` 기기 수만큼 보정.
- 판독 한계: 체험 중 GA 억제로 체험 시간·화면은 측정 불가. 판독은 대표 공유 수치 또는 8주 경과 정성 판정.

## 4. 위험
- #59 데이터 안전(최우선): 전역 localStorage 교체 방식이라 iOS Safari·WebView에서 격리 실패 시 실데이터 혼입 위험. fail-closed 검증이 실기기에서 통과하지 않으면 #59는 출시하지 않는다(월 +1 대비 위험 비대칭). 이 경우 #60·#61 분리 반영 여부는 cto 판단.
- #60 오탐: 일반 브라우저를 인앱으로 오판하면 사용자 차단. 실 UA 샘플 확정 전 정규식 추가 금지.
- #61 SEO: 메타 title 변경은 노출 영향, 대표 확인 필수. 신 문구도 단정 재발 위험(spec 카드2·PRINCIPLES 제안문 이견은 direction 합의 절).
- 일정: 11/26 qa PASS 불발 시 결산 창(11/27~12/10) 동결, 12/11 이월. 결산 화면·홈 팁 무접촉.
- 효과 위험: 유입 월 약 17기기라 8주에도 표본이 한 자릿수 — 지표 미달을 실패로 단정하지 않는다.

## 5. 마케팅 활용 (qa PASS·반영 후, 초안까지, 게시는 사람)
- #59: Threads 1건 "스크린샷 올리기 전에 예시로 먼저 둘러볼 수 있어"(예시 데이터·저장되지 않음 명시, 새 URL 없이 사이트 메인 안내), 블로그 검색형 1건("엑셀 대신 자산 정리 앱 가입 없이 미리 써보기" 류). 카페는 월 1회 결산 연재만, GeekNews 쓰지 않음(큰 출시 아님).
- #60: 별도 홍보 없음. 출시 후에야 카페·Threads 링크 클릭이 의미 있어지므로 UTM 규약을 이 시점에 적용.
- #61: 정정 자체는 홍보하지 않음. 보안 문구는 대표 기준만: ① 자산 정보는 서버에 저장되지 않고 기기에 저장(동기화를 켜지 않는 한) ② 기기 동기화는 이중 암호화로 관리자도 알 수 없음. "서버는 ~만 한다"·"서버로 아무것도 안 간다" 단정, 서버 역할 나열 금지. 필요 시 블로그 검색형 1건("로그인 없는 자산 관리, 내 데이터는 어디에 저장되나").
- 공통 규칙: 금액·투자 조언 없음, 반말 축약형, "안전한 자산 관리, 시크릿에셋"으로 마무리, 실제와 다른 기능 설명 금지(체험은 예시 데이터이며 저장되지 않음을 숨기지 않기).

## 6. 대표 판단 포인트
1. 월 +1 안팎의 작은 기여를 알고도 #59(위험 medium, 전역 객체 교체)를 진행하되, **실기기 격리 검증 실패 시 출시 보류**에 동의하는지, 그때 #60·#61 분리 반영 허용 여부.
2. GA에서 `app_mode=inapp` 신규 기기 수 1회 조회(#60 규모 확인).
3. #61 대표 동의 대기 문구 전부 + PRINCIPLES 2장 문안. 문안은 "서버는 자산 내용을 알 수 없다" 대신 "동기화한 자산은 이중 암호화돼 관리자도 알 수 없다"로 범위 한정, 스크린샷 분석·실거래 조회 서버 경유 사실 반영 여부. 메타 title 변경 여부.
