## 2. 짝 id 규칙 — 조회 정본 1곳 (`linked-record.ts`)
- `cashLinkId(txId)=ctx_link_<txId>`, `loanLinkId(txId)=ltx_link_<txId>`. txId는 `tx_…`/`crtx_…` 그대로(예 `ctx_link_crtx_1731…_ab12c`).
- `linkedTradeIdOf(rec)`: id가 접두어로 시작하면 나머지 = 거래 id, 아니면 null. `findLinkedRecord(data, txId)`: cash→loan 순 조회(해당 id 1개 or null). `buildLink(...)`(기록+잔액 patch 생성)·`removeLink(data, txId)`(기록 삭제 + 잔액 역가감, 기존 삭제 UI와 같은 `Math.max(0, …)`). 모든 호출부(폼·삭제·결산·홈·테스트)는 이 파일만 import, 접두어 문자열 직접 사용 금지(lint 대신 테스트에서 grep 단언).
- 충돌 없음 근거: 기존 생성 id는 `ctx_<숫자>`(cash-tx-input:98, asset-storage:955 토큰 복원), `ltx_<숫자>`, 데모 `demo_ctx_*`. `link_`는 숫자 아님 → 기존 데이터에 접두어 일치 0.

## 5. 결산·홈 id 짝 4종 (추정 규칙 불변)
- `matchRecordedTransferDetail`(change-hero.tsx:179) 앞단에 **1단계 id 짝**을 추가: 구간 `(from,to]` 안 반영 기록 중 `linkedTradeIdOf`로 거래와 짝이 확인되는 쌍만 — 현금 출금↔매수, 현금 입금↔매도, 대출 증가(borrow)↔매수, 상환(repay)↔매도. 금액 = `min(기록 금액 환산, 거래 금액)`, 쓴 만큼 양쪽 `left`에서 차감 후 **2단계(기존 ±3일 추정 코드 한 글자 변경 없이)** 가 남은 몫으로 동작. 입금↔매도 **추정 짝은 만들지 않음**(prep-103-b-settlement 폐기 사유). 반환형: `in`은 id 짝 입금↔매도만 채움, 대출 짝은 `viaLoan:{buy,sell}`(stock/crypto)로 분리 — 현금을 거치지 않으므로 `matchedTransfer`가 아니라 홈 헤더 상쇄와 `withLoanCause`의 `debtIncrease`/상환 쪽에서 짝 금액만큼 제외(개발 첫 작업: 현재 엔진이 대출로 매수 픽스처를 어떻게 분해하는지 측정 후 확정).
- `matchRecordedTransfers` 래퍼 = `out 합 − in 합`. `settlement.ts:224` 가드 `> 0` → `!== 0` + 주석(입금 짝만 있는 달이 음수라 무시되는 문제). 기존 데이터는 `in=0, out≥0`이라 가드 변경은 동작 동일.
- **과거 결산 diff 0 증명**(C8·C21): (1) 구조: id 짝 단계는 `ctx_link_`/`ltx_link_` 기록이 있어야 활성, 기존 데이터엔 0건 → 2단계만 실행 = 현행 코드 경로. (2) 현행 `matchRecordedTransferDetail`을 테스트에 `legacyMatch` 사본(골든)으로 박제 후, 무작위 AssetData 수백 건(링크 id 없음)에서 신/구 `detail`과 `computeSettlementCauses` 전체 출력 deep equal (속성 테스트, 고정 seed). (3) `demo-data.json`·기존 `settlement-flows`·`settlement`·`physical-*`·`cross-asset-flow` 테스트 **파일 수정 0**으로 통과(수정이 필요해지면 diff 발생 신호). (4) 신규 링크 데이터 픽스처는 신규 파일에만, 기대값 선기재. 항등식(원인 합 = Δ순자산) 단언.
- 한 쌍이 구간 경계에서 갈라지는 경우: 두 기록은 거래일 = 같은 날짜로 생성되고 수정 UI 없음 → 같은 구간. 시작일 제외(C15) 경계 테스트 포함.
- 홈: `dashboard.tsx:496` 호출은 detail 확장만 전달(인자 불변). 토스트 `현금도 맞추기`(3-T) 넣지 않음. 캡션은 컷 1순위.
