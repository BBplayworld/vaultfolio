# 4.xx #45 백업 JSON·공유 이미지 저장 iOS 신뢰 — direction

## 사업

### 1. 왜 지금
- 기여 축: **리텐션(신뢰)**. 첫 발견에는 기여 없음. 로컬 저장이 핵심 강점 2인데, 백업이 안 됐는데 "백업함"이 남으면 기기 분실·초기화 때 복구 불가 → 사용자는 영구 이탈한다. 50명 단계에서 한 명의 데이터 손실은 입소문 손실로 이어진다.
- 대표 사용 환경(iOS 웨일)에서 .ics가 같은 원인(blob + download)으로 이미 실패한 이력이 있다(LEARNINGS 2026-10). 같은 실수의 재발 방지다.
- v4.34 월말 결산으로 "돌아올 이유"가 생긴 직후라, 돌아온 사용자의 데이터가 안전하다는 신뢰가 먼저 맞아야 한다.

### 2. 누구를 위해
- 엑셀·노션 대신 시크릿에셋에 자산을 옮겨 적은 3040 투자자 중 **iOS 서드파티·인앱 브라우저 사용자**(웨일·크롬 iOS 등). 로그인이 없어 백업 JSON이 유일한 복구 수단인 사람. 데스크톱 사용자의 취소·차단 케이스도 같은 결과라 함께 해소된다.

### 3. 성공의 모습 (익명 기기 기준, 기존 GA 이벤트)
1. **내보내기 성공 기록의 정직도**: `data_action{method:export, source:more|home_tip}`의 result 비중(success / fail / blocked). 수정 후 실패·차단이 정직하게 잡히면 fail+blocked 비율이 0보다 커지는 것이 정상이다(이전엔 항상 success). 기기·브라우저 분리는 GA 기본 차원(기기 범주·브라우저·OS)을 쓴다.
2. **재시도 후 완료**: 같은 기기(GA 익명 클라이언트 ID)에서 `export` fail 뒤 같은 세션 내 `export` success 발생 비율. 백업 안내 오꺼짐은 자동 테스트(실패 시 `lastBackupAt` 불변)로 확인하고 운영 지표로 삼지 않는다.
- 공유 PNG 저장은 `share{method:save}`에 result가 없어 성공/실패를 구분할 수 없다. 측정하려면 result 파라미터(기존 사전의 success/fail) 추가가 필요하다. 신규 이벤트·파라미터 추가가 아니라 기존 사전 값 재사용이므로 developer 판단 사항으로 남긴다.
- 사용자 자산 값은 전송하지 않는다(enum만). 로컬 저장·E2EE 원칙 불변, 서버 경유 다운로드 금지.
- 한계: 표본이 작아(월 50명) 비율은 방향 확인용이다. iOS 실기기 동작은 자동 검증 불가.

### 4. 하지 않으면 무엇을 잃나
- iOS 서드파티 사용자의 백업이 조용히 실패하고 안내까지 30일간 꺼진다. 복구 파일 없이 기기를 바꾸는 순간 기록 전체를 잃을 수 있다(회복 불가능한 이탈). 근거 강함(qa 결함 확정 D2, 기존 데이터 손실은 없음).
- 공유 PNG는 저장 안 됐는데 성공 표시. 근거는 중간(사용자 불편, 데이터 손실 아님). 이탈 영향은 백업보다 약하다.
