## 1. 저장 위치: 분리 키 채택, 단 이름은 `secretasset_` 접두 밖 (정정)
**사실 확인**
- 구버전 `clearAssetData()`(asset-storage.ts:407~445)는 `Object.keys(localStorage)` 중 `secretasset_`로 시작하는 키를 keep 목록만 남기고 **모두 지운다**.
- 이 함수는 동기화 pull, 백업 가져오기(`applyImportedPayload:341`), 데모 주입에서 매번 호출된다.
- 그래서 spec이 제안한 `secretasset_physical_assets`는 다음 경우에 지워진다.
  - 롤백된 구버전 기기의 **첫 pull 또는 가져오기**
  - 동기화 사용자는 앱을 열 때마다 pull한다
- spec이 비교한 "assetData 안 배열"(첫 `saveAssetData` strip에 유실)과 실질 차이가 거의 없다.

**판정**
- 분리 키를 쓰되, 키 이름이 `startsWith("secretasset_")`에도 `STORAGE_KEY_PREFIXES`에도 걸리지 않게 한다. 이름은 tech-review가 정한다.
- 이렇게 하면 구버전의 다음 경로가 모두 이 키를 건드리지 않는다.
  - `clearAssetData`
  - `clearUserCaches`
  - `migrateStorageKeys`
  - one-time-migrations: 키 순회 6곳을 grep으로 확인함
- 신버전에서 책임질 일:
  - ① "모든 데이터 삭제"에서 명시적으로 지운다(`backup-status.ts:106` 패턴)
  - ② `applyImportedPayload`·`applySharedData`·데모 주입의 교체 의미를 아래 2절대로 처리한다
  - ③ `storage-stats`에 이 키를 집계한다
- 알려진 한계: 구버전에서 "모든 데이터 삭제"를 하면 이 키가 남는다. 그 상태로 신버전에 재진입하면 실물 자산이 다시 보인다. 롤백 기간에만 생기는 일이라 브리프 위험 절에 적는다.

## 2. 경로별 계약 (spec 3-5 보완)
| 경로 | 계약 |
|---|---|
| 동기화 pull | spec 1·2 동의. 원격 `assetData.physicalAssets` 키가 없으면 로컬을 유지한다. 키가 있으면 `mergeById`를 적용한다. 키가 없는 payload의 `remoteIds`에는 실물 id를 넣지 않는다 |
| 구버전 기기의 pull | `assetDataSchema`는 zod 기본 strip이라 오류 없이 실물 자산만 버린다. 이후 push에는 키가 없으므로 위 계약으로 보호된다(C5·C13 순환 테스트) |
| 백업 가져오기 | 키가 없으면(구 백업) 로컬을 유지하고 토스트 1줄을 띄운다. 이것을 채택한다(기록 손실 0 우선). 키가 있으면 교체한다 |
| **공유 링크·복원 코드(packV7)** | 이 토큰은 Safari→PWA 이전용 "복원 코드"(`importSharedByCode`)이기도 하다. v1에서 토큰에 넣지 않는다면 ① 코드 생성 시 실물이 1건 이상이면 "실물 자산은 복원 코드에 포함되지 않아요. 백업 파일을 써 주세요" 1줄 ② `applySharedData`는 교체 의미에 맞춰 로컬 실물을 비운다(남의 데이터와 섞이지 않게). 받는 쪽 순자산이 보낸 쪽보다 작아지는 것은 알려진 한계로 둔다(공유 사용 0건). 토큰 포맷 변경(C7)은 하지 않는다 |
| 월 스냅샷 병합 | spec 5에 동의한다(같은 달에 로컬 `physical > 0`이고 수신값에 필드가 없으면 로컬 유지) |
| **일별 스냅샷** | v1 제외(축소). 현재 pull은 일별을 통째로 교체한다(`:358`). 병합을 새로 만들면 범위가 커진다. 구버전 기기가 쓴 날의 일·주 그래프가 실물만큼 내려가는 문제는 SW 갱신 지연·롤백 기간의 알려진 한계로 둔다 |
| 체험 거부(C28) | `trialRejectReason`(trial-boot.ts:66)은 assetData 키만 본다. 새 키에 1건 이상 있으면 거부하도록 한다 |

## 3. 줄일 것
- `quantity`·`unit` 선택 메타는 v1에서 뺀다. v2 시세 연동 대비용이라 지금 쓰는 곳이 없다.
- 대신 앞으로의 하위 호환을 위해 두 가지를 정한다.
  - **`physicalAssetSchema`는 `.passthrough()`**로 두어, v4.40 기기가 미래 필드를 저장 중에 지우지 않게 한다.
  - **`type`은 모르는 값을 `other`로 읽는다.** v2에서 유형을 추가해도 v4.40 기기의 pull이 parse 오류로 실패하지 않게 하기 위함이다. 유형 5개는 라벨만 다르므로 유지한다.

## 4. 결산·원인 매핑 정정 (C21·C23·C24)
**완료 기준 7의 기대값은 현재 매핑과 다르다.** `mapSettlementCauses`(settlement.ts:209)에서 `TRADE_KEYS`는 현금 등록 사용자에게 내부 이동 풀이다. 맞은편에 반대 부호의 현금 변화가 없으면 "기록 안 된 변화"로 남는다. 패턴별 기대값을 아래로 바꾼다.

| 패턴 | 기대값 |
|---|---|
| ① 오래전 산 금을 처음 등록(현금 등록 사용자) | 기록 안 된 변화 +X. 기존 InfoHint "새로 등록한 자산이나…"로 설명된다(C24 충족). 부동산과 같다 |
| ② 같은 상황, 현금 미등록 사용자 | 순유입 +X. 부동산과 같은 규칙이다. COO 관점에서 어색하지만 기존 규칙을 따른다. "등록일 분리" 후보(STATE)에서 함께 다룬다 |
| ③ 현금 잔액을 직접 줄이고 금 등록 | 풀 G(+X)와 C(−X)가 상쇄되어 0이 된다 |
| ④ **기록된 출금 → 금 등록(±3일)** | 지금 매핑으로는 순유입 −X / 기록 안 된 변화 +X로 두 다리가 갈린다(C23 위반). `matchedTransfer` 짝짓기 대상에 "구간 안 `purchaseDate`가 있는 실물 신규분"을 추가한다(±3일·금액 min, 기존 규칙 재사용) |
| ⑤ 평가액만 수정 | 평가 갱신 ±Δ다. "평가 갱신"은 부동산과 한 항목으로 묶는다. 결산 항목은 늘리지 않는다(대표 2026-10-29 과도 분할 금지). 자산 변화 원인 상세에서만 `price:physical` 행을 따로 둔다 |

- 결산 화면 컴포넌트·라벨은 무변경이다. 엔진 키 매핑과 짝짓기 함수만 바뀐다. 매핑 표에 거래 다리별 목적 항목을 적는다(C23).
