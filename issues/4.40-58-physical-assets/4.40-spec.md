# #58 실물 자산 등록 — 금 등 — spec

상태: planning ② 초안(planner-designer, 2026-11-01) — 사업 절 합의 후 확정. 코드는 12/11 이후 / 근거 코드: main 5eebe74
위험 등급: **high** (assetData 스키마 + 저장 + 동기화 병합 + 스냅샷·결산 매핑)

## 1. 문제
자산군이 부동산·주식·코인·현금·대출 5종뿐이라(`types/asset.ts` `assetDataSchema`) 금 같은 실물 보유분은 현금·부동산 "other"로 위장 입력하거나 빠진다. "내 자산을 정확히 아는 상태"(PRINCIPLES 1장)에 구멍이 있다.

## 2. 목표 행동
실물 자산을 1건 이상 등록하고, 평가액을 고친 달의 결산에서 그 변화가 "평가 갱신"으로 분류된다. 혼재·롤백에서도 실물 자산이 남는다.

## 3. 범위
### 3-1. 유형(5)
`gold` 금 · `silver` 은 · `jewelry` 귀금속·보석 · `collectible` 수집품·미술품 · `other` 기타 실물. (차량·보험환급금·전월세 보증금 제외 — 대표 2026-11-01)

### 3-2. 입력 방식 비교와 권고
| | 부동산(현행) | 코인(현행) | 실물 권고 |
|---|---|---|---|
| 저장 정본 | `purchasePrice`·`currentValue`(원, 수동, 필수>0) | `quantity`×`currentPrice`(시세 자동, `baseDate`) | **평가액 방식**: `purchasePrice`·`currentValue` |
| 시세 | 실거래 추정은 보조(`marketEstimate*`, 파생) | 업비트 시세가 정본 | v1 없음 |
| 결산 | `breakdown.realEstate`·`cost.realEstate` 차이 → `price:realEstate`(평가 갱신)/`buy·sell:realEstate`(`asset-report.ts:696-746`) | 시세 효과 | 부동산 경로와 동형 |

권고 근거: ① v1은 시세가 없어 수량×단가로 받아도 사용자가 단가를 매번 고쳐야 해 수고가 같고 입력 칸만 늘어난다. ② 보석·수집품은 수량×단가가 성립하지 않는다 → 유형 공통 분모는 평가액. ③ 부동산과 같은 형태라 `computeNetAsset`·스냅샷·결산 매핑을 같은 패턴으로 재사용한다. 수량·단위(`quantity?`, `unit?: "g"|"don"|"oz"|"ea"`)는 **선택 메타**로만 저장해 v2 금 시세 연동(코인 `positionSource`처럼 계산 전환) 대비. 폼의 "수량×단가로 계산" 보조는 줄일 수 있는 것.

### 3-3. 자료형 (제안)
`physicalAssetSchema = { id, type(enum 5), name(필수), currentValue(>0 필수), purchasePrice(≥0, 비우면 저장 시 currentValue로 채움 → 수익 0), purchaseDate(필수, 결산 유입 판정), quantity?, unit?, description? }`. `assetDataSchema.physicalAssets: z.array(...).optional()` — **`.default([])` 금지**(키 부재와 빈 배열을 구분해야 3-5가 동작. 현행 `cash`·`loans`는 default([])라 이 구분이 없다).

### 3-4. 저장 위치 (권고: 분리 키 + 메모리 병합)
- 사실: 구버전 코드는 `assetDataSchemaLoose.parse`(zod 기본 strip)로 읽고 `saveAssetData`가 검증본을 쓴다(`asset-storage.ts:111,121-123`) → `assetData` 안에 새 배열을 두면 **구버전으로 롤백한 기기가 첫 저장 때 실물 자산을 지운다**.
- 권고: localStorage는 새 키 `secretasset_physical_assets`(값 = 배열 JSON)에 따로 저장하고, `getAssetData`가 읽을 때 `physicalAssets`로 합쳐 메모리·Context·동기화·백업 payload에서는 `assetData.physicalAssets`로 다룬다. 구버전은 새 키를 모르므로 롤백해도 남고, 재업데이트 시 다시 보인다.
- 대안(비권고): `assetData` 안에 저장 — 구현은 작지만 롤백 유실을 막을 수 없다(브리프에 "롤백 금지, 수정 배포" 명시 필요).
- tech-review 판정 필요: 분리 키 채택 여부, `saveAssetDataRaw`(`:396`)·`trial-boot.ts:68`·`clearAssetData` 목록(`:407`)·`itemCountFingerprint`(`:160`) 반영.

### 3-5. 데이터 안전 계약
1. **키 없으면 로컬 유지**: 동기화 pull(`applyImportedPayload`, `syncedIds` 있음)에서 원격 `assetData.physicalAssets` 키가 **없으면**(구버전 기기가 push) 로컬 배열을 그대로 둔다. 키가 있으면 `mergeById`로 기존 규칙(신규 보존·삭제 존중)을 적용.
2. `collectAssetIds`(`:197`)·`reconcileAdditiveMerge`(`:228`)에 실물 배열 추가. 단 키 부재 payload의 `remoteIds` 계산에는 로컬 실물 id를 넣지 않는다(다음 pull이 삭제로 오판하지 않게).
3. 파일 가져오기(백업 복원): 키 있으면 교체, **키 없으면(구 백업) 로컬 유지**(데이터 보존 우선). 복원 완료 토스트에 "실물 자산은 기존 값을 유지했어요" 1줄. cto 판정 대상.
4. 스냅샷: `SnapshotBreakdown.physical?`·`SnapshotCost.physical?` optional(`tenantDeposit` 선례). 필드 부재 = 0으로 읽는다(기능 이전 스냅샷은 실제로 0이므로 참).
5. 월 스냅샷 병합(`mergeMonthlySnapshots`, `:290`): 같은 달에서 로컬 `breakdown.physical > 0`이고 수신값에 필드가 없으면 로컬을 유지(구버전 기기가 실물 빠진 순자산으로 덮는 것 방지). 일별도 같은 규칙.
6. `hasAnyAssets`(`:67`)·`countAssets`(GA)·`trial-boot` 자산 보유 판정에 실물 포함 — 실물만 가진 기기가 웰컴을 다시 보거나 체험 모드가 열리지 않게.
7. 마이그레이션: 기존 데이터에는 키가 없으므로 변환 없음. 복원 테스트 필수(10절).

### 3-6. 결산·원인 매핑
- `computeNetAsset`(`asset-data-context.tsx:212`): `physicalValue` 추가, `totalValue = realEstate + physical + financial`. 실물은 **금융자산에 넣지 않는다**(`financialAsset` 정의 유지).
- 스냅샷 기록(`asset-data-context.tsx:699`, `asset-report.ts:1162`)에 `breakdown.physical`·`cost.physical`.
- 원인 효과(`asset-report.ts`): `price:physical` = Δbreakdown.physical − Δcost.physical, `buy:physical`/`sell:physical` = Δcost.physical(추정 경로는 `purchaseDate` 구간 판정, 부동산 `:556-558`과 동형). 라벨 "실물 평가 상승/하락", "실물 등록/정리". `AttributionGroupKey`에 `physical`("실물").
- 결산 매핑(`settlement.ts` `mapSettlementCauses`): `price:physical` → `valuation`(평가 갱신), `buy/sell:physical` → `TRADE_KEYS`(내부 이동 풀). 결산 화면 컴포넌트·문구는 무변경.

## 4. 사용자 흐름
1. FAB → "실물 자산" → 입력 폼(유형 칩·이름·현재 평가액·매입가(선택)·매입일·메모). 확인 = `Button variant="brand"`.
2. 저장 → 토스트, `trackAssetSave{asset_type: physical, method: manual}`(0건이었으면 `first_asset_saved`).
3. 홈: Hero 순자산에 합산, 구성 바에 "실물" 항목(부동산·금융자산과 같은 단계).
4. 상세 허브 "실물" 탭: 항목 카드(이름·유형·평가액·매입가 대비 손익), 편집·삭제.
5. 평가액 수정 → 당일 스냅샷 갱신 → 다음 결산에서 "평가 갱신"에 반영.

## 10. 완료 기준 (qa 검사 문장)
1. v4.39 형식 `secretasset_asset_data`(실물 키 없음)로 시작한 기기가 v4.40에서 기존 5종 자산·스냅샷을 그대로 보여 준다(복원 테스트).
2. 실물 1건 저장 후 `secretasset_physical_assets`에 배열이 있고, `secretasset_asset_data`에는 `physicalAssets`가 없다(분리 키 채택 시).
3. v4.40에서 실물을 저장한 뒤 v4.39 코드로 자산을 1건 저장하고 다시 v4.40으로 열면 실물이 남아 있다.
4. 구버전 payload(키 없음) pull → 로컬 실물 유지 / 신버전 payload에서 실물 삭제 → 다른 기기 pull 후 삭제 반영 / 동시 추가 → 양쪽 보존(단위 테스트, push→pull→저장→push 순환).
5. 구 백업 JSON 가져오기 후 실물 유지 + 안내 1줄.
6. 홈 Hero 순자산 = 기존 순자산 + 실물 합계, 구성 바에 "실물" 항목, 금융자산 합계는 불변.
7. 실사용 패턴 픽스처(등록 달·평가액 수정 달·변화 없는 달)에서 월 결산 원인 합계가 Δ순자산과 같고, 평가액 수정분이 "평가 갱신"에, 등록분이 "기록 안 된 변화"가 아닌 내부 이동/순유입에 들어간다(C20·C21·C24).
8. 같은 달 구버전 기기의 월 스냅샷(physical 필드 없음)이 로컬 실물 포함 스냅샷을 덮지 않는다.
9. 실물만 1건 가진 기기에서 웰컴이 아니라 홈이 뜨고, `/?trial=1`은 거부된다.
10. `src/` 전체에서 실물 관련 문구에 투자 조언 표현이 없다. 확인 버튼 brand, 320·375px 끊김 없음.
