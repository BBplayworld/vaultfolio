## 문제 (사용자 관점)
- 기기 두 대로 같은 금고를 쓰는 사람이 A 기기에서 고친 내용이, 그 사이 B 기기가 먼저 저장했다는 이유만으로 **통째로 사라진다**. B가 건드리지 않은 항목(예: 주식 수량)의 수정도 사라지고, A에서 지운 항목은 **다시 살아난다**. 새로 추가한 항목만 남는다.
- 사라졌다는 사실이 보이지 않는다. 자동 동기화는 조용히 돌고, 보이는 것은 "다른 기기의 변경을 반영했습니다." 한 줄뿐이다. 사용자는 나중에 숫자가 틀린 것을 발견하고 "내가 잘못 입력했나"로 오해한다. "내 자산을 내가 정확히 아는 상태"(PRINCIPLES 1장)와 정면으로 충돌하고, CHECKLIST 원칙상 기록 손실 가능성은 FAIL이다.
- 언제: 60초 폴링 사이에 두 기기가 엇갈려 저장할 때, 또는 오프라인에서 고친 뒤 다시 연결될 때.

## 사업 (business-pm 확정 2026-11-07 — 대리 초안 보강)
- **왜 지금**: 동기화는 핵심 강점 2번(로그인 없는 로컬 + 기기에서 암호화하는 동기화)이다. 강점이 기록을 조용히 지우면 신뢰가 깨지고, 기록 도구에서 신뢰 상실은 곧 이탈이다. 결함이 qa 재현으로 확정된 이상 미룰 이유가 없다.
  - **강점 방어 관점**: 엑셀·노션 대비 이 서비스가 내세우는 차이는 "로그인 없이도 휴대폰·PC에서 같은 숫자"다. 엑셀은 느리지만 적은 숫자가 사라지지 않는다. 동기화가 숫자를 조용히 되돌리면 엑셀보다 못한 지점이 생기고, 그 경험을 한 사람은 "내가 잘못 입력했나"로 오해한 뒤 결국 엑셀로 돌아간다. LEARNINGS(#45 반려: 내부 신뢰성은 자율 과제 주력 아님)와 구분되는 점: 이것은 추정 위험이 아니라 **재현 확정된 기록 손실**이고(CHECKLIST상 FAIL), 팀 결정(DECISIONS 11-06 #84)으로 이미 범위가 정해졌다.
- **누구를 위해**: 동기화를 켠 다기기 사용자(휴대폰+PC로 같은 금고를 쓰는 1인). 10/31 당시 구 GA(sync_enabled) '사용' 4기기 중 대표 기기 2대를 빼면 **외부 약 2기기**로 소수다. 이후 가족 공유(#57 보류)의 전제 조건.
- **월 활성 100 기여 크기(솔직히): 직접 기여 거의 없음.** 신규 유입 0, 리텐션 효과도 대상이 몇 명뿐이다. 이 과제의 가치는 성장이 아니라 **손실 방어**(강점 2의 근거 유지, 앞으로 동기화를 홍보할 때 거짓이 되지 않게 함)다. 그래서 범위는 A안(저장 형식 무변경)으로 최소화한 현행이 맞다.
- **지표**(GA 단일 규칙: page_title만, 새 맞춤 정의 0, 자산 값·건수 원값 미전송):
  - 코드 확인: 현재 자동 동기화(폴링·409 화해)는 GA를 보내지 않고, `sync_action`은 전부 "기기 동기화" 한 행으로 합쳐진다 → 기존 행만으로는 덮임 발생을 알 수 없다. 구 지표 sync_enabled는 11/06 GA 단순화로 사라져 **동기화 사용자 수 자체도 지금은 셀 수 없다.**
  - 그래서 **새 이벤트는 만들지 않고, 기존 `feature_use` 이벤트에 category 2개만 추가**해 page_title 행 2개를 둔다(#78 "설치 안내" 행과 같은 방식): ① `동기화 덮임 알림`(덮임 1건 이상 감지 시 1회) ② `동기화 되돌리기`(되돌리기 확정 시). 건수·항목은 보내지 않는다. track은 try/catch no-op이라 동기화 흐름에 영향 없음. cto·developer가 동기화 경로에 계측 호출을 넣는 것 자체를 위험으로 보면 **계측 없이 진행 수용**(판정은 qa 하네스로 충분, 아래 판독만 포기).
  - **판독(머지 후 8주, 표본 극소라 효과가 아니라 '발생 확인' 용도)**: 운영 GA에서 대표 기기는 따로 걸러낼 수 없다(익명 집계). preview는 GA가 꺼져 있어 대표의 preview 확인은 섞이지 않는다. 따라서 `동기화 덮임 알림` 활성 사용자 **0명 = 실사용 발생 미확인, 1~2명 = 판별 불가(대표 기기일 수 있음), 3명 이상 = 외부 발생 확정**으로 읽는다. `동기화 되돌리기`는 알림 대비 사용 여부만 본다.
  - **실패·확대 판정선**: ① qa 하네스 완료 기준(spec 8절) 중 1개라도 미충족 = 실패(머지 불가). ② 운영에서 `동기화 덮임 알림` 3명 이상(외부 발생 확정) **또는** 되돌리기 후 다시 덮임 사례가 보이면 → "A로는 부족, 덮임이 실사용에서 반복" 근거로 B안(막기)을 대표 승인 안건으로 올린다. 0명이면 B안은 후보로만 유지.
  - 초안의 "동기화 연결 끊기 증가 없음"은 **측정 불가라 삭제**(연결 끊기 계측 없음, 새로 만들지 않음).
- **하지 않으면 잃는 것**: 동기화 사용자의 기록 정확성, "안전한 자산 관리" 브랜드 문장의 근거. 근거 강도: **중간**(대상은 적지만 결함이 확정됐고, 손실은 사용자가 알아채지 못하는 형태라 발견되면 신뢰 회복이 어렵다).
- **알리기**: 외부 마케팅·게시 없음. 버그 수정을 "동기화가 더 안전해졌어" 식으로 홍보하지 않는다(A는 막는 게 아니라 알리고 되돌리는 것이라 과장이 된다). 앱 내 새 보안 문구도 없음(spec 4절 규칙 동의).

## 경험
### 1. 사용자가 하게 될 행동 (관찰 가능)
- 덮임이 실제로 일어난 순간 알림을 보고, 알림의 [확인하기]로 **어떤 항목이 어떻게 바뀌었는지 목록**을 본다.
- 목록에서 [되돌리기]를 누르고 확인 문구를 읽은 뒤 확정하면, 덮였던 항목이 이 기기에서 고친 값으로 돌아오고 다른 기기에도 반영된다. 또는 [그대로 두기]로 다른 기기 값을 받아들인다.
- 알림을 놓쳐도 같은 앱 실행 중에는 **더보기 > 기기 동기화**에서 같은 목록을 다시 연다.

### 2. 범위
- **포함**: 자동 pull(충돌 409 화해·온라인 복귀·폴링·포커스) 직전 로컬 사본을 메모리에 보관 → 이 실행 안의 마지막 동기화 시점과 비교해 "내가 고쳤는데 바뀐 항목"만 감지 → 알림(토스트 1회) + 기기 동기화 다이얼로그 안 안내 카드 → 목록·되돌리기(항목 단위)·백업 파일로 저장. 새 저장 키·스키마·payload·서버 API 변경 0.
- **줄일 수 있는 것**: ① 되돌리기를 항목별 선택이 아닌 **목록 전체 한 번**으로(체크박스 없음) ② 기존 토스트 두 개("다른 기기의 변경을 반영했습니다", "클라우드가 더 최신이라…")는 덮임이 있을 때 새 알림 하나로 **대체**(추가 아님) ③ 목록 행은 항목명 + 상태 한 줄(필드별 값 비교표 없음) ④ 백업 파일 저장은 보조 텍스트 버튼 1개(기존 백업 내보내기 재사용).
- **하지 않을 것**: 항목 단위 3-way 병합(B안, 후속) / 편집 전 사전 pull(C안) / 앱을 닫아도 남는 보관(저장 키 필요) / 새 보안 문구 / 가족 공유 UI(#57) / 수동 "기기 데이터 가져오기"·다른 금고 연결 시 알림(사용자가 덮어쓰기를 직접 확인한 경로) / 같은 항목 동시 수정의 규칙 변경(원격 우선 유지).

### 3. 바뀌는 곳 / 그대로인 곳
- 바뀜: 자동 동기화 토스트(덮임 있을 때만 새 문구), 기기 동기화 다이얼로그 armed 상태줄 아래 안내 카드(덮임 있을 때만), 덮임 목록 다이얼로그(신규, 기존 Dialog 재사용).
- 그대로: 덮임이 없을 때의 모든 화면·토스트, 동기화 상태줄·링크·코드 카드, pull·push 저장 결과(main과 동일), 월 스냅샷·닉네임 원격 우선 규칙, 결산·홈·첫 화면(diff 0).

## 대표 승인 요청용 한계 문장 (decision-brief에 그대로 사용)
> 이번 수정(A안)은 동기화 충돌 때 이 기기의 수정이 덮이는 것을 **막지는 못합니다.** 대신 덮인 순간 어떤 항목이 바뀌었는지 알려 주고, 앱을 닫기 전까지 한 번에 되돌릴 수 있게 합니다. 앱을 닫거나 새로고침한 뒤에는 되돌릴 수 없고, 되돌리면 같은 항목에 대한 다른 기기의 변경도 함께 되돌려질 수 있습니다. 저장 형식은 바꾸지 않아 문제가 생기면 코드 되돌리기만으로 원상복구됩니다. 덮임 자체를 막으려면(항목 단위 병합, B안) 동기화 상태 저장 형식에 필드를 추가해야 하며 별도 승인 후 후속으로 진행합니다.
