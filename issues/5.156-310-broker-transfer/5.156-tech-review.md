## 2. 원자 저장 가능 여부: 가능
`saveData(data)`(asset-data-context.tsx:1298)는 AssetData 전체를 1회 저장하고 성공 시 state·userEdit 신호를 갱신한다. 이미 `addTransactionWithPosition`·`addTransactionsBatch`가 stocks+transactions를 1회 saveData로 저장한다. handleApply는 지금 `{ ...fresh, stocks: result.stocks }`만 저장(344)하므로 `{ ...fresh, stocks, transactions }`로 바꾸면 된다. 실패 시 전부 미저장.

## 3. 확장 설계 (줄이는 순서)
- 경로 A(재작성 0): 옛 종목이 1개이고 B가 추가 행이면 `inheritedPreds`(apply.ts:150)가 이미 옛 id를 이어받는다. 이 경로에 `broker`만 바꾸는 이어받기를 허용하면 거래·참조 변경 0. 현재 이어받기는 같은 증권사 안 삭제+추가용이라 후보 조건(tickerKey 같고 증권사 다름, 사용자 체크)만 추가하면 된다.
- 경로 B(재작성): B가 이미 있거나(변경 행) A가 여럿이면 A의 거래 `stockId`를 B.id로 바꾸고 A를 제거. `transfer.ts`에 `applyTransfer(data, pairs)`(순수)로 둔다. 재작성 값은 `stockId`뿐이며 수량·평단·환율·매수일은 건드리지 않는다. B 포지션 합산은 맞추기 화면 값(수량·평단)이 권위라 거래로 재계산하지 않는다.
- 새 허용 값: 거래 `ticker`·`reflected`는 그대로 둔다.

## 4. 되돌리기가 거래까지 되돌리게 하는 방법
- `buildUndoEntries(before, after, coll)`는 이미 `coll="transactions"`를 받는다(undo.ts:15). overwrite-guard `ARRAY_COLLS`·`planRevert`·`applyRevert`도 transactions를 컬렉션으로 다룬다(overwrite-guard.ts:12·18·173). 따라서 handleApply가 `entries = [...buildUndoEntries(fresh.stocks, result.stocks), ...buildUndoEntries(fresh.transactions ?? [], nextTx, "transactions")]`로 합쳐 `undoRef`에 넣으면 되고(353행), `doUndo`의 `planUndo`(undo.ts:36)가 그대로 처리한다. 현재 `planUndo`는 "거래 배열은 그대로"라는 주석이 있어 주석·테스트만 갱신.
- 되돌리는 순간 `getAssetData()` 최신본에 적용하고, 맞춘 뒤 직접 고친 항목은 R1로 건너뛴다(기존 동작). 거래 쪽도 같은 규칙: 사용자가 이관 후 그 거래를 수정했으면 건너뜀. 부분 복원(종목은 복원·거래는 건너뜀)이 고아를 만들지 않는지 왕복 테스트 필요.
- relink-dialog의 undo pack은 별도 구조라 재사용하기보다 위의 `buildUndoEntries` 확장이 변경이 작다(CEO 조건 2의 "undo pack 재사용" 대신 제안).

## 5. stockId 참조처 전수 (grep 결과)
- 거래 레코드: `types/transaction.ts`, `trade-input.tsx`(20)·`trade-screenshot-import.tsx`(18)·`stock-trades-view.tsx`·`stock-target-picker.tsx`: 입력 시 id 선택. 이관 후 id는 B/A 중 남은 것이므로 변경 불필요. 단 입력 폼이 열린 채 이관되면 stale → 맞추기는 모달이라 낮음.
- 계산: `lib/tax-utils.ts`(10)·`tax-year-end-simulator.tsx`(20)는 `t.stockId`로 보유 종목과 조인. A 거래가 B로 이동하면 세금 FIFO 줄이 B 한 줄로 합쳐지므로 **세금 시뮬레이터 결과가 이관 전후 같은지 테스트 필요**(증권사 무관 합산 여부 확인).
- 결산·원인: `lib/report/asset-report.ts:648`(tradedStockIds), `:1059`·`:1214`(`_pid`=stockId로 종목 조인, 실현손익). 이관 전후 `stockId`가 존재하는 종목을 가리키면 불변.
- 선택·그룹 상태(메모리): `stores/trade-view-store.ts`·`stock-page-store.ts`의 `groupStockIds`, `lib/finance/stock-page.ts:73`, `lib/asset/grow-pick.ts`·`grow-rows.ts`, `lib/trade/effective-target.ts`, `import-inherit.ts`. 지워진 id가 남을 수 있으니 이관 후 모달 닫을 때 두 store 선택을 초기화하거나 존재하는 id로 필터(기존 deleteStock 동선 확인 필요).
- 다른 참조: `Loan.linkedStockId`(types/asset.ts:139; loan-tab·share-card·stock-tab·ai-prompts). **A 삭제 시 담보 연계가 끊긴다.** 이관은 A→B 이어받기이므로 `linkedStockId`도 B로 옮기는 규칙을 spec에 추가해야 한다(CEO 조건 3에 없던 항목).
- 백업·복원: `asset-storage.ts:779·792`(내보내기: stockId→stocks 인덱스 변환, 없으면 원본 id 유지), `:933~959`(가져오기: 인덱스→새 id, 없으면 ticker 매칭 폴백). 이관 후 유효 id만 있으면 왕복 안전. 고아가 남아 있으면 원본 id로 내보내져 복원 후에도 고아라 현상이 보존될 뿐 악화 없음.
- 동기화 병합: `cloud-sync/sync-client.ts:84`의 `pullAsset`이 `syncedIds` 기준으로 로컬의 미동기 **신규 항목**만 원격에 되살린다(mergedAdditions). 컬렉션별 id 단위, 참조 무결성 검사 없음.
- 마이그레이션 `one-time-migrations.ts:144~155`(2026-08 orphan prune)는 1회성(완료 표시 후 재실행 안 함).

## 6. 구버전 기기 혼재·고아 가능성
- 일반 경로: sync payload 형식 불변이라 구버전도 읽고 쓴다. payload는 통째 교체(+미동기 신규 항목 되살림)이므로 stocks와 transactions가 한 push로 같이 간다(1회 saveData). 일관 상태가 원격에 올라간다.
- 고아 발생 경로 2가지: (a) 구버전 기기가 이관 전 상태에서 **새 거래를 A.id로 추가**해 미동기 신규로 가진 채 pull하면 `mergedAdditions`가 그 거래를 이관 후 원격(A 없음)에 되살려 고아가 된다. (b) 구버전이 이관 전 payload를 그대로 push해 이관 자체가 덮이면(4.47 overwrite-guard 없는 기기) 이관 취소로 끝나 고아는 아니다. (a)가 핵심이고 질문 카드 안내로 줄이기 어렵다. 방어: 이관 후 `detectRelink`류가 아닌 간단한 고아 감지(stockId 미존재 거래 수)를 qa 점검 항목으로 두고, 1차 범위는 "고아 0 확인 + 발생 시 기존 relink(#147)로 복구 불가를 알림"으로 한정. 롤백(배포 되돌림) 시에도 레코드 형식 불변이라 손실 0.

## 7. relink(#147) 재사용 불가 확인
`relink.ts`는 이미 고아인 거래만 대상이다(`detectKind` 170행: `orphans = txs.filter(!ids.has(oldId))`). 이관 직전 A 거래는 A가 존재하므로 고아가 아니라 감지되지 않는다. 또 대상 S는 `stock_import_<ms>_N` id·매수일 = 만든 날인 종목으로 한정(IMPORT_ID, 173행)이고 근거가 createdAt 선후다. 이관은 사용자가 지목한 A→B 쌍이라 규칙이 다르다. 재사용 가능한 것은 `applyRelink`의 stockId 치환 방식(227행)뿐이며 그대로 `transfer.ts`에 같은 모양으로 쓴다.

## 8. 결함 의심 판정(코드상)
- **고아 거래 — 확정 가능성 높음.** `applyResync`(apply.ts:236~241)는 `stocks`만 필터하고 `transactions`를 받지도 않는다. 체크 삭제된 종목의 거래는 남는다. 다른 삭제 경로(`deleteStock`·`planDeleteStocks`, asset-data-context.tsx:364)는 평가액>0이면 거래를 지우도록 되어 있어 불일치다. 고아 반영 거래는 `reflectedTradeFlow`(asset-report.ts:1140~1156)가 종목 존재 확인 없이 `transactions` 전부를 합산하고(`reflected && 기간`), `tradedStockIds`(648)에도 들어간다 → 매수·매도 흐름이 남아 결산·홈 원인에 잔차가 생긴다. one-time prune은 2026-08 1회라 이후 맞추기 고아는 정리되지 않는다.
- **현금 유입(`reflectedCashInflow`, asset-report.ts:1122)은 영향 없음.** `cashTransactions`만 보며 resync는 현금 레코드를 건드리지 않는다. 연결 짝 기록은 거래 삭제와 함께 정리되지 않으나 "고아 짝 기록 유지, 잔액 불변"이 4.58 F24 정책이다.
- 조치: 이관과 같은 저장에서 체크 삭제 종목의 거래를 `planDeleteStocks` 규칙(평가액 0 이하 보존 규칙 C24 포함)으로 정리. 이 규칙을 resync에 재사용하되 이어받기로 id가 이동한 종목은 대상 제외.
