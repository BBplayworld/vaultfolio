# #32 반대 검토 (challenge.md) — cto

## 판정: 축소: 결산은 "전체 자산 월 탭"에만, 공용 엔진·홈 헤더는 손대지 않음, 신규 부가 기능 제거 + 연말 데이터 소실 선결

v1에서 빼는 것 (합의 절 수정 대상):
1. **주식 범위 월 탭의 결산 분해(시세/환율/순매수/기록 안 된 변화) 제외.** 주식 범위의 일·주·월·연은 기존 수익 화면(종가 비교)을 옮기기만 한다. 결산 블록 1·2·3·7은 전체 자산 범위에서만. → 순매수 라벨, 주식 전용 fx 분리, 범위 파라미터 논의가 모두 사라진다.
2. **원인 분해를 일·주·연 탭에 재사용하는 것 제외.** 지금 일·주·연 탭에는 원인 분해가 없다(아래 "코드와 다른 주장" ①). 새로 붙이는 건 확장이다.
3. **홈 헤더("지난 접속 이후") 라벨 일괄 변경 제외.** 결산 규칙 재분류는 엔진(`resolveAttribution`)을 고치지 않고 월 탭 전용 표시 매핑(순수 함수)으로만 한다. 홈 헤더의 매수·상환 라벨 정리는 별도 `type:simplify` 후보로 분리한다.
4. **"변동 없음 확인" 버튼 제외.** 코드에 없다(신선도 리마인더는 철회됨). 블록 7은 기존 `getStaleCategories`(S-4.30) 결과를 그대로 보여주고 갱신 화면 링크만 둔다.
5. **"기록 안 된 변화" 안내의 월별 접기 상태 저장 제외.** 임계값 조건부 한 줄만.
6. **과거 달 선택은 저장된 월 스냅샷 범위(최대 13개월)까지만.** 그 이전은 비활성.
7. 블록 4·5·6, 원인 기간 "3개월" 제거는 direction대로 v1 제외에 동의.

유지(대표 결정): 메뉴 3개, 일·주·월·연 × 전체/주식 토글, 허브 결산 카드, .ics, 결정 4-4 규칙.

## 1. 꼭 해야 하는가
해야 한다. PRINCIPLES 4장 우선순위 1이자 대표 결정이다. 다만 근거 강도는 direction 스스로 "중간"이라 인정했고, 그 핵심 가설(월 1회 의식 → 재방문)은 **결산 화면이 실제로 맞는 숫자를 보여줄 때만** 검증된다. 그래서 기능 수가 아니라 숫자의 정확성(아래 §6 연말 소실, §7 월 1회 방문자 기준일)에 v1 자원을 몰아야 한다. 메뉴 통합 자체는 리텐션 근거가 약한 정리 작업이므로 "옮기기"를 넘는 새 UI를 붙이지 않는다.

## 2. 더 작게 할 수 있는가
위 판정의 1~6. 핵심 논리: 결산의 질문은 "내 순자산이 왜 바뀌었나"이고 이건 전체 자산 범위의 질문이다. 주식 범위 결산·일/주/연 원인 분해·홈 헤더 통일은 모두 그 질문 밖이다. v1 신규 코드는 (a) 월 탭 결산 화면 (b) 표시 매핑 함수 (c) 허브 카드 (d) .ics (e) 스냅샷 보존 13개월로 한정한다.

## 3. 빼거나 합치는 쪽이 낫지 않은가
- 허브 카드 4→3, 성적표의 "순자산 변화, 왜?" 제거는 "빼기"라 찬성.
- 순자산 "월별 막대+증감 목록"은 월 선택기로 흡수, 별도 목록 삭제 — 찬성(중복 제거).
- 단 **전체 자산 × 주 탭은 현재 없다**(순자산은 년도별/월별/일별뿐). direction이 이 빈칸을 언급하지 않았다. 새 화면을 만들지 말고 기존 일별 30일 데이터로 "최근 7일" 목록을 재사용하는 수준으로 spec에서 확정할 것.

## 4. DECISIONS·LEARNINGS 충돌
- 충돌 없음(방향). 결정 4-1~4-5 준수.
- 확인된 기존 부채: 홈 헤더가 지금도 "주식 매수"·"대출 상환"을 원인으로 띄운다(`causeShortLabel`) — LEARNINGS "원인에 상환·매수를 넣지 않는다"와 이미 어긋나 있음. v1에서 같이 고치면 4.33 회귀 범위가 커지므로 분리 후보로 기록한다.
- 결정 4-4 예외("현금 자산 미등록 사용자의 매수 = 외부 투입")와 "평가 갱신"(부동산 수동) 항목이 direction의 재분류 설명에 빠져 있다. 매핑표가 필요하다(§7).
- LEARNINGS "알림은 경과일만으로 갱신 요구 금지": 블록 7이 30일 경과 기준(`getStaleCategories`)을 재사용하므로 "이번 달 갱신 안 됨" 표시는 정보 표시에 그치고 재촉 문구를 쓰지 않는다.

### direction.md 주장 중 코드와 다른 것
① "홈 헤더·일/주/연 탭이 같은 엔진을 쓴다" — 틀림. 엔진(`computePeriodAttribution`/`computeAttributionSince`) 사용처는 `asset-report-view.tsx`와 `dashboard.tsx`(홈 헤더) 둘뿐. 수익 화면은 종가 비교로 별개다.
② "월 스냅샷은 기존 기록으로 재구성 가능해 보인다" — **연 경계에서 깨진다.** `asset-data-context.tsx` 스냅샷 저장이 `s.month.startsWith(currentYear)`로 필터해, 1월 첫 접속 시 전년 월 스냅샷을 모두 지운다. 1월 1~10일에 보여야 할 "12월 결산"은 11월 값이 없어 비교 불가(일별은 30일 롤링, 연도 앵커는 netAsset만이라 예측). 출시 후 두 번째 결산이 바로 이 경우다.
③ "갱신 안 된 자산 → 변동 없음 확인" — 해당 기능 없음.
④ 통합 시 옮겨야 할 진입점 누락: `config/app-features.ts`(netasset·profit 기능 카드), `stores/tutorial/tutorial-store.ts`(step5 profit), `header-menu/top-bar.tsx`, 성적표 `growth` 링크, FAB(`floating-add-button.tsx`의 netasset 이동), GA 화면키(`/v/activity/profit` 등, `ga.test.ts`).

## 5. 목표 기여 측정 가능성
가능하나 조건부. GA는 production 전용·익명 client_id라 원칙 위반 없음.
- 지표 1(결산 창 재방문율)은 **출시 전 기준선**이 필요하다. 오늘(10-27) 기준 다음 창은 10-29~11-10이고 출시 전이다 → 지금 창의 값을 기준선으로 기록하는 일을 business.md에 넣을 것. 놓치면 비교 대상이 없다.
- 지표 2는 `settlement_view` 추가로 가능. v1에서 주식 범위 결산을 빼므로 범위 파라미터는 불필요.
- 표본 50명 → 2회 결산 누적 판단 동의. 단 ②가 고쳐지지 않으면 2회째(12월 결산)가 깨져 판단 자체가 불가능하다.
- 탭 이름 변경으로 GA 화면키가 바뀌면 출시 전후 page_view 연속성이 끊긴다. 옛 키→새 키 대응표를 business.md에 남길 것.

## 6. 위험 등급 초안과 근거
**medium.**
- 스키마 변경 없음, 서버 전송 값 없음(4-5 유지) → high 아님.
- 그러나 월 스냅샷 **보존 규칙 변경**(올해분 → 최근 13개월)이 필수이고, 이 키는 동기화·공유 토큰(`AssetSnapshots.monthly`)에 실린다. 구버전 기기가 동기화 후 다시 올해분으로 잘라낼 수 있다. 사용자 데이터 삭제 경로를 건드리므로 low도 아니다.
- 해시 라우트 `#activity/netasset|profit` 변경 → 옛 해시 리다이렉트 누락 시 진입 실패.
- 롤백: PR revert로 화면 복구 가능. 보존 규칙은 "더 많이 남기는" 방향이라 롤백해도 데이터 손실 없음(되돌리면 다음 저장 때 다시 올해분으로 잘릴 뿐).
- specs/README 판정: 저장 데이터 보존·동기화 영향이 있으므로 `/spec` 명세 작성 대상.

## 위험 재판정 (design-review)
### 결론: **high** 유지(developer 안 채택) + **축소: 동기화 pull 월 스냅샷 합집합 병합(spec §5-1 "대응" 줄)을 v1에서 제외**

근거 (WORKFLOW 6장, 2026-10-27 main 코드 기준)
1. 동기화 병합은 v1에 꼭 필요하지 않다. 병합이 막는 것은 "구버전 기기가 올해분만 push → 신버전 pull이 통째 교체(`asset-storage.ts:333`)"뿐이고, spec §5-1이 이미 적었듯 미적용 시 최악도 현행(올해분만)과 같다. 실제 손실이 날 수 있는 시점은 2027-01 연 경계인데, PWA는 `sw.js` skipWaiting + `updateViaCache:'none'`이라 구버전은 다음 실행 때 바뀐다. 출시 후 약 2개월 동안 구버전이 남아 push할 가능성은 낮다. 반대로 병합을 넣으면 모든 동기화 사용자의 pull 경로가 바뀌고, 같은 달 우선순위(enrich 소실, tech-review 결함 의심)라는 새 쟁점이 생긴다. 얻는 것보다 위험이 크다.
2. 병합을 빼도 medium으로 내려가지 않는다. 남는 두 항목이 6장 high 기준에 걸리거나 경계에 있다.
   - `mapSettlementCauses`: 내부 이동 상쇄와 결정 4-4 예외로 사용자가 보는 결산 금액(순유입·기록 안 된 변화)을 정한다. 저장하지 않는 읽기 전용 계산이지만 내용이 "금액 계산 규칙"이다.
   - 보존 규칙 교체(`asset-data-context.tsx:770`): 스키마 변경은 아니다. 그러나 사용자 기록을 지우는 코드 경로라서 컷오프 계산이 틀리면 과거 달이 사라지고 복구할 수 없다.
   - 둘 다 판단이 애매하다. 6장 "애매하면 높은 쪽"에 따라 **high**로 판정하고, 초안 medium은 번복한다. 그래도 진행 판정은 그대로다. high는 대표가 판단할 때 쓰는 정보이고, 진행을 막는 사유가 아니다.
3. 위험을 줄이는 조건(필수)
   - 엔진 파일에는 `computeAttributionBetween` 래퍼 export 1개만 추가한다. 기존 함수 시그니처와 동작은 바꾸지 않는다. 기존 `asset-report.test.ts`는 수정 없이 통과해야 한다. 이 경우 "엔진 미변경" 조건을 지킨 것으로 본다.
   - `pruneMonthlySnapshots`: 현재월은 항상 남는다. 입력보다 결과가 늘지 않는다. 연 경계 2026-01·2027-01을 vitest로 고정한다(완료 기준 8에 추가).
   - pull 경로는 이번 PR diff에 포함하지 않는다. F-SYNC 회귀는 "동작 불변"으로 확인한다.
