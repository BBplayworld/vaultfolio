## 쟁점 판정
**① 데이터 안전**: A는 pull·push 저장 결과를 main과 똑같이 두고 "모르는 손실"을 "실행 중 알림+복구 가능"으로 바꾼다. 남는 손실(무시·재시작)은 현행과 같아 **이번 diff의 FAIL 기준 = main보다 나빠지는 경우 또는 되돌리기가 목록 밖·이후 변경을 지우는 경우**로 qa가 판정한다. 되돌리기 위험과 필수 대응:
- R1 이후 변경 덮어쓰기: 덮인 뒤 이 기기에서 다시 고쳤거나 다음 pull로 또 바뀐 항목은 되돌리면 새 손실. → **목록은 열 때·확정 때 다시 계산하고, 현재 값이 '덮인 직후 값'과 다른 항목은 되돌리기에서 빼고 목록에서 지운다.**
- R2 복원 경로: `applyImportedPayload`·`clearAssetData` 사용 금지. 현재 데이터에 목록 항목만 적용해 사용자 편집과 같은 저장 경로(클릭 핸들러에서 저장 + notifyAssetUserEdit)로 쓰고 일반 push. 월 스냅샷·설정·목록 밖 항목 무접촉. push 409면 같은 감지 흐름으로 다시 들어간다(전용 경로 없음).
- R3 확인 문구: 원격 삭제분 재추가도 다른 기기 변경을 되돌리므로 → "목록의 N건을 이 기기 값으로 되돌리고 다른 기기에도 반영해요. 같은 항목을 다른 기기에서 바꾸거나 지운 내용도 함께 되돌려질 수 있어요."
**② 재시작 알림**: **spec 채택(폴백 없음).** 기준 사본이 없으면 내 변경과 다른 기기 변경을 구별할 수 없어, 폴백은 남의 변경을 "내 변경"으로 보여 주고 '전체 복원'은 다른 기기 변경을 통째로 되돌린다(고치려는 손실보다 큰 새 손실). 저장 결과는 main과 같으니 악화 없음. 한계 문장에 명시. tech-review 2절 폴백 문장은 이 판정으로 대체.
**③ GA**: 허용(direction 안). `feature_use` category 2개 → page_title `동기화 덮임 알림`·`동기화 되돌리기`. 조건: 호출은 UI 계층(감지 완료 후 토스트 표시 지점, 되돌리기 확정 핸들러)만 — `pullAsset`·`applyImportedPayload`·`runPush` 내부 금지, 덮임 알림은 실행당 1회, 건수·항목 파라미터 0, ga.test 매핑 2줄 추가. track은 try/catch no-op이라 위험 low. ui.md 6절 'sync_action' 문장은 이 판정으로 대체.

**⑤ 대표 승인용 한계 문장(최종, decision-brief 그대로)**
> 이번 수정(A안)은 동기화 충돌 때 이 기기의 수정이 덮이는 것을 **막지는 못합니다.** 대신 덮인 순간 어떤 항목이 바뀌었는지 알려 주고, 앱을 닫기 전까지 한 번에 되돌릴 수 있게 합니다. 앱을 닫거나 새로고침한 뒤에는 되돌릴 수 없고, **앱을 다시 연 직후의 동기화에서 덮인 경우(예: 오프라인에서 고치고 앱을 닫았다 연 경우)는 알림도 뜨지 않습니다(지금과 같음).** 되돌리면 같은 항목에 대한 다른 기기의 변경(삭제 포함)도 함께 되돌려질 수 있습니다. 저장 형식은 바꾸지 않아 문제가 생기면 코드 되돌리기만으로 원상복구됩니다. 영향 대상은 두 기기 이상으로 동기화하는 소수 사용자이며, 두 기기에서 짧은 간격으로 엇갈려 저장하거나 오프라인에서 고칠 때 생깁니다. 덮임 자체를 막으려면(항목 단위 병합, B안) 동기화 상태 저장 형식에 필드를 추가해야 하며 별도 승인 후 후속으로 진행합니다.
