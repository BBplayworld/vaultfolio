## ① 코인 고아 거래 원인과 해법
- 원인: `holdings-resync-dialog.tsx:375-378`. 코인은 `stocksToCrypto`로 `crypto` 배열만 바꾸고 `plan = null`이라 `{...fresh, crypto: nextCrypto}`만 저장한다. 체크 삭제된 코인의 `cryptoTransactions`(cryptoId)가 그대로 남아 고아가 된다. 주식은 `planResyncSave`(transfer.ts:78)가 `planDeleteStocks`로 정리한다(#310).
- 해법: `planDeleteCryptos(data, ids, rates)`(`contexts/asset-data-context.tsx:383`, 이미 export)를 그대로 재사용한다. 새 규칙을 만들지 않는다. 직접 삭제와 같은 규칙이므로 평가액 0 이하 코인 거래 보존(C24), 닫힌 달 짝 기록 보존이 자동 적용된다.
  - 삭제 id = `fresh.crypto` 중 `nextCrypto`에 없는 id. `transfer.ts`에 `planCryptoResyncSave(fresh, nextCrypto, planDelete)`로 주식과 대칭 구현한다. 인자 `exchangeRates`는 이미 대화상자에 있다.
  - 주의: `stocksToCrypto`가 id를 새로 만들거나 바꾸는 경우(이름 변경 매칭)는 삭제 id에 들지 않아야 한다. "diff의 remove 체크 행 id"가 아니라 "fresh에 있고 next에 없는 id"로 계산해 이 위험을 없앤다. 테스트로 고정.
- **되돌리기**: 현재 코인은 `buildUndoEntries(fresh.crypto, nextCrypto, "crypto")`(389행) — cryptoTransactions가 없어 되돌려도 지워진 거래가 안 돌아온다. 이 상태로 (a)만 넣으면 **되돌리기 후 기록 손실(기록 유실)**이다. 따라서 `buildUndoEntries`를 `crypto`+`cryptoTransactions` 두 컬렉션으로 확장(`undo.ts:43` `buildResyncUndoEntries`와 같은 방식)해야 하며, 이것이 (a)의 필수 조건이다. `planUndo`·`applyRevert`가 `cryptoTransactions` 컬렉션 이름을 지원하는지(타입상 `coll`에 있음)는 구현 때 단위 테스트로 확인한다: "삭제→되돌리기 후 거래 id·내용 동일".
- 토스트·결과 화면 되돌리기는 같은 `undoRef` 사본을 쓰므로 경로 추가 0.

## ② 프롬프트 총평가금액 필드 (서버)
- **현재 상태**: `route.ts:94` 프롬프트 `무시: 계좌번호·총평가금액·광고배너`, `STOCK_SCHEMA`는 배열(type ARRAY, 행 객체), 파싱은 `Array.isArray`(820행), 응답은 `respondParsed`에서 `{ stocks: [...] }`(이미 객체).
- **설계(조건 3 충족)**: 응답 JSON `{ stocks, screenTotal? }` — 클라이언트 응답은 additive라 구버전 클라이언트·`/ratio`(`ratio-preview.tsx:181`은 `data.stocks`만 읽음)·온보딩·`stock-screenshot-import`에 영향 0. 난점은 **Gemini 출력 스키마**다: 현재 최상위가 배열이라 총액을 넣으려면 `{ rows: [...], screenTotal }` 객체로 바꿔야 하고, 이는 **모든 주식 인식(맞추기·가져오기·/ratio)에 걸린 변경**이다.
  - 축소안(권장): 최상위는 배열 유지. 행 스키마에 optional `screenTotal`(화면 하단·상단의 총 평가금액)을 **마지막 행에만** 채우게 하지 않고, 별도 필드를 둘 수 없으므로 객체 래핑을 택하되 파서가 **배열·`{rows}` 둘 다 받게** 한다(`Array.isArray(x) ? x : x.rows`). 그러면 모델이 구형 형태로 답해도 행은 유지된다.
  - 프롬프트 한 줄 `무시: 계좌번호·광고배너`로 줄이고 `screenTotal=화면에 합계 라벨(총평가금액·총 평가·총자산 등)로 명시된 숫자 1개·없거나 불확실하면 0`을 추가. 총액이 `rows` 행으로 새로 섞이지 않게 "합계 줄은 행으로 만들지 말 것"을 명시(현재 `무시: 총평가금액`가 이 역할을 하고 있으므로 **회귀 핵심**).
  - `maxOutputTokens: 2048`(788행): 래핑·필드 추가로 출력이 늘어 잘림(`MAX_TOKENS`→422 truncated)이 더 일찍 날 수 있다. 행당 필드 12개 기준 여유를 픽스처로 측정하고, 필요하면 상향(요금 영향 작음).
- **요청 본문 불변**: `form.append("image")`·`assetType`(278행)만. 앱 합계·보유 목록을 보내지 않음(조건 1). route 입구 `formData.get`은 image·assetType·entry만 읽는다.
- **저장·캐시·로그 0 grep 근거**: `route.ts`의 `console.*`는 833행 1건(`e.message`만), 캐시·KV·파일 쓰기 호출 없음(`cache` 계열 grep은 `GEMINI_SERVER_DAILY_LIMIT` import 1건, 사용량 카운터는 `api-guard`/`cache-storage` 쪽이며 응답 값 저장 아님). 구현 시 `screenTotal`이 로그·카운터에 안 들어가는지 qa가 같은 grep으로 재확인(조건 2).

## ③ 대조 1줄 계산
- 기준: **적용 후 앱 합계**가 아니라 **이번에 올린 화면이 덮는 범위의 미리보기 합계**와 `screenTotal`을 비교(맞추기 후 저장값과 화면이 같아야 하므로 `result.stocks` 중 이 맞추기에 포함된 종목만, 원화 환산은 `computeNetAsset`의 `mul`과 동일 환율). 구체적으로 `sum(item.quantity × currentPrice × 환율)`이 아니라 **인식된 행의 `currentValue`(화면 원값)를 합산**하는 게 화면 대조에 맞다. 앱 합계와 화면 합계를 비교하면 시세 시각 차이를 앱이 이미 흡수한 값이라 의미가 흐려진다. spec에서 "화면 행 합 vs 화면 총액"인지 "맞춘 뒤 앱 값 vs 화면 총액"인지 하나로 확정해야 한다(권장: 후자, 사용자가 궁금한 것은 '내 앱이 증권사와 같은가'). 후자라면 대상 = 이번 올린 화면이 덮은 증권사·계좌의 종목만(`brokerOverrides`/`accountOverrides` 단위).
- 허용 오차: `max(|screen|×0.5%, 1,000원)`(시세 시각·환율 차). 이내면 '일치', 초과면 '차이 N원'+`시세 시각이 달라 조금 다를 수 있어요`+차이가 큰 행 표시.
- **숨김 조건(조건 6)**: ① `screenTotal ≤ 0` 또는 없음 ② 올린 장 2장 이상(범위 불일치) ③ `truncated`/`failed`/`limit` 장 포함·`failedRemoved` ④ 해외 종목 혼재 + 환율 추정(`estimated`) ⑤ 예수금 포함 여부 불명 — 응답에 포함 여부 신호가 없어 **프롬프트에 "예수금·현금 포함 총액이면 `screenTotalIncludesCash: true`"를 요구하는 대신, 앱 쪽 판정**: `screenTotal`이 행 합보다 큰 경우(차 > 오차)와 같을 때를 구분 못 하므로, 예수금 모호 시 차이가 나면 줄 숨김이 아니라 '차이' 대신 `총액이 예수금을 포함하면 다를 수 있어요` 문구를 쓰는 것을 spec에서 확정. 라벨 확신 없음(`screenTotal` 0)은 숨김.
- 순수 함수 `reconcileTotal({ screenTotal, rows, tolerance, flags }): "match"|"diff"|"hidden"`. 단위 테스트에 일치·차이·총액 없음 3값과 경계(오차 정확히 경계) 포함(C138).
- GA: `track("feature_use", { category: "resync_check_match|diff|none" })` — 금액·% 없음.

## ⑤ 위험 등급 초안
- **medium** 유지 가능. 이유: 거래 삭제 경로(a) + 서버 프롬프트(e) 있으나 저장 형식 0. 단 **조건**: (a)에서 되돌리기가 거래까지 복원(위 ①). 이를 못 지키면 데이터 손실이라 high로 올린다. (e)는 서버 프롬프트라 위임 조건 ⑤(보안·데이터 문구)와 무관하나, 서버 전송 변경은 0이다(입력 불변, 응답 필드 1개 추가) — COO 확인 사항.
- 서버로 나가는 값 증가 0(요청 본문 불변, 이미지 그대로). 응답 값은 기기 메모리에만. 사용자 보유 정보 역산 불가: 서버는 보유 사실을 받지 않고 이미지에서 읽은 총액을 돌려줄 뿐이다.
- spec보다 커질 때 줄이는 방법: ① (e) 스키마 래핑이 전 호출에 걸리는 부담이 크면 **(e)를 5.162로 분리**(ceo 축소 경로 그대로) ② (c)(d)는 기존 데이터 읽기·문구뿐이라 작음. (d) 환율 기준일은 `syncTodayExchangeRate`·`exchangeRates`에 날짜 필드가 없다(`contexts` grep: 환율 날짜 필드 없음) — 날짜를 새로 저장하지 말고 응답 시각을 메모리에서만 쓸 것(저장 시 스키마 변경 → high). 수단이 없으면 (d)는 spec에서 제외 제안.
