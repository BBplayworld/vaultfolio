**이 문서가 바꾸는 것은 '총액을 어디서 받는가'뿐이다.** 계산·문장·허용 오차·정보 구조 대조표·엣지 케이스는 원 spec §5~§7을 그대로 따른다(아래에 다시 쓰지 않은 항목은 원문이 정본).

## 1. 문제 / 목표 행동
- 5.161에서 총액을 행 추출 호출에 함께 넣었다가 B 화면 행이 회귀해 대조 1줄을 뺐다. 맞춘 뒤 숫자가 증권사 화면과 같은지 확인할 방법이 여전히 없다.
- 목표 행동(원 spec 동일): 주식 보유자가 증권사 화면 1장으로 맞춘 직후 결과 화면에서 합계가 맞는지 읽고, 다르면 이름이 나온 종목을 고친다.

## 2. 범위
| 포함 | 줄일 수 있는 것 | 하지 않을 것 |
|---|---|---|
| 총액 전용 호출 1회, 전용 풀, 결과 화면 대조 1줄, GA | qa FAIL 2회면 둘째 줄 `차이가 큰 종목`을 빼고 일치/차이 1줄만 | 행 추출 프롬프트·스키마·설정 변경(해외 0 개선 포함), 코인 대조, 금액 표시, 총액 저장, 대기 표시, 총액 재시도, 안내 문구 변경, 전역 한도 인상 |

## 3. 호출 흐름 (`holdings-resync-dialog.tsx` `runRecognition`)
1. 사용자가 주식 화면을 올리고 `인식`을 누른다. 행 호출은 지금과 같다(요청·응답·차감 불변).
2. 그 인식 실행이 끝났을 때 **주식 AND 올린 장이 정확히 1장 AND 그 장이 `ok` AND `failedRemoved` 아님 AND 그 장으로 총액을 부른 적 없음**이면, 같은 실행 안에서 같은 파일로 총액 호출을 1회 보낸다(`assetType=stock-total`). 행 인식이 실패·잘림·한도면 보내지 않는다.
3. **대기 표시는 없다.** 미리보기 진입과 `맞추기` 버튼을 막지 않는다. 행 인식이 끝난 뒤 다시 기다리게 하면 실패했을 때 설명할 말이 없는 표시가 되기 때문이다.
4. 판정 시점은 사용자가 `맞추기`를 누른 순간 1번이다. 그때까지 응답이 없으면 줄을 숨기고, 뒤늦게 온 응답으로 줄을 끼워 넣지 않는다(결과 화면 흔들림 0). 호출은 8초에 끊는다 [TR 값 확정]. 대화상자를 닫거나 초기화하면 함께 취소한다.
5. 재전송 규칙(조건 ① 개정문): 한 장당 총액 호출은 평생 1회. 실패해도 다시 보내지 않고, 실패한 행 인식을 `다시 시도`로 살린 경우에만 그때 1회 보낸다. 기기는 이미지를 저장하지 않으며 대화상자가 닫힌 뒤에는 보내지 않는다.
6. 총액 호출은 기기 30회를 차감하지 않고(`geminiUsage.increment` 호출 0), 장 상태·남은 횟수 표시·오류 문구를 바꾸지 않으며 `trackParse`도 보내지 않는다.
7. 온보딩·종목 등록(`stock-screenshot-import`)·`/ratio`·코인 맞추기에서는 총액 호출 0.

## 4. 서버 계약 (`api/parse-screenshot/route.ts`)
- 요청: `image` + `assetType=stock-total`. 그 밖의 필드 0(앱 합계·보유 목록·증권사 0).
- 응답 200: `{ screenTotal: { value, label, currency } | null }`. `value`는 0보다 큰 숫자, `label`은 화면에서 읽은 글자, `currency`는 `KRW|USD`. 하나라도 어긋나면 서버가 `null`로 낸다(`sanitizeScreenTotal`, b28a134e 재사용). 프롬프트는 "합계 라벨이 화면에 글자로 있을 때만, 행을 더해 만들지 말 것".
- 입구 가드(`guardRequest`·크기·시그니처·`isTinyImage`)는 그대로 거친다. 너무 작은 이미지는 호출·차감 없이 `null`.
- 전용 풀 `{ name: "stock-total", dailyLimit: 60 }`를 `RATIO_POOL`과 같은 방식으로 `reserveGeminiCalls`에 넘긴다. 전역 일 1,500·시간 150 안의 몫이며 전역 한도는 올리지 않는다. 초과는 429.
- 저장·캐시·로그 0: 풀 카운터는 횟수만 센다. `value`·`label`을 쓰는 로그·캐시 경로 0(grep 테스트). 오류 로그는 기존 `e.message` 1건뿐.
- **행 경로 불변**: `buildStockPrompt`·`STOCK_SCHEMA`·주식 호출 config(`maxOutputTokens` 2048 포함)·`respondParsed` 주식 분기는 한 글자도 바꾸지 않는다. 한 요청 안에서 Gemini를 2번 부르는 변형은 쓰지 않는다(ceo ①).
- 보안·데이터 안내 문구 변경 0. 바꿔야 하면 대표 승인으로 올린다.

## 6. GA

## 7. 완료 기준 (qa)
1. **해시 고정 테스트(요청 0)**: vitest가 `buildStockPrompt()` 문자열, `STOCK_SCHEMA` JSON, 주식 호출 config의 SHA-256을 분기 시점 main 값에 고정한다. `git diff origin/main -- route.ts`에서 이 셋의 diff 0.
2. **C154 실호출 예산 약 30회**: 픽스처 5장(A 총액 있음, B 총액 없음·2줄 헤더·다크, **C 해외 포함·가격 칸 라벨 없음**, D 총액 없음·1줄 표·라이트, E `총 평가손익`·`예수금`만 있는 함정) × [행 구(운영) 2회 + 행 신(preview) 2회 + 총액(preview) 2회]. 순서: 같은 프롬프트 반복 diff 0 → 구·신 diff 0. `/ratio` Referer를 쓰지 않는다.
3. 합격선: 행 diff 0(5장 전부, 하나라도 다르면 중단·폐기) / 총액 A·C 정답, B·D·E `null` / 총액 2회 반복 동일.
4. 화면: A 픽스처로 일치·차이 문장이 원 spec §5 표와 글자 단위로 같다. 숨김 0~6 각각에서 줄 DOM 0. 대기 표시(스피너·자리 표시) DOM 0. 줄이 생긴 결과 화면에서 `되돌리기`·`닫기`를 390·320 실제 클릭과 `elementFromPoint`로 확인한다(C153).

6. 네트워크 관찰: 주식 1장 맞추기에서 `stock-total` 요청 정확히 1회, 본문은 이미지 + 모드 값뿐. 2장 맞추기·코인·온보딩·종목 등록·`/ratio`에서 0회. 대화상자를 닫은 뒤 0회.
7. 데이터 안전 점검표: 개정 조건 ①(재전송 1회·이미지 보관 0·앱 값 0), 저장 키·스키마·마이그레이션·동기화·공유 토큰 변경 0, `screenTotal`은 컴포넌트 state에만 있다.
