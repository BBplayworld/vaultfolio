## 1. 현재 '보유 현황 업데이트' 흐름
- 진입: FAB 시트 hub → "보유 현황 업데이트" → 카테고리 → `select-method`(스크린샷/직접) (`app/(main)/_components/layout/floating/floating-add-button.tsx:101-137`). 주식 스샷은 `dispatchAddStock`, 그 외는 `trigger-add-*` 이벤트로 `stock-input.tsx:688`·`crypto-input.tsx:366`의 `*ScreenshotImport` 열기. 다른 진입: 온보딩 마법사(`onboarding-wizard-flow.tsx:101-102`), /ratio 인계(`ratio-handoff-host.tsx:50`, 파싱 결과 `initialParsed`로 업로드 단계 생략).
- 단계(주식 `forms/asset-update/screenshot/stock-screenshot-import.tsx`): upload → (기존 보유와 키 중복이 1건 이상일 때만) conflict → preview → 등록. 코인·현금·대출도 같은 3단계.
- conflict 선택지 2개(`stock-screenshot-import.tsx:399-432`): "덮어쓰기"(merge) = 겹치는 종목만 새 값으로 교체, 나머지 유지 / "초기화 후 등록"(reset) = 해당 자산군 기존 전부 삭제 후 스샷 종목으로 대체. 로직은 `lib/asset/holdings-conflict.ts` `resolveKept`(reset이면 `[]`, merge면 가져온 키와 안 겹치는 기존만 유지)이고 호출부가 `[...kept, ...신규]`로 합친다(`:272-275`).
- 종목 식별 키: 주식 `keyOfStock = ticker:category`(증권사 `broker` 미포함), 코인 `symbol:exchange`, 현금 `name:institution`, 대출 `name:institution:type`(`holdings-conflict.ts:7-16`). 이름 매칭은 없고 티커만 쓴다. 티커 미인식이면 `":category"`로 키가 같아 서로 충돌 판정(`:7`), 사용자가 직접 티커를 넣어야 등록(`stock-screenshot-import.tsx:230-234`).
- 수량·평단 갱신 규칙: 갱신이 아니라 **항목 통째 교체**. 신규 항목은 `id: stock_import_<now>_<idx>`(`api/parse-screenshot/route.ts:204`), `purchaseDate=오늘`(`:213`), `description=""`로 만들어지며 기존 항목의 id·purchaseDate·description·`positionSource/positionEffectiveDate`·inactive 상태는 이어받지 않는다. 평단은 화면 값이 없으면 `현재가/(1+수익률)` 역산(`route.ts:183-186`), UI에도 "평단가(추정)"로 표시(`stock-screenshot-import.tsx:617`).
- 증권사·환율: `mapParsedStocks`(`lib/asset/screenshot-stock-map.ts:77-110`)가 `brokerHint`→`matchBrokerHint`(`config/asset-options.ts:19`)로 `broker` 설정, 힌트 없고 동일 ticker:category 2번째부터 "항목 N". 해외는 `purchaseExchangeRate = 오늘 환율`로 고정(`stock-screenshot-import.tsx:262`), 국내는 삭제. 상세 화면은 `groupStocksByTicker`/`mergeStockGroup`(`views/detail/asset-detail-tabs.tsx:66-117`)로 증권사별 행을 가중평균 합산해 보여준다(저장은 분리).
- **덮어쓰기/초기화가 정리 안 된 지점(파일:줄)**
  1. 키에 `broker`가 없다: 같은 종목을 증권사 2곳에 보유(분리 행 2개)하고 한 증권사 스샷만 올려 merge하면 두 행 모두 제거되고 1행만 남는다(`resolveKept` 필터 `holdings-conflict.ts:36`).
  2. 교체되는 항목이 새 id를 받는데 `transactions[].stockId`/`cryptoTransactions[].cryptoId`는 갱신·정리되지 않는다(`stock-screenshot-import.tsx:275`, `crypto-screenshot-import.tsx:193-204`는 `transactions` 미접촉). 반면 개별 삭제는 거래도 함께 지운다(`asset-data-context.tsx:1368-1375`). 결과: 고아 거래가 남고, reset은 거래를 그대로 둔 채 보유만 비운다.
  3. merge 시 "스샷에 없는 기존 종목"은 무조건 유지 → 팔고 없는 종목이 현황에 남음(전체 재동기화가 안 됨). reset은 스샷에 없는 다른 증권사/계좌 종목까지 자산군 전체를 지움(카테고리·계좌 범위 한정 없음).
  4. 코인 거래소가 스샷 하나=거래소 하나로 일괄 지정(`crypto-screenshot-import.tsx:139-141`), 거래소 미인식이면 `""` 키.
  5. 서버 `section`(국내/해외/기타)과 활성 탭 카테고리(isa/pension 등)가 섞여 같은 티커의 category가 달라지면 같은 종목이 다른 키가 됨(`screenshot-stock-map.ts:81-86`).

## 3. 거래 기록과 '반영'
- `types/transaction.ts`: `transactions`(stockId, ticker, type, quantity, price, currency, exchangeRate, date, **reflected**, reflectedAt, reflectionId…), `cryptoTransactions`(cryptoId, symbol, KRW 고정…). `reflected=true`면 보유 수량·평단에 반영된 거래, false는 기록만. 보유 항목에는 `positionSource: manual|computed`·`positionEffectiveDate`(`types/asset.ts:60-62`).
- 포지션 재계산: `lib/trade/trade-utils.ts` `computeNewPosition`/`recomputeFromLog`(기준 스냅샷 + reflected 거래 시간순 적용), `rollbackTransaction`. 거래는 보유 항목을 바꾸지만 그 반대(보유 현황 변경 → 거래 보정)는 없다.
- **현황만 맞추고 히스토리를 보존하는 기존 경로는 없다.** 스샷 현황 업데이트는 positionSource를 건드리지 않고(신규 항목은 undefined=manual) 거래도 만들지 않는다. 수동 수정은 `updateStock`(id 유지)이라 거래 연결이 유지되지만 스샷 경로는 id가 바뀐다. 거래 쪽은 `addTransactionWithPosition`/`addTransactionsBatch`(`asset-data-context.tsx:125-126`)로 보유와 거래를 함께 쓴다.
- 손익·결산 의존: 원인분해는 `lib/report/asset-report.ts`에서 ① 일·월 스냅샷의 breakdown·cost 차(스냅샷은 저장 시점 박제, `asset-data-context.tsx:683-710`) ② `reflectedTradeFlow`(`:892-908`)/`reflectedCryptoFlow`(`:587`)가 **보유 존재 여부와 무관하게** reflected 거래를 집계 ③ 예측 경로 `estimatePeriodInflows`(`:513-565`)가 **보유 항목의 `purchaseDate`·평단×수량**을 기간 내 신규 투입으로 추정(해당 종목에 기간 내 반영 거래가 있으면 제외). 재동기화가 수치를 바꾸는 경로: (a) 교체 항목 purchaseDate=오늘 → 오늘 구간 신규 투입으로 잡힐 수 있음(예측 경로, 거래 연결 끊기면 제외 조건도 풀림) (b) 고아 거래가 flow에 계속 집계 (c) 평단 변경 → 원가·손익률 변화, 오늘 이후 스냅샷의 cost 변화 (d) 해외 `purchaseExchangeRate` 오늘 환율 덮어쓰기 → 환차손익 변동(`asset-report.ts:544-549`, `tax-utils.ts:123,203-208` 양도세 계산도 사용). 과거 스냅샷은 박제라 안 바뀐다.

## 4. 증권사·매입 환율 자동 추정 가능 입력
- 증권사: 인식 필드 `brokerHint`(텍스트만) → `matchBrokerHint` 매칭 성공 시 설정. 로고/앱 이름 별도 인식 필드 없음(프롬프트 확장 필요). 기존 보유 재사용: 같은 ticker:category 기존 항목의 broker를 가져오는 코드 없음(교체 시 유실). 단 신규 '항목 N' 규칙은 있음.
- 환율: 서버 이력은 **최근 2일치만** 제공(`api/finance?type=exchange`의 history, `asset-data-context.tsx:386-396`), 로컬은 접속일마다 누적(`profit-utils.ts` `readExchangeHistory`/`getRatesForDate`, 이력 없으면 fallback). 임의 과거 거래일 환율 조회 API는 없다. 해외 종목 통화는 스샷 currency + 가격≥5000 휴리스틱(`route.ts:188-201`). 기존 항목의 `purchaseExchangeRate` 재사용 코드는 없음(현재는 무조건 오늘 환율로 덮어씀, 원가 환산이 바뀌는 원인).

## 6. 데이터 안전 위험 후보 (CHECKLIST C5·C6·C13·C14·C16·C17 관점)

- 항목별 diff 미리보기: preview는 이미 종목 카드와 "교체" 배지(`stock-screenshot-import.tsx:574`)가 있으나 기존 값 대비 변경(수량·평단) 표시와 '삭제될 종목' 표시는 없음.
- 스키마 변경: 옵션 A/B 모두 저장 스키마 변경 없이 가능(세션 내 메모리 사본, 기존 필드 유지). 사본을 localStorage에 남기려면 새 저장 키 필요(→ risk:high, 마이그레이션·동기화 제외 규칙 필요).

## 7. 재사용 vs 신규
재사용: `holdings-conflict.ts`(키·`countConflicts`·`resolveKept`), `screenshot-stock-map.ts`(`mapParsedStocks`·`applyCommonDefaults`·`BROKER_NONE`), `matchBrokerHint`, `useGeminiUsage`, `StockScreenshotImport`/`CryptoScreenshotImport` 3단계 다이얼로그, `StockTargetPicker`(보유 항목 선택 카드), `groupStocksByTicker`/`mergeStockGroup`, `trade-utils.ts` 재계산 함수, `saveData`/`saveAssetDataRaw`+`notifyAssetUserEdit`, `getRatesForDate`, `markCategoryRefreshed`, `SCREENSHOT_UPLOAD_NOTICE`(보안 문구, `config/security-copy.ts`; 문구 변경 시 대표 승인 대상).
신규 필요(후보): 기존 항목 대비 diff 계산 순수 함수(추가/변경/삭제 후보 분류), 기존 id·메타 승계 병합 함수(id 유지로 거래 연결 보존), 증권사 단위 범위 키, 다중 이미지 업로드·합치기(클라이언트 N회 호출 합산), diff 미리보기 UI, 되돌리기 사본(메모리 또는 저장).

## 8. 기술 옵션 (설계 제안, 비용은 개발 일수 추정)
- **옵션 A 최소(정리 우선, 약 2~3일, risk:medium)**: 기존 conflict 단계를 '현황 재동기화' 용도로 정리. ① 교체 시 기존 id·purchaseDate·description·broker·purchaseExchangeRate 승계(거래 연결 유지) ② 키에 broker 추가 또는 같은 종목 다행이면 선택 ③ preview에 "삭제될 종목/수량·평단 변경" 목록 추가 ④ 저장 직전 메모리 사본으로 같은 다이얼로그 내 되돌리기. 스키마·서버 변경 0, 서버 전송 값 증가 0, 이미지 1장 유지. 단점: 여러 화면 합치기 불가.
- **옵션 B 다중 이미지(약 4~6일, risk:medium)**: A + 이미지 최대 3~5장 순차 호출·결과 병합(티커 중복 제거), 앱 내 한도 15회/기기·IP 30회 안에서 장수 차감 안내. 한도 소모가 커지므로 `maxOutputTokens`·장수 상한 결정 필요. 서버는 기존 라우트 재사용(요청 1장 유지).
- **옵션 C 사본 영속화·거래 보정(약 7일+, risk:high)**: 재동기화 전 전체 사본을 새 저장 키에 보관(복원 UI)하거나, 차이를 reflected 거래로 자동 생성해 히스토리 일치. 새 저장 키·마이그레이션·동기화 제외/병합 규칙(C5·C13)·결산 영향 검증 필요 → 대표 승인 대상. 지금은 비권장.
- 공통 제약: 자산 값은 서버에 저장하지 않고 이미지만 AI 분석에 전송(기존과 동일), 신규 보안 문구가 필요하면 `security-copy.ts`를 단일 출처로 하고 대표 승인 대상. #71 반려 교훈에 따라 '앱 안에 이미 있는 스샷 가져오기·덮어쓰기'를 확장하는 방식이며 신규 입구는 아님.
