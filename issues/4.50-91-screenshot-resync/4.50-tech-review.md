## 2. 다중 이미지·한도·잘림
- **서버 호출은 클라이언트 순차 N회, 요청당 1장 유지**(병렬 금지: 분당 20 한도·순서 보장·장별 진행 표시). 상한 5장, `<input multiple accept>` + 드롭은 `files` 앞 5개만 받고 초과 안내. 닫기·재선택 시 `AbortController`로 진행 중 요청 중단.
- 한도: 기기 15/일은 `useGeminiUsage`가 **성공 시** `increment`(기존 스크립트와 동일, 서버는 실패도 차감). 시작 전 `remaining()`을 읽어 선택 장수 > 남은 횟수면 앞에서 남은 만큼만 받고 나머지는 `한도 미인식`(S2 해제 조건). 한 장 재시도 = 1회 추가 차감, 실패 장만 `다시 시도`/`빼기`. 429는 즉시 중단하고 남은 장은 한도 미인식으로 둔다.
- **잘림 감지: 서버에서만 보이는 신호**(`result.candidates[0].finishReason === "MAX_TOKENS"`)라 서버 변경이 필요하다. `route.ts:739` 부근, JSON 파싱 앞에 4줄: 422 + 기존 `error` 문구 그대로 + `code:"truncated"` 추가. /ratio는 `error`만 읽으므로 diff 0(필드 추가). 서버 무변경 대안: 잘린 응답은 스키마상 배열이 안 닫혀 현재도 422가 되므로 클라이언트가 422 전체를 `일부만 인식됐어요, 나눠서 찍어 주세요`로 묶어도 안전하나 원인 구분이 안 된다. **권고는 `code` 추가.** `MAX_TOKENS` 없이 끝난 장이 화면보다 적게 읽힌 경우(스크롤 덜 됨)는 신호가 없어 S2 절반 규칙으로만 막는다(알려진 한계).
- **같은 이유로 주식 응답 필드 2개를 추가한다(`processStockResults`, 값 노출뿐):** `quantityMissing`(현재 `route.ts:176`에서 수량을 조용히 `1`로 채움 → 연결 항목 수량이 1로 덮이는 데이터 손실 경로) · `averagePriceEstimated`(`:183-186` 역산 여부). 플래그가 true면 수량은 `확인 필요`, 평단은 기존 값 유지(S4). 서버 변경 합계 약 10줄, 기존 필드·/ratio 소비 코드 불변.

## 4. 거래·결산 영향
**qa 요청 분석(`trade-utils.ts:127-190`)**: `deriveBaseSnapshot`은 `positionSource`·`positionEffectiveDate`를 읽지 않고 **모든 reflected 거래**를 역산한다(`stock-trades-view.tsx:168-173`이 source를 넘기지만 함수가 무시). `reverseTransaction` 매수는 `qtyBefore<=0`이면 수량 `max(0,…)`·평단 0으로 절단. 따라서 맞추기로 수량 100→60 후 (맞추기 전 반영된) 매수 100을 삭제하면 `60-100=-40→0`, 재적용할 거래도 없어 **보유 0·평단 0**이 된다. 수량을 늘린 경우(100→150)는 50으로 정상. 삭제 확인 대화상자가 결과 수량을 미리 보여 주는 점(`:178-181`)이 유일한 완화다. `updateStock`(직접 수정)도 id 유지·source 미기록으로 동일하게 재현되는 기존 현상이며, 맞추기는 `updateStock`보다 나쁘지 않다(source 추가 기록만 다름). 이 결함의 근본 수정(`deriveBaseSnapshot`이 effectiveDate 이전 거래만 제외)은 trade-utils·거래 화면 전체에 영향이라 **이 릴리스 범위 밖**, 후속 이슈 후보로 남기고 vitest로 현상을 고정한다.

`deleteStock` 대비 규칙 차이: 개별 삭제는 `transactions` 필터로 거래도 지우고(`asset-data-context.tsx:1368-1375`) 맞추기는 삭제 종목의 거래를 **보관**한다(되돌리기 무손실). 거래 화면은 현재 id로 거르므로(`stock-trades-view.tsx:103-110`) 삭제 종목 거래는 안 보이고 계산에만 남는다 — 한계로 명시.

`positionSource="manual"` 이후 기대(S5 표, vitest `validateReflection` 직접 호출): 새 거래 반영 → `manual_override` confirm(직접 수정과 동일) / 맞춘 수량 초과 매도 → `restrict` / 과거 날짜 거래 → manual 판정이 먼저라 confirm / 승인 시 `computed`+거래일로 전환.

C21 픽스처(`src/lib/report/__tests__/resync-flows.test.ts`, `settlement-flows.test.ts`의 `computeChainCauses`·`computeSettlementCauses` 헬퍼 재사용): (a) 거래 없이 수량 감소 (b) 지난달 반영 매수가 있는 종목 삭제 (c) 이번 달 반영 매수 후 삭제 (d) 신규 종목 추가 (e) 해외 평단 변경 (f) 해외 삭제 후 `computeForeignRealizedGain`. 공통 단언: 이번 달 매수+매도 합 = dCost, `기록 안 된 변화`는 같은 보유 변경을 `updateStock`으로 한 경우와 동일(main 동치), 지난달 결과 불변(C8), 양도세 (a)(b) 불변. `estimatePeriodInflows`: 승계 id라 기존 종목은 `purchaseDate` 불변 → 기간 내 신규 투입 오탐 없음, 신규 종목만 오늘 날짜로 잡힘을 (d)로 증명. 기대값은 spec 작성 시 표로 미리 적는다.

## 7. 테스트 설계 (vitest, 기존 하네스 재사용)

diff 0: 결산·홈 팁·웰컴·첫 등록 퍼널·현금·대출 스크린샷·/ratio 인계·마법사·`sync-client`·`sync-state`·`overwrite-guard`(함수 재사용만)·`trade-utils`·`asset-report`·`tax-utils`·`asset-data-context`·기존 두 스크린샷 컴포넌트. 변경 파일: 신규 `resync/*`·대화상자 2개, `stock-input`·`crypto-input` 분기 각 1곳, `ga.ts` 약 6줄, `screenshot-stock-map.ts` 헬퍼, `route.ts` 약 10줄.
위험: R-a 잘못된 삭제의 즉시 전파(완화: 삭제 기본 해제 규칙·미리보기·되돌리기·백업, 복구 범위는 결과 화면+토스트까지, 이후는 백업뿐 — C17), R-b 인식 오류 수량이 덮어씀(미리보기 전후 표기), R-c 위 4절 rollback 절단(기존 현상). 롤백: 신규 파일 제거 + 진입 분기 2곳 원복만으로 기존 흐름이 복귀하고 데이터 형식은 불변이라 기록 손실 없음. 구버전 혼재 시 손실 가능성은 맞추기 자체가 아니라 #84가 다루는 덮임뿐. 등급 **risk:high**(대량 수정·삭제의 동기화 전파).
