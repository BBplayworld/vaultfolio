## 1. A가 대표 요구를 충족하는가, C 대비 타당한가 — 타당, 재반려 위험 낮음~중간
- 대표 문장 대조: ① "더보기 갈 정도로 낮지 않다"·"더보기는 설정 전용" → A는 더보기 행 철회(C57 PASS). ② "페이지 혹은 상단 배치" → A는 '상단'에 그대로 해당. ③ "핵심 기능" → PWA에서 회색 하단 칸 → 채운 색 아이콘(브라우저와 같은 모양·자리)이라 시각 위계는 오히려 올라간다. 대표는 하단 칸 제거 자체가 아니라 '어디로 갔는가'를 반려했다(PR #126 5칸 화면을 보고 더보기 행만 지적).
- direction 비교의 보정: C의 단점으로 적힌 "브라우저와 위치 다름"은 인증카드 기준일 뿐이다. 브라우저에서 더보기는 **홈 맨 위 오른쪽**(`showMore`=홈만)이므로 C는 '더보기 위치를 브라우저와 맞추는 안'이다. 즉 A=인증카드 통일, C=더보기 통일. 둘 다 PWA 홈 맨 위 줄이 필요해 그 비용은 같다.
- 그래도 A인 이유(코드 근거): C는 더보기가 하단에서 빠지면 `PAGE_ORDER`(home·detail·activity·more)의 마지막 칸에 대응 탭이 사라진다. 고치려면 navigation-context 스와이프를 바꿔야 하는데 이 스와이프는 **브라우저 모바일에도 적용**된다(240행 `!isStandaloneMode && !isMobileViewport`일 때만 끔). C는 브라우저 변경·범위 M, A는 브라우저 diff 0·범위 S. 그리고 C는 대표가 말한 '페이지/상단' 밖이다.
- 재반려 위험 지점: PWA에서 인증카드가 '모든 화면·엄지 영역 1탭' → '주요 5개 화면·위쪽 1탭'이 된다(더보기·설정·배당·성적표·세금 등에서는 2탭). '핵심 기능 접근 축소'로 읽힐 수 있다. 완화: 브리프에 진입점 전후 표(화면 수·탭 수·색)와 PWA 전/후 스크린샷을 둔다.
- **대안 처리**: 두 안을 다 만들지 않는다. A만 개발한다. 다만 대표 메시지에 대안 1줄(아래 6절)을 넣어 `수정: 하단 유지`로 답할 수 있게 한다(선택 요청이 아니라 반려 시 경로 고지). 방향 확정 알림(사업 절 합의 직후, ORCHESTRATOR 허용 알림)에 같은 1줄을 넣으면 개발과 병행해 이견을 일찍 받을 수 있다. 회신을 기다리며 개발을 멈추지 않는다.

## 2. PWA 홈 맨 위 줄 — 첫 화면 원칙·#48·#113과 충돌 없음, 높이 조건 보강 필요
- #48·#113: 대상은 웰컴(자산 0·공유 대기). 이때 `TopBar`·`BottomNav` 모두 null 반환 → 렌더 0, 판독 무영향. 팀 선례(4.45·4.54 판정)도 '첫 화면'=웰컴. direction의 "위임 ⑥ PWA 홈 첫 화면" 표기는 근거를 ⑦·반려 영역으로 바꾼다(결론인 대표 승인은 같음).
- PRINCIPLES 5 "첫 화면 최소": 설치 사용자가 앱을 열면 보는 화면이라 정신은 적용된다. A는 새 정보 0, 화면 전체 요소 수는 하단 −1·상단 +1(+로고). B(콘텐츠 안 버튼)보다 덜 침범한다 → 수용.
- **높이 결함 위험**: 기존 `pwa-show-header`를 홈에 그대로 쓰면 헤더 = 48px + safe-area, 본문 위 여백 16px이 된다. 지금 홈 여백은 max(24px, safe-area). 계산하면 iPhone(safe-area 47)은 47→111로 **+64px**, safe-area 0 기기는 24→64로 +40px이다. direction의 "≤48px"는 iOS에서 깨진다 → V2.
- 시각: 아이콘 바로 아래 순자산 카드 오른쪽 위에 성적표 트로피 배지가 조건부로 붙는다. 오른쪽 위에 강조 두 개가 세로로 겹치는지 ui-designer가 확인한다. PC PWA는 상단 네비(로고가 홈 칸) 바로 아래 줄에 로고가 또 생긴다. 로고 생략 여부는 ui-designer가 정한다(차단 아님).

## 3. 버튼 1개 원칙 — 위험 실재, 구현 방식을 고정한다
- 사실: `trigger-open-share-card` 리스너는 top-bar `ShareScreenshotButton` 1곳(49행). 발송처는 홈 팁(`home-tip-box` 144·151행)뿐. 리스너가 `recordVisit`·`track`·`setOpen`을 모두 하므로 인스턴스가 2개면 홈에서 대화상자 2개, 기록·GA도 2회가 된다. PWA 허브·홈에서도 헤더는 CSS로만 숨겨진 채 마운트돼 있다(`showShare` 참).
- 따라서 **새 `ShareScreenshotButton`·새 `ShareScreenshotDialog`를 그리지 않는다.**
  - 홈·하위 화면(주식·자산 변화): 기존 헤더 인스턴스를 standalone에서 보이게 한다(CSS 클래스 조정). 선택기·설치·설치 안내·더보기는 standalone에서 계속 숨긴다.
  - 상세·성과 허브 h2 줄: PWA 전용 **발송 전용 버튼**만 둔다(`dispatchOpenShareCard` 호출, 대화상자·리스너 없음). 열기는 이미 마운트된 헤더 인스턴스가 받는다. 리스너는 `detail.source ?? "home_tip"`으로 출처를 받게 1줄 확장한다(허브 버튼 = `top_bar`).
  - 결함 의심 아님(설계 주의). 이 방식이면 #126 S1(더보기 직접 오픈 패턴)은 tool-menu 되돌림으로 소멸한다.

## 4. C55 오탭 — 데이터 변화 0 확인, 단 '중심점' 대신 '버튼 폭'으로 다시 계산
- 320의 0.4px 경계(옛 업데이트 중심 190 vs 새 경계 190.4)는 중심점 비교라 의미가 약하다. 손가락은 버튼 폭(52px) 안에 퍼진다. 버튼 폭 기준으로 계산하면 다음과 같다.
  - 320: 옛 업데이트(164~216)의 오른쪽 절반(190.4~216)은 **성과**로 간다.
  - 375: 옛 업데이트(191~243)의 223.4~243 구간(약 38%)은 **성과**로 간다. 옛 성과(132~184)의 132~151.6 구간은 **상세**로 간다. 옛 인증카드(251~303)의 295~303 구간은 **더보기**로 간다.
- 결과는 전부 화면 이동이나 시트 열림이고, 1탭으로 되돌린다. 데이터가 바뀌는 오탭은 0 → C55 PASS. 브리프 비용 절에 "옛 업데이트 자리를 누르면 320에서 절반은 성과로 이동"을 적는다.
- 참고: main은 320에서 6칸×52px=312px로 안쪽 폭 304px를 넘친다. 새 grid가 이를 해소한다(이득).

## 5. 판독 영향 — 계측 신설 효과를 분리한다
- '인증카드 열기': 머지 전에는 PWA 하단 칸이 미계측이었고, 머지 후에는 PWA 상단이 `top_bar`로 잡힌다. 그래서 전후 증가는 사용 증가와 구분할 수 없다(`app_mode` 폐기). **머지 전후 비교 금지, 머지 후 절대값만** 본다.
- 전후 비교는 '인증카드 저장'만 한다. 모든 경로의 합이라 경계 전후 정의가 같다. v1 가드레일 '저장 합산 유지'는 이 지표로 유지하고, 사업 절에서 확정한다.
- 홈 기능 팁: top-bar `recordVisit` 추가(S6)로 브라우저에서 인증카드를 쓴 사람에게는 share-card 팁이 빠진다 → '홈 팁' 구성 경계. #51 결산 팁은 `pickHomeTip`에서 결산이 먼저라 불변(C38 PASS).
- PWA 홈 콘텐츠가 ≤48px 내려간다. 머지 시각을 STATE·DECISIONS 경계로 기록한다. #48·#113은 무영향.
