## 2. A안 데이터 영향 (구 = 5.164 이하, 신 = 5.165)
- **E2EE 범위**: `pushAsset`이 `buildExportPayload()` 전체를 `encryptPayload`로 감싼다(`sync-client.ts:51`). 서버 평문 body는 `iv·ciphertext·baseVersion·pubKey` 그대로(`:57`). 절대 규칙은 '서버 평문 금지'이고 암호문 안은 허용이다 — 수량·메모가 든 이름표 키가 같은 경로로 나가는 선례(`stock-labels.ts` 머리 주석). 역산 불가 근거 동일.
- **백업**: `exportAssetData`가 같은 payload를 쓴다(`:237`) → 자동 포함. 필드 없는 구 백업 복원은 로컬 맵을 건드리지 않는다.
- **구 기기 동작**: payload 최상위 모르는 필드는 `applyImportedPayload`가 읽지 않고(strip이 아니라 무시), 구 기기 push에는 필드가 없다. **5.164 passthrough는 최상위를 제외했으므로 5.164 기기도 구 기기와 똑같다.**
- **id 맵 재-push 성립 조건**: ① 항목은 불변(현금 거래 수정 기능 없음) → 병합 = id 합집합, 충돌 없음(같은 id가 다르면 `heavier` 동률 규칙), 삭제 표식 불필요 ② **유효성 = 살아 있는 `cashTransactions` id와의 조인**(읽기·합계·내보내기·재-push 비교 모두 조인 뒤 값으로) — 이게 없으면 고아 항목이 두 신 기기 사이에서 재-push를 반복시킨다 ③ 수신 처리는 `saveAssetData` **뒤**(이름표와 같은 자리).

## 5. 저장 순서 · 고아 정리 · 되돌리기
- 저장 순서: 맵 먼저 → `saveData`(실물 선례 `asset-storage.ts:179`). 맵 쓰기 실패 = 저장 중단·오류 토스트, 거래 저장 실패 = 맵 항목 회수. push는 `saveData`의 notify 1회로 충분(맵이 먼저 써져 같은 payload에 실린다).
- 저장소에서 지우는 곳: 거래 삭제 2곳(`:1876·1890`)과 계좌 삭제(`:1659`)만. 3년 정리(`pruneCashTransactions`)·원격 삭제·1회성 정리(`one-time-migrations.ts:154`)는 **지우지 않고 조인으로 무시**한다.
- pull 때 고아를 지우지 않는 이유: 덮임 되돌리기(#84 `overwrite-guard.ts`)가 원격 삭제된 거래를 같은 id로 되살린다. 그때 표시도 돌아와야 한다.
- 현금 거래 삭제에는 토스트 되돌리기가 없다(`cash-tx-view.tsx:87·211`). 맞추기 되돌리기(`resync/undo.ts:40·51`)는 현금 거래를 다루지 않는다 → 추가 작업 0.
- 알려진 한계: 고아가 로컬에 남는다(건당 약 100B, 연 40건이면 4KB). v1은 압축 코드를 넣지 않는다(지우는 코드가 손실 경로).
- 읽기(5.164 조건 ②에 해당): 손으로 쓴 관대 파서. 항목 단위로 건너뛰고 모르는 필드는 보존, id는 `ctx_` 접두만 허용(`__proto__`·`constructor` 차단), 손상 원문은 자동 경로가 덮지 않는다.

## 7. 5.164 필요성 재평가
- cto가 든 진행 근거 3개 중 **롤백 하한**과 **백업 왕복**은 A안에 해당하지 않는다. 표시는 레코드 밖에 있고(롤백에도 키 보존), 최상위 필드는 5.164가 다루지 않는다.
- 남는 근거는 **예·적금 등 다음 레코드 필드 추가의 선행 비용** 하나다. 5.164 자체는 유효하나 5.165와는 독립이다.
- 제안: 5.165 조건 ③(5.164 운영 확인 + 7일)과 '5.164 revert 금지'를 A안에서는 해제. 유지하면 5.165가 근거 없이 7일 묶인다.
