결론: **높음 0건 / 중간 2건(운영 설정 확인 필요) / 낮음 4건.** 서버에 남는 푸시 정보로는 그 기기에 알림을 보내는 것만 가능하고, 사용자 식별이나 자산 접근은 불가능하다. (origin/main 0a71a94 코드 기준 점검, 2026-11-14. 비밀값은 확인·기재하지 않음)

## ① 수집 항목 (Redis는 Upstash, 키 접두어 `push:{prod|preview|dev}:`)

| 항목 | 예시 형태(가짜) | 용도 | 저장 위치 | 저장 형태 | 보관·삭제 |
|---|---|---|---|---|---|
| endpoint | `https://fcm.googleapis.com/fcm/send/AAAA…` (Apple은 `*.push.apple.com`, Mozilla는 `*.push.services.mozilla.com`, Windows는 `*.notify.windows.com`). URL 끝 긴 토큰은 브라우저가 만든 기기별 일회성 주소로, 이 주소를 아는 쪽만 그 기기로 푸시를 요청할 수 있다. 계정·이름과 무관 | 알림 발송 대상 주소 | `push:*:sub:{id}`의 blob 안 | **AES-256-GCM 암호화**(IV 12바이트 매번 새로 생성, 태그 16바이트) | 90일 TTL(갱신 시 연장), 끄기·데이터 삭제·410/404 응답 시 즉시 삭제 |
| keys.p256dh / keys.auth | 87자·22자 base64url 난수 | 페이로드 end-to-end 암호화(RFC 8291)용 구독 공개키·비밀값 | 같은 blob | 암호화(위와 동일) | 위와 동일 |

| 알림 종류 ID | `morning`, `kr`, `settle`, `tax` 등 고정 카탈로그 | 보낼 알림 선택 | 레코드 + `topic:{ID}` 집합 | **평문** | 구독과 동일 |
| cond | `daily` / `pm2` | 매일 / ±2% 이상만 | 레코드 | 평문 | 구독과 동일 |
| createdAt·updatedAt | `2026-11-14` (일 단위) | 갱신 판단 | 레코드 | 평문 | 구독과 동일 |

보유 종목·금액·금고 ID는 서버로 가지 않는다. 클라이언트 설정(prefs)은 기기 로컬에만 있다.

## ② 이 정보로 할 수 있는 것과 없는 것
- **Redis 전체가 유출돼도**: endpoint·keys는 암호문이라 PUSH_STORE_KEY 없이는 읽지 못한다. 평문으로 남는 것은 "알림 종류·조건·날짜"뿐이라 누가 어떤 기기인지 알 수 없다.
- **PUSH_STORE_KEY까지 유출되면**: endpoint+keys를 복원할 수 있다. 푸시 서비스는 endpoint로 요청을 받을 때 **VAPID 개인키 서명**을 요구하므로, VAPID 개인키가 없으면 임의 발송은 불가하다. 개인키 없이 가능한 것은 사실상 없다. 개인키까지 모두 유출되면 그 기기에 가짜 알림을 보낼 수 있다(내용은 SW가 `{m,t,b}` 형식만 표시, 클릭 시 앱 내부 경로만 열림).
- **불가능**: 사용자 식별(이름·계정·금고·IP 없음), 자산 데이터 접근(서버에 없음), 알림 내용 열람(푸시 사업자도 암호화로 못 봄).
- 푸시 사업자(Google·Apple·Mozilla)는 endpoint 발급 주체이므로 해당 기기의 구독 사실은 원래 안다(웹푸시 구조상 불가피).

## ③ 보안 점검

| 항목 | 판정 | 근거 |
|---|---|---|
| 저장 암호화·키 관리 | PASS(낮음 L1) | `crypto.ts` 32바이트 키(base64) 아니면 미설정 취급, 복호화는 `authTagLength:16`·짧은 블롭 거부 적용됨(4.91 권고 R2 반영). 같은 키로 HMAC과 암호화를 겸함(키 분리 안 함) |

| preview/production 키 분리 | **미확인(중간 M1)** | 코드는 키 접두어(`push:prod:`/`push:preview:`)만 분리하고 같은 Redis를 쓴다. 암호화 키가 같으면 preview 코드도 prod 블롭을 복호화할 수 있다. Vercel 환경 변수 범위는 코드로 확인 불가 |

## ④ 위험 등급과 권고
**높음: 없음.**

**중간**
- **M1 PUSH_STORE_KEY·VAPID·CRON_SECRET의 Preview/Production 분리 미확인.** 같은 Redis를 쓰므로 분리가 안 되면 preview 배포 코드로 운영 구독 복호화·발송이 가능. 권고: Vercel에서 Production 값이 Preview 범위에 체크되지 않았는지 확인하고, 필요하면 서로 다른 값으로 교체(교체 시 `push:prod:*` 삭제, 사용자는 앱 재실행 시 자동 재등록).
- **M2 유출·교체 대응 절차 문서 없음.** 권고: 키 유출 시 ① 새 키 등록·재배포 ② `push:prod:sub|topic|all:*` 삭제 ③ VAPID 유출이면 키쌍 교체의 순서를 운영 문서에 기록.

**낮음**
- **L1** HMAC과 AES에 같은 키 사용. 권고: HKDF로 용도별 파생 키 분리(선택).
- **L2** 호출 한도용 `rl:push-subscribe:<IP>`에 평문 IP가 1시간 남는다(기존 전 API 공통 가드). 권고: 처리방침·고지에 "부정 이용 방지용 IP 일시 처리(1시간)" 한 줄 명시, 필요하면 IP를 해시해 저장.
- **L3** 처리방침이 저장소 밖에 있다면 위 수집 항목 반영 여부 확인, 없다면 작성.
- **L4** 속도 제한은 Redis 장애 시 fail-open(L1 메모리·플랫폼 방화벽이 1차 방어). 구독 5천 상한과 허용 호스트 제한으로 실피해 낮음. 조치 불필요, 인지만.

참고: 4.91 보안 검토의 R2(GCM 강화)·R3(DELETE 미설정 시 500)·R5(고아 정리·상한)는 main에서 반영된 것을 확인했다. R4(삭제 판정이 prefs.on 기준)는 이번 범위에서 재확인하지 않았다.
