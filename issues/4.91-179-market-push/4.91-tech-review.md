### 2-4. Redis 키 (VERCEL_ENV 접두어)
- 접두어 `P = "push:" + (process.env.VERCEL_ENV === "production" ? "prod" : "preview") + ":"`. 로컬(VERCEL_ENV 없음)은 FileCacheStorage라 `dev`.
- `P+sub:{sha256(endpoint)}` → JSON `{endpoint,p256dh,auth,topics:string[],cond:"daily"|"pm2",updatedAt}`, TTL 90일
- `P+topic:{topicId}` set(구독 id). 갱신 시 이전 토픽 SREM·새 토픽 SADD. 발송은 회차 대상 토픽의 SUNION 후 구독 id 단위 1회(구독이 한 회차에 대상 여러 개 = 1건).
- `P+sent:{kr|us}:{marketDate}` 중복 방지 플래그(SET NX, TTL 3일)
- 운영 Cron 핸들러는 `VERCEL_ENV==="production"`일 때만 동작(그 외 즉시 204), 항상 prod 접두어만 읽는다. **같은 Redis이므로 `/api/push/*`는 접두어를 서버 환경 변수에서만 계산(클라이언트 입력 금지)**.
- 기존 `csync:asset:*`·share 키와 분리. `ICacheStorage`에 `putPushSub/getPushSub/deletePushSub/listPushSubIdsByTopics/markPushSent` 추가, 접두어는 메서드 안에서 처리해 호출부 실수 방지. File 구현은 기존 JSON 파일 패턴 확장.

### 2-5. Cron·발송 핸들러
- 플랜 사실(공식 문서 `vercel.com/docs/cron-jobs/usage-and-pricing` 기준, **이 세션은 접근 차단되어 기억에 의존 → 대표/개발자가 첫 push 시 확인 필요, 출처 URL 기재**): Hobby = 하루 1회까지, 시각 정밀도 시간대 단위(지정 시각부터 해당 시간 내 임의 시점), 개수 한도는 2025년 개편 후 프로젝트당 100개(구 문서는 계정당 2개). **필요 개수 2개라 어느 쪽 한도여도 충족.** 분 단위·1일 초과 표현식은 Hobby에서 배포 실패하므로 `0 0 * * 1-5`(미국: UTC 00:00 = 미국 장 마감 후 KST 아침, 월~금 UTC 기준이 KST 화~토 아침과 어긋남 → **미국 Cron은 UTC 화~토 `0 0 * * 2-6`**), 국내 `0 7 * * 1-5`. 주말·휴장은 핸들러가 재확인(Cron 요일은 1차 필터일 뿐).
- 인증: `Authorization: Bearer ${CRON_SECRET}` 정확 일치(미설정 시 401, 문자열 비교는 `timingSafeEqual`). 운영만 실행. preview 호출은 `isPreviewEnv`·VERCEL_ENV로 거부.
- 핸들러 순서: ① 인증 ② 시장 판별(`?m=kr|us`, vercel.json 쿼리) ③ 그 시장의 직전 거래일 계산·휴장(`isKrHoliday`/`isUsHoliday`)이면 종료 ④ `sent` 플래그 NX 실패면 종료(중복·재시도 방지, **플래그를 먼저 잡고 실패 시 삭제하지 않음 = 중복 알림 금지 우선**) ⑤ 대상 토픽에 구독이 0이면 KIS 미호출 종료 ⑥ `getKisAccessToken` — `unavailable`이면 건너뜀(알림 생략, 재시도 없음, 플래그 유지) ⑦ `withinUpstreamBudget("kis", n)` 초과 시 건너뜀 ⑧ 필요 대상만 KIS 조회(해외 종목은 350ms sleep 포함 순차 → 시총 미국 3개 ≈ 1초, 지수 호출 합쳐 `maxDuration=60`이면 충분) ⑨ 전부 실패면 `recordKisFailure`, 하나라도 성공이면 `recordKisSuccess` ⑩ 구독별 문구 생성(조건 pm2는 ±2.0% 이상 대상만, 없으면 미발송) ⑪ `Promise.allSettled` 청크(50)로 `webpush.sendNotification(sub, payload, {TTL: 3600*3, urgency:"normal"})`, 404/410이면 sub 삭제·토픽 SREM.
- **9시 전 차단**: Cron 시작 이전 실행은 구조적 불가이나 방어로 핸들러가 KST 시각을 확인해 `kr`은 KST 16시 미만·`us`는 KST 09시 미만이면 종료(수동 호출·잘못된 설정 방어).
- Hobby 흔들림: 지정 시각 이후 최대 1시간이라 us 09:00~09:59, kr 16:00~16:59 KST. 시각 방어 조건과 일치.
- 구독자 수천 명 시 분할은 P2 이후(현 규모 월 50명 기준 한 자릿수). 한 회차 `maxDuration` 60초 내 완료 못 하면 sent 플래그는 이미 설정되어 재진입 없음 = 일부 누락 허용.

### 2-8. sw.js
- `push`: `event.data?.json()` try/catch, 실패·형식 이상이면 폴백 제목 `시장 종가`·본문 `오늘 시장 종가가 업데이트됐어요`. `waitUntil(showNotification(title,{body,tag:"market-kr"|"market-us",renotify:false,icon:"/icons/icon-192x192.png",badge:동일,data:{url:"/?from=push"}}))`. 같은 시장은 같은 tag로 교체(쌓이지 않음). 페이로드는 `{m:"kr"|"us",t,b}` 3필드만.
- `notificationclick`: `close()` 후 `clients.matchAll({type:"window",includeUncontrolled:true})` — 같은 origin 창이 있으면 `focus()`만(화면 유지), 없으면 `openWindow("/?from=push")`. GA `알림·누름`은 앱이 `from=push`를 읽고 `history.replaceState`로 제거(P0 구현, 단위 테스트는 순수 함수 `consumePushFlag(url)`로).
- `pushsubscriptionchange`: 앱 로드 시 `getSubscription()`과 로컬 prefs를 비교해 재구독·서버 갱신(SW 안에서 서버 호출하지 않아 단순). `CACHE_NAME` v5로 올림(sw 갱신 트리거), 기존 fetch·오프라인 로직은 건드리지 않음.

### 2-10. '모든 데이터 삭제' 시 구독 해제
- `settings-page.tsx` 삭제 핸들러에서 `unsubscribePush()`(`src/lib/push/client.ts`) 호출: ① `registration.pushManager.getSubscription()` → endpoint 확보 ② `DELETE /api/push/subscribe {endpoint}`(서버 sub·토픽 삭제, 실패해도 다음 진행하되 **로컬 구독 해제를 먼저 하지 않고 서버 삭제 후 `unsubscribe()`**; 서버 실패 시 발송 시 410 정리·TTL 90일이 안전망) ③ `secretasset_push_prefs` 삭제. 문구 `시장 알림도 꺼져요`는 이 경로가 실제로 완료될 때만 사실. 네트워크 실패 시에도 로컬 해제·prefs 삭제는 수행하고 서버 고아는 TTL로 정리(문구는 기기 알림이 꺼진다는 의미로 유지).
- 체험 모드(`isTrialMode`)에서는 '알림' 섹션 숨김(체험이 서버 구독을 만들지 않게).

### 2-11. API 보안·남용 방지
- `POST /api/push/subscribe`: body `{endpoint,p256dh,auth,topics,cond}` 검증(endpoint `https:` 필수, 길이·허용 호스트 휴리스틱 = fcm.googleapis.com·updates.push.services.mozilla.com·*.push.apple.com·*.notify.windows.com, topics는 카탈로그 ID만·최대 15, cond 2값). `guardRequest`+`guardRateLimit` 재사용. DELETE는 endpoint 소지가 인증.

- 로깅 금지: endpoint·키를 console에 쓰지 않음, 에러는 상태 코드만. IP·UA 저장 금지.

## 3. 데이터 영향 범위
- 로컬: 신규 키 `secretasset_push_prefs` 1개만 추가. 자산 스키마·저장·동기화·스냅샷·거래·공유·백업·성적표 계산 **변경 0** → 마이그레이션 불필요(키 없으면 기본 off). 구버전 기기 혼재·롤백 시 신규 키는 무시, 자산 기록 손실 가능성 0, 서버에는 고아 구독만 남고 TTL 90일·410으로 정리.
- 서버: 신규 Redis 키(위 2-4). 동기화 금고와 분리.
- 머지 위임 조건 ④(저장 키·서버 전송 변경 0) 위반 → 위임 불가, 대표 승인 트랙.

## 4. 서버로 나가는 값
늘어남: endpoint·p256dh·auth, 카탈로그 ID(고정 15개 이내)·조건 2값. 자산 수량·금액·보유 종목 0. 역산 불가 근거: 대상은 보유와 무관한 서버 고정 목록에서 고른 값(자산 정보 0·자유 입력 0), 알림 내용은 대상별 공통 시장 수치, 서버는 구독자별 개인 데이터가 없음. 잔여 위험: endpoint = 기기 식별자(IP·UA·로그 저장 금지로 완화), 대상 조합 지문(고정 15개·프리셋 없이 개별 선택이라 조합 수 증가 → 사용자 수가 적어 식별 대상은 되나 개인 자산과 무관, 인지 필요).
