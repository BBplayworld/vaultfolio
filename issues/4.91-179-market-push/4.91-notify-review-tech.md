# #179 '내 자산' 개인 알림 기술 판정 (조사만, 코드 수정 없음)

기준: origin/main 저장소 코드, origin/issue-4.91(`public/sw.js`, `src/lib/push/*`). 웹 출처는 지식 기준(이 세션은 외부 접근 미확인)이라 "확인 필요"로 표시.

## 결론
서버가 자산을 모르는 채 '내 자산' 알림은 **이론상 가능하나 iOS PWA에서 신뢰할 수 없고, 저장 구조 변경(risk:high)이 따른다.** 현 시점 권장은 공통 메시지형 유지(③)이고, 개인 알림은 보류하거나 "앱을 열 때 보여주는 카드"로 대체한다.

## ① 공통 트리거 Push + SW가 기기 안에서 개인 알림 생성
| 항목 | 판정 |
|---|---|
| SW의 데이터 접근 | **불가(현 구조)**. 자산은 `localStorage`(`src/lib/local-storage.ts` `STORAGE_KEYS.assetData` 등)에 있고 SW에는 localStorage가 없다. IndexedDB는 가능 |
| IndexedDB 미러 | 필요. 앱이 저장할 때마다 보유 요약(종목·수량·평가용 값)을 IDB에 복제. 새 저장소 추가이며 저장 키·스키마가 새로 생기므로 **risk:high**, 마이그레이션·복원 테스트 필수. 쓰기 경로가 하나 더 생겨 두 저장소 불일치(삭제·초기화·E2EE 복원 후 미러 잔존) 위험. "모든 데이터 삭제" 경로에서 미러 삭제 누락 시 개인정보 잔존 |
| 보안 | 평문 IDB 복제는 localStorage와 동일 수준(같은 origin). E2EE 키(`cloud-sync/crypto.ts`의 encKey는 non-extractable CryptoKey)를 SW와 공유하려면 IDB에 CryptoKey 저장이 필요해 범위가 커진다. 동기화 데이터를 SW가 직접 복호할 필요는 없다(미러만으로 충분) |
| iOS PWA userVisibleOnly | iOS(16.4+ 홈 화면 추가)는 push 수신 시 **반드시 알림을 표시**해야 하며 무표시 반복 시 구독이 취소된다(Apple 문서·WebKit 블로그, 확인 필요). SW가 계산 실패(IDB 비어 있음·fetch 실패)해도 **폴백 알림을 띄워야** 한다 → 폴백은 공통 문구(현 sw.js `PUSH_FALLBACK`과 동일 패턴) |
| 실행 시간 | push 이벤트는 `waitUntil` 안에서 수 초 내 종료해야 한다(브라우저·OS별 비공개 한도, iOS는 특히 짧다). IDB 읽기+시세 fetch 1회는 보통 가능하나 보장 없음. Background Sync/Periodic Background Sync는 **iOS 미지원**, 사용 불가 |
| SW의 시세 조회와 서버 노출 | 현 앱 시세 API는 종목 코드 목록을 쿼리로 받는다(`/api/finance/profit?tickers=`, `crypto?symbols=`). SW가 같은 API를 쓰면 **서버가 보유 종목 목록을 알게 된다**(수량·금액은 아님). 앱 본체도 이미 같은 방식이므로 새 노출은 아니지만, 푸시 구독(endpoint)과 같은 요청 흐름으로 묶이면 "구독자 X의 종목" 연결이 가능해진다. SW 요청에는 쿠키·식별자가 없으나 IP·타이밍은 남는다 |
| 대안(노출 0) | (a) **공통 지수만** 조회 → 개인 비중 계산 불가 (b) **전 종목/카테고리 묶음 응답**: 서버가 공통 스냅샷(예: 카탈로그 대형주+지수 N개) 하나를 캐시 응답하고 SW가 필요한 것만 고름. 보유 종목이 카탈로그 밖이면 계산 불가라 '내 순자산 ±N%'는 부정확 (c) 푸시 payload에 공통 시세 스냅샷을 암호화 포함(RFC 8291, 4KB 한도) → fetch 없이 SW가 계산. 한도상 수십 종목 이내 |
| 정확도 | 순자산은 환율·부동산·현금·부채 포함이라 지수만으로 대부분 값이 안 나온다. SW가 앱의 계산 로직(`src/lib/finance/*`)을 재구현·번들해야 해 규모 큼 |
| 규모 | 큼: IDB 미러 + SW용 계산 번들 + 마이그레이션·테스트 + 폴백 설계 + QA(iOS 실기기 필수). 대략 신규 파일 8~12개, 기존 저장 경로 수정 |
| 위험 등급 | **risk:high**(저장 구조 추가, 데이터 삭제·복원 경로 영향, 원칙 해석 논쟁 여지) |

## ② 로컬 알림 예약 (Notification Triggers / TimestampTrigger)
- Chrome이 2022년 origin trial 후 **제거**했고 표준화되지 않았다. Firefox·Safari 미지원(확인 필요: chromestatus "Notification Triggers" 상태). **사용 불가**
- 대체: Periodic Background Sync(Chromium 설치 PWA만, 간격 브라우저 임의, iOS 미지원), 앱 열린 상태의 `setTimeout`(닫히면 소멸). 신뢰할 수 있는 예약 수단이 없다.
- 결론: 서버 Push가 유일하게 신뢰 가능한 "앱이 닫혀 있을 때" 경로이고, 그래서 ①이 필요해진다.

## ③ 공통 메시지형(월 결산 열림·세금 일정 등) 전환 난이도
현 구조: `src/lib/push/catalog.ts`(14개 ID, `PushSource` 종류 4개) → `cron-run.ts`(시장 회차별) → `message.ts`(순수 함수) → `send.ts`, 구독은 `subscribe`에 ID 배열 저장, SW는 `{m,t,b}` 3필드만 표시, vercel.json crons 2개(kr 07:00, us 00:00 UTC).
- **쉬움**: 개인정보가 없는 달력형 메시지는 구조 재사용이 높다. 필요 변경: `PushMarket`에 `"calendar"` 회차 추가(`types.ts`), `catalog.ts`에 `kind:"calendar"` 항목, 메시지 생성은 시세 조회 없이 날짜 기반 문구(`message.ts` 신규 함수 1개), `sw.js` `PUSH_TAGS`에 태그 1개, `validate.ts` ID 검증은 카탈로그 기반이라 자동 흡수. 구독 스키마(ID 배열)는 변경 없음 → 마이그레이션 불필요
- **주의**: Vercel Hobby cron은 일 1회·개수 제한(한도는 플랜 확인 필요). 현재 2개에 `calendar` 1개 추가는 가능하나 cron이 `*/월 N일` 같은 단일 일정이면 하루 1회 cron 한 개로 월 결산(매월 1일)·세금 일정(고정일)을 함께 처리해 개수를 늘리지 않는 편이 안전하다
- 규모: 소(신규 파일 0~1, 수정 5~6, 테스트 추가). 위험 등급 `risk:medium`(서버 저장 스키마 변경 없음 전제, 구독 ID 확장은 구버전 클라이언트가 모르는 ID를 무시하는 현재 규칙으로 호환)
- 문구 제약: 투자 조언 금지, 구체 금액 금지 준수. 4.91 보안 점검 ⑤(페이로드 3필드·암호화) 그대로 유지 가능

## 권고
1. 개인 순자산 알림은 이번에 하지 않는다. 하려면 별도 이슈로 "IDB 미러 + iOS 실기기 검증"을 선행 스파이크로 두고 risk:high 절차(spec·마이그레이션 테스트)를 밟는다.
2. 대표가 알림 가치를 인정하면 ③의 달력형 메시지부터 소규모로 확장한다.
3. 개인성은 알림 대신 "앱을 열었을 때"(홈 오늘 시장·결산 카드)에서 제공한다. 서버 노출·저장 변경 없음.
