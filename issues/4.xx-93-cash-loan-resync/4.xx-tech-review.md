## 2. 핵심 설계 검토
**저장 1회(C37).** `saveData`(`asset-data-context.tsx:1175`)는 `useCallback([])`급이라 stable하고 인자로 받은 data만 쓴다. 문제는 `updateCash`(`:1420`)가 렌더 시점 `assetData` 클로저를 쓰는 것. 해법은 4.50 resync가 이미 쓰는 패턴과 동일: 저장 핸들러 안에서 `const fresh = getAssetData()`(`@/lib/asset/asset-storage`, localStorage 정본, 4.50 `holdings-resync-dialog.tsx:312`) → `applyBalanceEdits(fresh.cash, edits)` → `saveData({ ...fresh, cash: next.list })` 1회. context 신규 API 0(`asset-data-context.tsx` diff 0이 기본, 4.50도 안 건드림).
- 시그니처 안: `applyBalanceEdits<T extends {id:string;balance:number}>(list:T[], edits:Record<string,number>) => { list:T[]; applied:number }`. 목록에 없는 id는 건너뜀(되살림 0), 같은 값은 applied에 안 셈, `balance` 외 필드는 `{...item, balance}`로 보존. `applied===0`이면 호출부가 저장 0.
- 저장 후 `saveData`가 `setAssetData` + `notifyAssetUserEdit` 1회 발행 → 동기화 push 경로는 기존 사용자 편집과 동일. 우회 저장(`saveAssetData` 직접) 금지.
- **overwrite-guard 영향 없음.** `cloud-sync/overwrite-guard.ts`는 메모리 baseline vs pull 결과 비교이며 cash/loans는 자동 갱신 필드가 없어(파일 주석 표) 사용자 `balance` 수정은 일반 편집으로 감지·되돌리기 대상이 된다. 코드 변경 0.
- `markCategoryRefreshed(kind)`는 `saveData` 반환 true 직후 1회, 스크린샷 import와 같은 위치·순서(`cash-screenshot-import.tsx:188`). 실패 시 호출·GA·성공 토스트 0. 렌더·effect 중 호출 0.
- 데이터 접근 주의: 화면에 표시하는 `현재 …원`은 열 때 `assetData`(훅), 저장은 `getAssetData()`. 두 값이 다르면 반영 건수가 줄 수 있음 -> 토스트 N=`applied`.

**스냅샷 귀속 — spec 7절 정정 필요(중요).** spec은 "저장한 날의 달에 업서트"라 적었으나 코드상 `saveData`는 스냅샷을 쓰지 않는다. `saveSnapshots`는 `initAndSync`(앱 시작·`refreshData`)와 0→양수 effect에서만 호출된다(`asset-data-context.tsx:856-923`). 즉 12/30 수정 후 앱을 닫고 1/3에 처음 열면 12월 스냅샷은 수정 전 값이고 수정값은 1월 스냅샷에 들어간다(앱을 12/30~12/31에 다시 열면 12월). 결산 12월 반영은 **"수정 후 같은 달 안에 앱이 한 번 더 동기화돼야"** 보장된다. 이는 기존 상세 수정도 동일한 현행 동작이다. 권고: v1에서 `saveSnapshots`를 건드리지 않는다(결산 diff 0·위험↑). spec 7절 사례를 "다음 스냅샷 동기화 시점의 달" 로 정정하고, vitest는 날짜 고정으로 `settlement.ts`에 스냅샷 입력을 직접 주는 방식(저장 로직 테스트와 분리)으로 쓴다. 화면·토스트에 반영 문구 0 방침이 이 불확실성과도 맞는다.
