## 후보 1. 스크린샷 한 번에 전체 등록 (재평가: 기존 후보)
- 내용: 사진 여러 장 선택 -> 유형(주식·코인·현금·대출) 자동 판별 -> 유형별 묶음 미리보기 1화면 -> "전체 등록" 1탭. 4단계 마법사를 이 화면으로 대체.
- 병목 연결: 병목 2 중 "단계 수·준비" 부분만. welcome에서 CTA를 안 누른 6/7에는 직접 효과가 약하다(가설 H1·H2 미해소).
- 보수적 기여: 유입이 안 늘어서 신규 활성 수 기여는 0에 가깝다. Δ등록 = 월 welcome 15 x 시작률 14% x 완주율 개선 +25%p x 보정 0.7 = **+0.4/월**. 정직하게 "방향 확인 수준".
- 지표: `wizard_step`/`screenshot_parse`에 `method: batch` 값 1개. 시작->first_asset_saved 비율.
- 규모·위험: L, medium. 서버 라우트 변경(유형 자동 판별 프롬프트), 호출 증가로 하루 한도 소비 증가(전역 300, 마법사 1회 4~8호출 -> 일 신규 상한 40~75). 스키마·저장 키 무변경. 저장은 기존 `*-screenshot-import` 로직 재사용.
- 체험 모드 관계: 충돌 없음, 시너지 중간("보고 -> 쉽게 등록"). 단 둘 다 웰컴/등록 경로라 #48 코호트가 겹친다.
- 평가: 안전하고 재사용도 크지만 **확장이 아니라 개선**이고 기여가 가장 작다.

- 기여(참고): ΔGA활성 +2~15, Δ등록 +1~4(v3 산식). 가정 의존이 가장 크다.

## 후보 3 (신규). 스크린샷 비중 미리보기 — 로그인·설치 없이 증권앱 화면 1장으로 "내 비중" 보기 (새 공개 페이지)
- 누구의 어떤 문제: 엑셀·노션으로 종목 비중을 직접 계산하던 3040. 앱을 설치하고 금고를 만들어야 결과를 보는 지금 구조 때문에 "한번 해보기"가 없다. 대표가 매주 올리는 Threads·블로그·카페 글에 걸 **행동 유도 링크(설치 앱이 아니라 "증권앱 캡처 1장 올려서 비중 보기")** 도 없다.
- 흐름: 새 라우트(`(main)` 밖, 예: `/preview-ratio` 류 — 이름은 spec에서) -> 주식 스크린샷 1장 업로드(기존 `/api/parse-screenshot` assetType=stock) -> **저장하지 않고** 화면 메모리에서 종목 비중 링·국내/해외/ETF 구성·월 배당 분포(기존 `/api/finance/dividend`) 표시 -> "내 기기에 저장하고 계속 관리" 버튼 = 기존 `StockScreenshotImport`의 저장 경로로 이어서 등록(같은 이미지 재업로드 없이 파싱 결과 인계). 결과 화면에는 투자 조언 문구·금액 공유 유도 없음, 금액은 기본 가리기 토글.
- 병목 연결: 유입(링크 한 줄로 열리는 별도 입구, 검색 롱테일 "주식 비중 계산" 보조)과 병목 2(등록 전에 **내 데이터로** 가치 체감 = 체험 모드의 샘플 한계를 보완). 두 병목을 한 구조로 잇는 유일한 후보.
- 보수적 월 활성 기여 산식 (가정 값 모두 노출, 실측 없음):
  - 입구 방문 = 채널 글 클릭 월 30 (현재 first_visit 17의 약 2배 가정, UTM 규약이 없어 현 클릭 수 미확인 -> 불확실)

  - **Δ등록** = 완료 3.6 x 저장 전환 30% x 0.7 = **+0.8/월** (범위 +0.5~2)
  - 합산: 단독으로 100명 도달 불가. 판정은 "채널 노출을 늘렸을 때 효과가 측정되는 입구가 생겼다"가 핵심 가치.

- 규모·위험: M~L, **risk medium**.
  - 데이터 안전: 사용자 금고(localStorage)를 읽거나 쓰지 않는 격리 페이지. 저장은 사용자가 버튼을 눌렀을 때만 기존 경로. 스키마 무변경 -> risk:high 아님.

  - 투자 조언: 비중·구성 사실 표시만, 추천·평가 문구 금지.
- 재사용 근거 (신규 엔진 없음): 파싱 `parse-screenshot` 라우트와 `stock-screenshot-import.tsx`의 파싱·미리보기·저장 로직(`:132`), 비중·구성 계산은 기존 홈 구성 차트·`asset-grade.ts` 분산 계산, 배당은 `/api/finance/dividend`·`monthly-dividend-stocks.tsx`, 가리기 패턴은 v4.37 AI 프롬프트 금액 가리기, 가드는 `api-guard`.

## 추천: 후보 3 (조건부), 후보 1은 후속
근거:
1. 병목 1(유입)에 직접 닿는 후보는 3뿐이다. 후보 1은 유입이 늘지 않아 기여 +0.4, 후보 2는 체험 모드와 가설 중복이다.
2. 4.38이 전환(체험)·도착(인앱)을 이미 해결하므로, 같은 구간을 반복하지 않고 **새 입구**를 만드는 것이 서로 겹치지 않는다.
3. 위험이 데이터 격리로 통제된다(금고 미접촉, 스키마 무변경). 재사용 비율이 높아 신규 엔진이 없다.
4. 스크린샷 등록 중심 유지, 새 URL 허용 범위 안.

솔직한 한계:
- 산식의 방문 30·시도 15%는 근거 없는 가정이다. 현재 채널 클릭 수를 모른다. 선행으로 마케팅 초안에 UTM 규약(source=threads|cafe|blog)을 넣어 클릭을 먼저 재야 한다(코드 변경 없음, business-pm 즉시 가능).
- 전역 Gemini 한도가 공유 자원이라 입구 전용 상한이 없으면 오히려 기존 사용자 해를 줄 수 있다. 이 설계가 spec에서 통과하지 않으면 보류하고 후보 1로 전환한다.
- 업로드 시도율 15%는 "계좌 화면을 낯선 사이트에 올린다"는 신뢰 장벽(H4) 때문에 더 낮을 수 있다. 기대치가 가장 불확실한 후보라 v1은 주식 1장만으로 제한하고 8주 후 판독.
- 후보 3을 하면 검색 SEO(G2)와 같은 새 입구 구조를 쓰므로, G2 재개 때 이 페이지의 메타·sitemap을 같이 정리한다.

일정 제안: spec·tech-review 11/1~11/14(문서, 체험 모드 문서와 병렬), 개발은 4.38 머지 직후(11/27 이후, 결산 화면 무접촉이라 창과 무관), qa 후 owner-review. #58(4.39 예정, 12/11 개발)과 순서가 겹치므로 **대표 판단: 4.39를 이 과제에, #58을 4.40으로 미룰지**(#58은 risk:high 대표 승인 대기 중이라 순서 조정에 비용 적음).
