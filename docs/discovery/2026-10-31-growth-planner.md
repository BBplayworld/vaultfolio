# 월 신규 활성 유저 확대 후보 (planner-designer, 2026-10-31)

전제: 월 신규 약 17명, 웰컴 조회 월 약 15기기. 대표 지시로 D 동결 해제. 11/27~12/10 결산 화면·홈 팁 무접촉(아래 후보는 모두 해당 파일 미접촉). 릴리스는 11/26 이전(4.38) 반영 후 창 동안 관찰만 한다.
진단: 유입이 좁은 만큼 "들어온 사람이 첫 화면을 못 보거나(A), 첫 등록 경로가 막히거나(B·C), 공유로 되돌아올 길이 없는(D)" 지점을 고치는 것이 우선. 표본이 작아(웰컴 7기기) 아래 근거는 코드 기준이며, GA 수치는 사전 확인 항목으로 둔다.
기존 후보(G2 SSR·sitemap, G3 #33, E2 체험 모드, E3 v2, AI 프롬프트 v2)와 반려(#45, 스트릭 카드, 워터마크, 대기업 방식)는 반복하지 않음.

## 후보 A (1순위) — 인앱 브라우저의 자산 0건 방문자에게 웰컴을 먼저 보여주기
- 문제: 카페·Threads·블로그(DECISIONS 시드3 채널)·카톡 링크는 대부분 인앱 브라우저로 열린다. 현재는 자산 0건 첫 방문자도 전체 화면이 "외부 브라우저에서 열어주세요" 하드 게이트로 가려져, 앱이 뭔지 보기 전에 이탈한다. 게이트 사유(세션 끊김 데이터 유실)는 데이터가 생긴 뒤의 문제인데 0건 방문자에게도 똑같이 적용된다.
- 사용자 흐름: ① 인앱에서 링크 클릭 → 웰컴(히어로·신뢰 한 줄·포트폴리오 미리보기) 그대로 노출 ② 시작 CTA 슬롯만 "외부 브라우저에서 시작하기"(기존 게이트의 go/iOS 가이드 재사용)로 대체 ③ 외부 브라우저에서 기존 웰컴 → 등록. 자산이 1건이라도 있으면 지금처럼 전체 게이트 유지(데이터 안전 불변).
- 줄이기·고치기 성격: 신규 화면 없음. `welcomeCtaState`에 "inapp" 상태 1개 추가(주석상 이미 "#33 대체 지점"인 CTA 슬롯 활용), 게이트 조건에 `hasAssets`만 추가.
- 지표(기존 이벤트만): 인앱 노출 = `welcome_view`(source=inapp, 게이트 뒤에서도 이미 발생), 이동 클릭 = `pwa_install`(method=inapp_move, source=inapp). 성공 기준: 이동 클릭 기기 ÷ welcome_view(inapp) 기기가 변경 전 게이트 클릭률보다 상승. 사전 확인: GA에서 welcome_view source별 비율(inapp 비중 15% 미만이면 우선순위 하향).
- 규모·위험: S~M, risk medium(데이터 안전 경로 변경: 0건 판정 이전에 쓰기·동기화·시세 경로가 열리지 않는지 `isBackgroundWorkBlocked` 소비처 전수 확인, 자산 생성 진입점 4곳이 인앱에서 막히는지 qa 검증). 스키마 무변경.
- 코드 근거: `app/(main)/layout.tsx:51` 게이트 전역 마운트 / `in-app-browser-gate.tsx:37`(`!isInApp`만 보고 hasAssets 무시)·`:75-79`·`:83-91` / `lib/pwa/detect-browser.ts:17,74-77` / `welcome-guide.tsx:84-89,101,190-199`.
- 확인 필요(검증 못 함): IN_APP_BROWSER_RE(`detect-browser.ts:17`)에 Threads("Barcelona" UA 추정)·다음·밴드가 없어 일부 인앱은 게이트 없이 열려 데이터 유실 위험이 있을 수 있음 — 실기기 UA 확인 후 별도 판단.
- 충돌: 결산 창 없음. #48 첫 화면 퍼널은 inapp 코호트만 변경 → welcome_view source=inapp를 #48 분모에서 제외하면 판독 가능(변경 시점·코호트 기록).

## 후보 B (2순위, 대표 확인 필요) — 스크린샷 업로드 전 "AI 서버 처리" 사실 고지 정정
- 문제: 주 CTA(스크린샷 등록)는 이미지를 서버(/api/parse-screenshot, 외부 Gemini 호출)로 보내는데, 첫 화면은 "자산은 내 기기에만"·카드 문구 "데이터가 기기를 절대 벗어나지 않습니다", 업로드 다이얼로그는 "개인정보 측면에서 문제없습니다"로만 안내한다. 업로드 직전에 사실과 어긋난 안심 문구는 신뢰를 깨는 지점이자 DECISIONS(2026-10-31 마케팅, "대표 확인 필요")의 미해결 항목이다.
- 사용자 흐름: 업로드 다이얼로그 안내 박스를 사실 기반 2문장으로 교체("이미지는 종목 인식에만 쓰이고 저장되지 않아요"는 서버 코드 `route.ts:690` 근거로 확인된 범위만, 계좌번호 등 가리고 올리라는 안내). 첫 화면 보안 카드 1번 문구는 "저장된 자산 데이터" 범위로 정정.
- 지표: 기존 `onboarding_action`(method=wizard) 기기 → `screenshot_parse`(result=success) 기기 전환율 전후 비교. 하락해도 정직성 복구가 우선이므로 가드레일이 아니라 "관측값"으로 둠.
- 규모·위험: S(카피만), risk low. 단 "서버 단정 금지"(대표 2026-10-31 보안 메시지 기준)와 PRINCIPLES 2장(서버 역할 2가지)과 현실의 차이를 건드리므로 문구는 대표 확인 후 확정(원칙 변경 아님, 사실 정정). 사실 확인(보관·로그 여부, Gemini 약관상 학습 사용 여부)은 cto/개발 선행.
- 코드 근거: `stock-screenshot-import.tsx:371-373`(동일 문구가 cash/crypto/loan 다이얼로그에도 있는지 확인 필요), `welcome-guide.tsx:128-133,161`, `onboarding-wizard-flow.tsx:93`, `app/api/parse-screenshot/route.ts:2,690`.
- 충돌: 결산 창 없음. #48: 첫 화면 보안 카드 1개 문구 수정이 포함되므로 변경 시점만 기록(퍼널 구조 불변).

## 후보 C (3순위) — 첫 등록까지 단계 줄이기: 웰컴 "직접 입력"에 현금 추가 + 마법사 중도 종료 노출
- 문제 1: 스크린샷이 없거나 올리기 싫은 사용자의 수동 경로가 웰컴에서는 "주식 직접 입력" 하나뿐이다. 현금·코인·부동산·대출만 있는 사용자는 마법사/스크린샷 외 길이 없다. 현금은 이름·잔액 2개 입력으로 끝나 가장 낮은 진입 비용인데 숨어 있다.
- 문제 2: 마법사는 주식→코인→현금→대출 4단계 순차인데, 첫 저장 직후에도 나머지 단계가 계속 이어지고 "홈 보기"는 작은 X 아이콘뿐이다. 현금만 가진 사용자는 "없어요"를 두 번 누른다.
- 사용자 흐름: ① 웰컴 "직접 입력·가져오기" 팝오버에 "현금 직접 입력" 1줄 추가(숨은 `CashInput`이 이미 마운트되어 `trigger-add-cash` 이벤트 재사용) ② 마법사에서 1건 이상 저장된 뒤에는 단계 화면에 "여기까지 저장하고 홈 보기" 텍스트 버튼(기존 `finish` 재사용, 새 화면 없음).
- 지표(기존만): `onboarding_action`(method=manual)·`asset_add_start`(asset_type=cash, method=manual) → `first_asset_saved`(asset_type 분포). 마법사: `wizard_step` step=complete 대비 step=exit 비율, 중도 종료 시 기존 result 값(done) 부여로 "저장 후 종료"와 "미저장 이탈" 구분. 성공 기준: first_asset_saved 기기 ÷ onboarding_action 기기 상승.
- 규모·위험: S, risk low(UI 연결만, 스키마·저장 로직 무변경).
- 코드 근거: `welcome-guide.tsx:330-334,360-395`, `welcome` 숨김 입력 `page.tsx:91-96`, `floating-add-button.tsx:38-45,129-138`, `onboarding-wizard-flow.tsx:44-52,70-99,124-149`.
- 한계: 현재 GA 표본에 wizard_step·screenshot_parse가 0건이라 마법사 이탈 지점은 코드 추정이다. 현금 경로는 효과 불확실 → 4.38에서 팝오버 1줄 + 마법사 버튼 1개로 한정하고 8주 후 판독.
- 충돌: 결산 창 없음. #48: 웰컴 CTA 팝오버 항목 1개 추가(주 CTA·순서 불변)라 퍼널 정의는 유지, 변경 시점 기록.

## 후보 D (4순위, 착수 비권고 — 대표 판단) — 유형 카드 공유 시 앱으로 돌아올 길
- 현황: 인증카드 공유는 이미지 파일만 `navigator.share({ files })`로 보내 본문·링크가 없고 워터마크는 "S" 아이콘만(DECISIONS 2026-08)이라, 받은 사람이 앱을 찾을 방법이 없다. share 이벤트 28일 0건이라 효과 크기도 미확인.
- 안: 공유 시트 기본 텍스트(사용자가 지우거나 수정 가능)에 "나는 어떤 투자 유형일까?" 한 줄 + 사이트 주소. 금액 없음, "재미" 프레임 유지.
- 충돌 위험: LEARNINGS "도메인·서비스명 워터마크 반려", "자산·성과 공유는 부담". 이미지가 아닌 편집 가능한 텍스트라는 차이가 있으나 같은 반감 가능성이 있어 대표가 허용하지 않으면 접는다. 지표는 `share`(method=share, content_type=type) 후 신규 `first_visit` 증가는 귀속 불가 → 판독 곤란.
