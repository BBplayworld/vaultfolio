# S-4.24 대출 상환/추가 대출(마이너스통장) 거래내역

> 상태: 완료 | 브랜치: `issue-4.24-loan-transactions` | 작성 2026-08-02

## 1. 왜
대출(`loans[]`)은 `balance` 단일 스칼라만 있고 이력 개념이 전혀 없다(`src/types/asset.ts:124-137`) — 상환·추가 대출(마이너스통장 사용액 증감 등)은 사용자가 잔액을 직접 덮어쓰는 방식뿐이다. 그 결과 자산 성적표의 "순자산 변화, 왜?" 원인분해에서 대출 잔액 증감(`debt` cause)은 "얼마 변했다"만 계산될 뿐 "상환인지 추가 대출인지, 언제 얼마씩 있었는지"를 설명하지 못한다. 현금은 이미 S-4.22에서 같은 문제(`cash.balance` 단일값)를 입출금 거래내역으로 해결했다 — 대출도 같은 구조적 결함을 겪고 있다.

## 2. 무엇 (범위)
- 포함:
  - 대출 자산에 **상환/추가 대출 거래내역**(현금 `cashTransactions` 패턴 답습, 잔액 선형 가감).
  - 반영(reflected) ON 시 `loans[].balance` 자동 가감, OFF는 로그만(과거 소급 기록).
  - `loanSchema.balance`의 `.refine(val => val > 0)`를 완화해 **0(전액 상환)을 허용**.
  - 잔액 0 대출은 **완납**으로 표시하고, 대출 탭의 현재 대출 현황(목록·잔액/이자 집계·부채비율·레버리지 박스)에서는 제외하되, 데이터와 거래내역은 **히스토리로 보존**(삭제하지 않음).
  - 자산 성적표 원인분해의 기존 `debt` cause를 기록된 대출 거래 기반으로 정확화(신규 cause 키는 만들지 않음).
  - 공유 토큰·JSON 내보내기에 대출 거래내역 포함.
- **제외**:
  - 이자 자동 계산·상환 스케줄(원리금균등 등) — 이번 범위는 원금 잔액 가감만.
  - 마이너스통장 한도(limit) 필드 신설 — 기존처럼 `description` 자유텍스트로 한도를 남기는 관행 유지.
  - 대출 스크린샷 일괄 가져오기.
  - 현금 `cashSchema.balance`의 동일한 `> 0` refine 완화 — 이번엔 대출만 다룬다(현금 쪽은 별도 판단 필요, 잠재 이슈로만 기록).
  - `debt` cause를 상환/신규대출 두 개로 쪼개는 것 — 표시 항목 수를 늘리지 않기로 결정(사용자 확정).
  - `asset-options.ts`의 `loanTypes`에 있는 `{ value: "tenant" }`(표시 전용 가상 카테고리, `loanSchema` enum에는 없음) 정합화 — 이번 범위 밖, 아래 "영향 표면" 주의사항으로만 기록.

## 3. 수용 기준

- [x] AC1. 대출 카드에서 "상환/대출 내역" 진입 → 상환/추가 대출 기록 폼(금액·날짜·메모, 반영 ON/OFF)과 로그 뷰(기간·유형 필터, 총상환·총추가·순상환 통계).
- [x] AC2. WHEN 반영(reflected) ON 상환을 기록하면, 시스템은 해당 `loan.balance`를 `−amount` 하고 로그+잔액을 **단일 저장**한다. 추가 대출이면 `+amount`.
- [x] AC3. WHEN 반영 ON 상환액이 현재 잔액을 초과하면, 시스템은 기록을 **차단**(restrict)한다(현금 출금 초과 가드와 대칭 — `isCashWithdrawalValid` 동형).
- [x] AC4. WHEN 반영 ON 거래를 삭제하면, 시스템은 `loan.balance`를 역가감하고 로그+잔액을 단일 저장한다. 미반영 거래 삭제는 잔액 불변.
- [x] AC5. WHEN 거래 날짜가 오늘 기준 3년(`TRANSACTION_RETENTION_YEARS`) 밖이면, 시스템은 저장 시 해당 로그를 정리(prune)한다.
- [x] AC6. WHEN 반영 ON 상환으로 `loan.balance`가 정확히 0이 되면, 시스템은 해당 대출을 **완납**으로 표시하고 대출 탭의 목록·잔액 합계·이자 집계·부채비율·레버리지 박스 계산에서 **제외**한다. 대출 데이터·거래내역 자체는 삭제하지 않는다(히스토리 보존).
- [x] AC7. WHEN 완납 대출에 추가 대출(반영 ON, `+amount`)을 기록하면, 시스템은 해당 대출을 다시 활성 상태로 되돌려 대출 현황에 포함한다.
- [x] AC8. 원인분해 기간 내 **반영된** 대출 거래 순액(Σ상환−Σ추가대출)이 기존 `debt` cause에 반영되어, 잔액 델타만으로 계산하던 것보다 정확도가 높아진다. **표시 금액 합계 = deltaNet 불변**(현금의 `reflectedCashInflow`와 동형 구조로 `debt` 잔차를 보정).
- [x] AC9. WHEN 공유 URL을 생성·복원하면, 시스템은 대출 거래내역을 손실 없이 왕복하고 부모 대출(`loanIdx`)에 재연결한다. 구버전 공유 토큰(대출 거래 미포함)도 정상 파싱한다(R3).
- [x] AC10. 구버전 백업 JSON(대출 거래 필드 없음, 대출 `balance > 0` 필수였던 구버전 포함)이 `applyImportedPayload`를 통과한다(신규 필드는 optional/default, `balance` 하한 완화는 기존 데이터와 호환).

- 컨텍스트·유틸: `asset-data-context`(CRUD 단일저장 4곳, `cashTransactions` CRUD와 동형) · 신규 `lib/loan-tx-utils.ts`(`pruneLoanTransactions`·`findDuplicateLoanTx`·`reflectedLoanBalanceDelta`·`isLoanRepaymentValid`, `cash-tx-utils.ts` 미러링) · 신규 `stores/loan-tx-view-store.ts` · `lib/report/asset-report.ts`(`debt` cause에 `reflectedLoanFlow` 형태로 반영, 신규 cause 키 없음).
- API·캐시 키: 없음(외부 API 무관).
- **건드리지 않는 것**: `cashSchema`·`cashTransactions`(참조만) · `getAssetSummary`/`computeNetAsset`/스냅샷 계산의 `loanBalance` 집계 방식 자체(완납 제외는 대출 탭 표시 레이어에서 처리, 집계 함수는 `balance` 그대로 합산 — 완납은 balance=0이라 자연히 0으로 반영됨) · 주식 `transactions`·`trade-utils`(참조만) · `debt` cause를 두 개로 분리하는 것(제외 확정).

### 주의사항
- `loanSchema.balance`와 `cashSchema.balance` 양쪽 다 `.refine(val => val > 0)`가 있다(`asset.ts:128, 144`) — 이번엔 대출만 완화한다. 현금 쪽에 동일 이슈가 잠재해 있음을 인지만 하고 넘어간다.
- `asset-options.ts`의 `loanTypes`에 `{ value: "tenant", label: "임차보증금" }`가 있으나 `loanSchema` enum에는 없다(표시·필터 전용 가상 카테고리). 완납 섹션 UI 작업 시 이 불일치로 인한 필터링 오류에 주의.
- 대출은 현금과 같은 **잔액 선형 가감**이라 주식의 `computeNewPosition`/`recomputeFromLog` 같은 가중평균 포지션 재계산은 불필요 — `cash-tx-utils.ts`(38줄) 계열만 미러링하면 된다.
